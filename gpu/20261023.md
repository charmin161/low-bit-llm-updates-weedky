<a id="triton-tmem-scale-lifetime"></a>
## 同一 partition 也须等 MMA 读完 scale｜TRITON-TMEM-SCALE-LIFETIME｜已合入主分支｜10-22 UTC｜Blackwell / Triton NVWS

**结论：** Triton 修复 warp-specialized scaled matmul 的 TMEM scale 复用同步：producer 与异步 consumer 在同一 partition，不能保证下一轮覆盖 scale 时上一轮已读完。

**技术机制与证据：** 数据路径是“producer 构造 scale → 初始化 TMEM → 异步 MMA 读取 → accumulator/output”。旧分析在初始化和消费属于同一 partition 时跳过同步，遗漏指令发出与实际读完成的时间差。persistent 外循环随后初始化新 scale，可能覆盖仍在使用的数据。补丁通过已有 aref producer/consumer 周期建立顺序，并在拆除 barrier 前等待最终 consumer 完成。需要保护的是 scale 生命周期，不仅是 A/B operand 加载完成。[编译器修改与回归测试](https://github.com/triton-lang/triton/commit/1ec1eee840b8a35b15101e5ab9a4388e905291f3)。

新增 Blackwell 回归使用全一 FP8 operand、FP32 accumulator，外层迭代改变 E8M0 scale，并用 ConSan 检查同步。两个输出 tile 的 scale 乘积为 0.5 和 2，K=256 时预期分别为 128 与 512，零容差比较；另测零次迭代，输出保持不变。这比固定 scale 的随机 GEMM 更容易暴露生命周期错误：若每轮 scale 相同，错误复用也可能得到相同数字。测试针对特定序列，不是全部 persistent shape、stage 和 CTA 配置的穷尽证明。

**边界与影响：** 已确认的是主分支编译器及测试变化，不是某个发布 wheel 已修复；固定 Triton 版本的框架须核对所带提交。证据不支持推广到所有 Blackwell GEMM，也不说明硬件违反同步语义。kernel 开发者应把 scale/metadata 当作具有独立异步读生命周期的 operand，构造主矩阵不变、scale 逐轮变化的反例。正确性通过后才能测新增等待是否改变 overlap。本期无 B200 实测，不把 barrier 开销估算为端到端损失。

<a id="triton-ada-fp32-add"></a>
## Ada FP8 dot 外的 FP32 加法不能随意融合｜TRITON-ADA-FP32-ADD｜已合入主分支｜10-22 UTC｜SM89 / L40S

**结论：** Triton 为 SM89 调整默认 accumulation 配置，阻止独立 FP32 加法折入低精度累加 FP8 MMA；源代码 accumulator dtype 并不能独自决定最终数值。

**技术机制与证据：** `acc += tl.dot(a, b)` 与 `tl.dot(a, b, acc)` 数学表达相近，前者可在 dot 外做 FP32 add，后者把已有 accumulator 交给 MMA。旧 SM89 默认 `max_num_imprecise_acc=0` 允许 CombineDotAdd 融合；新代码把 SM89 默认值与 SM90 一样设为非零，由既有 guard 保留外部 FP32 add。显式链式 dot 或用户显式设置零仍保留原行为；这是编译默认语义收紧，不是所有 FP8 MMA 自动升级累加精度。[固定提交](https://github.com/triton-lang/triton/commit/389dd29e1d135b1ba4d449476dfa501c93d7148c)。

提交者在 L40S 报告全一循环从错误的 16,384 恢复到 20,000，bias-add 反例从 1,048,576 恢复到 1,048,608。它们展示独立加法被吸收后的数值差异，不代表真实模型误差幅度。提交说明中 24 个定向 separate-add 用例修复前失败、修复后通过；跨架构 compile-only 成功仅说明能生成代码，不能当作其他 GPU 上的运行正确性证据。

**边界与影响：** 保留更准确加法可能有性能代价，但本期不把未经完整 shape/测量范围复核的延迟汇总作为升级依据。须区分 FP8 存储、MMA operand、内部累加、外部 FP32 add 与输出 cast；输出 FP32 无法恢复中间已经丢失的信息。Ada/Blackwell 共用 kernel 的项目不能从 B200 数值表现推断 L40S，也不能以编译成功代替运行比较。检查优化前后的算子边界很重要：升级后的延迟变化，可能伴随此前被融合破坏的数值语义恢复。本次不推导新 ISA 规格或物理 issue 粒度。

Rubin Adaptive Compression 保留为研究索引观察项。本轮检查 CUTLASS 窗口内提交及官方架构检索结果，未形成可核实的本周新增机制结论，因此不复述历史 sparse descriptor 推测。华为本期确定支持边界见 [DeepInfer](../inference/20261023.md#deepinfer-public-runtime)；Intel 官方检索未找到符合窗口的可靠入选项，覆盖有限不代表没有更新。

<a id="nvshmem-put-signal-order"></a>
## put 的数据与 signal 必须保持同一 QP｜NVSHMEM-PUT-SIGNAL-ORDER｜主分支提交｜10-19 UTC｜IBGDA / GPUNETIO GDAKI

NVSHMEM 修复多 chunk put-with-signal 的接收竞态：数据和通知若选不同 queue pair，收到 signal 不保证先前 payload 已可安全消费。新实现复用所选 QP，并让非阻塞 on-stream 路径走单一 put-signal 操作。它是通信顺序修复，没有改变量化格式，也未给出训练/serving 收益；patch 未新增测试。本次作者日期为 10-15、committer 日期为 10-19，应按本周主分支落地表述，不能称本周才提出机制。[固定 diff](https://github.com/NVIDIA/nvshmem/commit/63da6921a1dbf184a4da293bf3b4cba8af113cee)。
