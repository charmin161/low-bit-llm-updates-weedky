### 发生了什么变化

**已确认事实：CUTLASS 4.8.0 首次在正式 release notes 中明确写出 Rubin Primitives 支持 `2:4 sparsity support for FP4`。** 同一版本还把 Rubin 的高吞吐 FP4 Tensor Core 模式明确为 `MMA_K=128`，并同时公开 B collector reuse、576-column TMEM、328 KB SMEM 等能力。与 8 月 27 日的 `4.8.0dev` 相比，最终版对 FP4 2:4 的表述已经从泛化的 “Rubin FP4 Tensor Core support” 收敛成了明确的 **2:4 sparse FP4 primitive**。:chatgpt-content-reference{index="1"}

更重要的是，我检查了最终版源码，`v4.8.0` 新增了 `Sm107GemmSparseConfig`，文件注释直接写的是 **“SM107 2:4 FP4 compression”**。它把软件侧 contract 写得非常具体：每个 chunk 是 **4 个逻辑 FP4 → 2 个物理 FP4**；每个 4-value chunk 使用 **4 bit metadata**，等价于每个被保留元素 2 bit index；metadata `E` 使用专门的 sparse element 表示，并定义了 **128×128 的 metadata atom/alignment**。同时还新增了 SM107 MXF4 的 `StructuredSparseCompressor` 测试。[SM107 sparse config 源码](https://github.com/NVIDIA/cutlass/blob/v4.8.0/include/cutlass/gemm/collective/builders/sm107_sparse_config.inl?utm_source=chatgpt.com)

这意味着我们现在已经不只是从 PTX 的 `spcompress` 猜数据格式了：**CUTLASS 正式软件层已经开始消费这套 Rubin 2:4 FP4 representation。**

另外一个很值得修正此前理解的点，是 **Rubin FP4 sparse MMA 的 K descriptor 约束现在非常清楚**。PTX 9.4 的 `.kind::mxf4/.kind::mxf4nvf4` descriptor 明确规定：

`dense K64  ↔ sparse K128`  
`dense K96  ↔ sparse K192`  
`dense K128 ↔ sparse invalid`

而 SM107 必须使用 sparsity version `v1`，对应真正的 **2:4**；此前 Blackwell/Blackwell Ultra 的 `v0` 是 pair-wise `4:8`。:chatgpt-content-reference{index="3"}

这一点非常关键：**CUTLASS 4.8 所说的 Rubin “FP4 MMA_K=128”是 dense 高吞吐 FP4 模式，不能直接理解为 sparse K=128 的同一个 issue mode。** sparse 路径有自己独立的 K128/K192 descriptor encoding。

### 证据可靠性与来源等级

本轮核心证据全部属于 **NVIDIA 一级官方证据**：CUTLASS 4.8.0 release、CUTLASS 源码以及 PTX ISA 9.4。

PTX 目前仍是 **9.4**，没有出现更新版本。它继续明确规定 `spcompress` 只允许 `.sp::2:4`，从每 4 个元素选择 2 个，并输出被选元素的位置 metadata；而 `tcgen05.ld{.red}.spcompress` 可以在 **从 TMEM load 时 inline 完成 2:4 compression**，并且该形式只支持 `sm_107a`。:chatgpt-content-reference{index="4"}

Transformer Engine 这边截至当前最新正式版仍然是 **v2.19**，9 月 11 日发布；它只有 “CUDA 13.4+ 下支持 Rubin SM107a”这一层，没有新增公开的 `AdaptiveCompression` recipe/API。:chatgpt-content-reference{index="5"}

CUDA/cuBLAS 本轮也没有出现比上次更直接的 Adaptive Compression 线索：最新公开 CUDA 仍为 **13.4 Update 1 / PTX 9.4**。因此这次的实质增量非常集中：**CUTLASS。** :chatgpt-content-reference{index="6"}

### 对可能技术路线的含义

现在我会把实现路线进一步细化为：

**已确认事实：Rubin 有一套正式的软件可表示的 FP4 2:4 sparse contract。**

它已经形成了：

`dense FP4 A`
→ 2:4 selection/compression
→ `A_compressed + E metadata`
→ SM107 sparse MMA

而且 metadata 的粒度、bit 数、alignment 已经进入 CUTLASS 类型系统，不再只是 ISA 层的抽象描述。

**强证据推断：这大幅提高了“FP4 2:4 是 Rubin Adaptive Compression 核心机制之一”的可信度。** 尤其是 PTX `spcompress` 的语义和 CUTLASS `Sm107GemmSparseConfig` 的数据 contract 正好对得上：

`4 dense values → choose 2 → 2×2-bit positions → compressed A + metadata`

这已经非常接近一条完整的 hardware/software path。

但这里出现了一个值得保留的新分叉：CUTLASS 现在同时存在显式的 **`StructuredSparseCompressor`**，而 PTX 又支持 **`tcgen05.ld{.red}.spcompress` inline compression**。因此目前不能断言 TE3 最终一定采用：

`TMEM → ld.spcompress → mma.sp`

它也可能根据场景采用：

`独立/融合 compressor → packed A + E → mma.sp`

或者由 compiler/kernel planner 在两种路径之间选择。

换句话说，**我们现在对“格式是什么”越来越确定，但对“压缩发生在 pipeline 的哪一级”反而应该避免过早锁死。**

Zero-Column Mask 的判断则完全不变。PTX 仍明确把它定义成 **B 矩阵整列级 mask**，通过 Start Count / Skip Span / Use Span / Column Shift 等字段生成 N-bit column mask；它与 A 侧 2:4 element metadata 是两套独立机制。:chatgpt-content-reference{index="7"}

### 与此前判断相比是否需要修正

**需要两处重要修正。**

第一，应该把“Rubin FP4 2:4 是 Adaptive Compression 核心候选机制”的置信度再提高一级。此前主要是：

**PTX primitive → 强推断**

现在已经变成：

**PTX primitive + CUTLASS 正式 2:4 FP4 primitive + SM107 sparse config + compressor/test → 很强的软件/硬件共证据。**

但仍不能把“NVIDIA Adaptive Compression”这个产品名与它画严格等号，因为 NVIDIA 还没有正式说出：

> Adaptive Compression = SM107 FP4 2:4 sparse path。

所以它仍然属于**强证据推断，而非官方命名确认**。

第二，也是更技术性的修正：**此前不能再笼统把 Rubin 的 FP4 `K=128` 看成统一原子 issue 粒度。** PTX descriptor 已经清楚表明 dense 与 sparse 是不同编码空间：

**dense FP4：K64 / K96 / K128**  
**sparse FP4：K128 / K192，且 dense K128 对应的 sparse encoding 无效。** :chatgpt-content-reference{index="8"}

这对我们之前一直关注的 **K_issue=96 / K=64 atomic step / collector 重打包**尤其重要：现在更合理的模型不是“所有 FP4 都逐渐统一到 K128”，而是 Rubin 内部存在 **dense 和 2:4 sparse 两套不同的 logical-K issue 模式**，且 sparse 的 logical K 正好因为 50% 压缩而翻倍。

因此，本轮我会把当前路线图更新为：

**已确认：Rubin FP4 2:4 已从 ISA 能力进入 CUTLASS 正式 software contract。  
强推断：它极可能是 Adaptive Compression 的核心执行机制之一。  
需要修正：不能把 dense `MMA_K=128` 与 sparse K128 混为一谈，也不能再假定唯一实现一定是 inline `spcompress`。  
仍未确认：TE3 何时/是否公开 Adaptive Compression recipe，以及 TE/cuBLAS 最终选择独立 compressor、inline TMEM compression，还是两者按场景混用。**
