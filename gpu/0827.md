有一项**达到“实质性进展”阈值**的更新，但需要先把范围说清楚：**它推进的是 Rubin / TE3 的 NVFP4 训练数据流，而不是 attention 2:4 `spcompress` 本身。** 对我们判断第三代 Transformer Engine 的整体实现路线有价值，因此我认为值得通知。

### 发生了什么变化

**2026 年 8 月 26 日，NVIDIA 已合并 cuDNN Frontend PR #693。** 这次修改把此前的

`Grouped GEMM → GLU → RHT → NVFP4 quant`

融合 kernel 向前推进了一步：**column-wise RHT 不再输出一个随后还需要 reshuffle 的普通 tensor，而是直接输出成每个 expert 独立、拼接在一起的 ragged NVFP4 布局；这个布局可以被后续 wgrad Grouped GEMM 直接消费。** NVIDIA 在 PR 中明确说明，之前的 reshuffling “significantly reduced its usefulness”，现在每个 expert 的数据直接以 GEMM-friendly 格式放在共享 buffer 的相应 offset。该 PR 已于 8 月 26 日合并到 `develop`。

数据流因此从原先近似的：

```text
FC/Grouped GEMM
      ↓
    SwiGLU
      ↓
      RHT
      ↓
 NVFP4 quant
      ↓
普通 colwise tensor
      ↓
 reshuffle / transpose / repack
      ↓
   wgrad GGEMM
```

变成：

```text
FC/Grouped GEMM
      ↓
    SwiGLU
      ↓
      RHT
      ↓
 NVFP4 quant
      ↓
per-expert ragged / transposed
wgrad-ready NVFP4
      ↓
   wgrad GGEMM
```

这不是简单 API 整理。新的 colwise RHT 输出被定义为 **NVFP4-only**，FP4 payload 按 expert segment 直接以 `(N_out, expert_m)` 的逻辑转置形式排列；对应 block-scale 也按 expert ragged segment 直接存储，因此下一阶段 wgrad 不需要再对 activation 进行一次大规模 layout conversion。

还有一个与我们最近讨论 UE5M3 非常相关的新细节：Rubin kernel 中现在显式设置

```text
rht_sf_dtype =
    UE5M3   if input sf_dtype == UE5M3
    E4M3    otherwise
```

也就是说，在 Rubin 的 UE5M3 路径下，**RHT 后重新量化得到的、直接交给 wgrad 的 block scale 也可以继续保持 UE5M3 语义**，而不是只能让输入 A/B 使用 UE5M3。 同一个 kernel 的 per-expert colwise 分支直接把量化后的 RHT 数据和对应 scale 写入最终 ragged output buffer。

### 证据可靠性与来源等级

这部分我给 **A+ 级证据**。它来自 NVIDIA 官方 `cudnn-frontend`，并且不是 Draft/POC，而是已经 merge 的实际 kernel 修改。PR 的核心目的也明确写成“让输出能够被 wgrad GGEMM 直接消费”，因此这里不需要依赖架构猜测。

TransformerEngine 的 UE5M3 PR #3325 本轮**尚未 merge**，当前仍是 open、非 Draft；它的描述仍是 UE5M3 quantization 原生支持、GEMM 通过 cuDNN Frontend。 因此这次真正更值得关注的变化，是底层 cuDNN fused training pipeline 已经继续向“端到端可直接消费”的方向推进，而不是 TE API 又增加了一个开关。

### 对可能技术路线的含义

这让我对 Rubin/TE3 的低比特训练路线判断进一步收敛：**NVIDIA 显然不希望每一个算子之间都 materialize BF16/FP32 tensor，再由独立 quant / transpose / swizzle kernel 重新准备下一个 GEMM operand；更可能的设计原则是，上一个 kernel 的 epilogue 直接生成下一个 Tensor Core kernel 所需要的最终低比特物理布局。**

也就是：

```text
compute
  ↓
activation
  ↓
RHT
  ↓
quantize
  ↓
layout / transpose / expert packing
  ↓
直接成为下一次 MMA operand
```

全部尽量融合在 producer kernel 内。

这与我们之前看到的 UE5M3、RHT、block16 scaling、SM107 block-scaled MMA 是一致的，而且现在又多了一层 **producer-consumer layout contract** 的代码证据。

对于 distributed MoE training，这一点尤其重要。真正节省的不是几个 scale byte，而是避免：

`BF16 activation write HBM → read → RHT → write → read → quantize → write → read → transpose/repack → write → wgrad read`

逐渐收缩成：

`GEMM epilogue → RHT + NVFP4 + final wgrad layout → HBM → wgrad GEMM`

所以我现在会把 **“Rubin TE3 的主要收益来自低精度格式本身”**进一步修正为：

> **低精度格式 + fused transformation + consumer-native layout generation 三者共同构成 Rubin training datapath。**

### 与此前判断相比是否需要修正

对 **attention adaptive compression** 的核心判断**不需要修正**。

截至本轮，CUDA 13.4 Developer Preview 仍明确是 **PTX ISA 9.4**。公开 ISA 仍是我们已经分析过的：

`sm_107/a/f`、`tcgen05.ld{.red}.spcompress`、`spcompress/spdecompress`、UE5M3 scale for `tcgen05.mma{.sp}`；没有出现更新的 PTX revision 或新的 adaptive-compression descriptor 语义。([NVIDIA Docs][1])

我也没有在这几天新合入的公开 cuDNN Frontend / TransformerEngine 路径里发现实际 SDPA kernel 开始调用 `tcgen05.ld.red.spcompress`。因此：

```text
Attention Adaptive Compression
──────────────────────────────
dense QK score in TMEM
        ↓
tcgen05.ld.red.spcompress
        ↓
2:4 cdata + metadata + reduction
        ↓
sparse Softmax
        ↓
tcgen05.mma.sp(P,V)
```

仍然属于：

**ISA 已明确确认，NVIDIA OSS production SDPA 尚未公开落地。**

这轮真正需要更新的是另一条线：

```text
Rubin NVFP4 Training
──────────────────────────────
Grouped GEMM
 → GLU
 → RHT
 → NVFP4 / UE5M3
 → per-expert ragged transpose layout
 → 直接进入 wgrad Grouped GEMM
```

已经从“融合量化 kernel”进一步发展成了**producer 直接生成 consumer-native 低比特 operand**。

因此，本轮最值得记录的新结论是：

**Rubin/TE3 的 NVFP4 路线正在从“低比特 GEMM + 独立量化”演变成跨算子的低比特流水线：前一个 fused kernel 直接产生下一次 Tensor Core GEMM 所需的 NVFP4 + block-scale + expert/layout 形式。这个变化不改变我们对 2:4 adaptive compression 的判断，但明显强化了“数据尽量不回到高精度、不做中间重排”的 Rubin 设计方向。**
