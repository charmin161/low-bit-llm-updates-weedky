# 低比特硬件与编译器周报｜2026-10-23 至 2026-10-30

[本期总览](../weekly/20261030.md) · [训练与后训练](../train/20261030.md) · [推理框架](../inference/20261030.md)

本期围绕 NVIDIA、AMD、Intel、Apple 的硬件执行与软件适配展开，昇腾更新见[推理栏目](../inference/20261030.md#sglang-ascend-fp8)。重点是不同架构怎样消费低比特数据，而不是按某张可用显卡安排实验。性能数字均为来源作者的特定配置结果。

## NVIDIA

<a id="nvidia-spark-moe"></a>
### DGX Spark 官方博客：MXFP4、FP8 输出层与投机解码怎样配合

**技术博客 · 10-27。** NVIDIA 用 Ling-3.0-flash 展示三项组合：替换 MXFP4 MoE 内核、把输出层权重转为 FP8、加入多 token 预测。共同目标是减少读取权重的成本和生成所需轮次。GSM8K 的单请求评估中，输出吞吐提高 42.5%，准确率基本持平；合成负载的增幅明显更大。值得关注的是框架接口一致性：草稿模型若没有共享完整的量化输出层，组合反而会失效。

原文：[3 Ways to Boost MoE Inference on NVIDIA DGX Spark](https://developer.nvidia.com/blog/3-ways-to-boost-moe-inference-on-nvidia-dgx-spark/)

<a id="flashinfer-rubin-moe"></a>
### Rubin：FlashInfer 扩大 FP4 MoE 的可选执行方案

**已合入 · 10-27。** FlashInfer 修正 Rubin/SM107 的调优候选过滤，让成对线程块协作的大 tile 方案和更多 cluster 配置进入自动选择。作者报告特定大批量 MoE 算子耗时下降约 12%–17%，小批量基本不变。它说明新硬件能力需要编译器与框架把正确方案暴露出来；这次是软件适配进展，不是新硬件规格发布，也不是全模型加速比例。

原文：[Rubin FP4 MoE tactics，PR #7027](https://github.com/flashinfer-ai/flashinfer/pull/7027)

## AMD

<a id="amd-warp-pipelining"></a>
### 官方博客：让数据准备与矩阵计算错开执行

**技术博客 · 10-27。** AMD 介绍 Triton warp-pipelining：让两组执行单元保持一个阶段的错位，一组计算时另一组准备数据，减少矩阵单元等待。文章讨论 MI300X、MI350、MI450 的不同调度条件。MI355X 的 FP16 示例接近手工调优性能，不能转述成低比特加速数据；但流水组织、寄存器与共享内存的取舍，对研究低比特内核同样有参考价值。

原文：[Warp-Pipelining Triton GEMMs on AMD Instinct](https://rocm.blogs.amd.com/software-tools-optimization/triton-warp-pipeline/README.html)

<a id="triton-gfx1250"></a>
### Triton：gfx1250-strict 开放更多带缩放的矩阵指令

**已合入 · 10-28。** LLVM 能力补齐后，Triton 移除旧限制，让更多 FP4/FP8 相关 WMMA 路径可用于 gfx1250-strict；同时启用 32 元素分组的硬件缩放转换。16 元素分组仍可能走软件路径。值得关注的是分组大小会直接影响是否命中硬件指令；这些编译器变化还不能证明所有上层框架已经适配，或已有统一的端到端收益。

原文：[WMMA 指令开放](https://github.com/triton-lang/triton/commit/96ffafdd35cbd70f0a12a81ba2b3d1acb43888a2) · [block32 硬件转换](https://github.com/triton-lang/triton/commit/8afd743d38de3937f8a2874b48dfcd781312342f)

<a id="aiter-mxfp8-attention"></a>
### AITER：新增 gfx1250 的 MXFP8 注意力内核

**已合入 · 10-28。** AITER 新增 MXFP8 多头注意力内核，通过进一步拆分计算 tile 与提前准备数据改善执行效率，并支持因果注意力、分组查询注意力和不等长序列。关注点在于 MX 格式正从线性层扩展到注意力算子。当前证据主要是该内核实现与算子测试，不能直接外推为整个 LLM 服务的加速结果。

原文：[MXFP8 MHA subtiled kernel，PR #7045](https://github.com/ROCm/aiter/pull/7045)

<a id="aiter-mxfp4-tuner"></a>
### AITER：MXFP4 MoE 调优改为分阶段搜索

**已合入 · 10-28。** 原先要逐一测量前后两个 GEMM 的大量组合；新策略先分别筛选候选，再验证少量完整 MoE 组合，同时保留回退路径。它降低的是“找到合适内核配置”的成本，有利于适配更多专家形状和模型。最终仍由完整 MoE 测量决定胜出方案，不能把搜索更快写成推理本身同幅度加速。

原文：[MXFP4 MoE staged search，PR #6461](https://github.com/ROCm/aiter/pull/6461)

AMD 的训练生态另有两篇本周官方博客：[Quark 草稿训练](../train/20261030.md#quark-eagle3)、[MI308X 强化学习栈](../train/20261030.md#amd-mi308x-rl)。消费级 RDNA 的兼容路径见 [SGLang MXFP4 W4A16](../inference/20261030.md#sglang-rdna-w4a16)。

## Intel

<a id="llamacpp-kv-dpas"></a>
### llama.cpp：量化 KV 直接进入 XMX 的整数点积路径

**已合入 · 10-29。** SYCL 后端为 Xe2 增加 Q4/Q8 KV cache 注意力路径：QK 点积直接消费压缩缓存，减少先把整份缓存还原成 FP16 的开销。Arc B580、Llama 3.1 8B、16K 上下文示例中，生成从 31.3 升到 54.2 token/s。该结果只有单次端到端测量，不能泛化成普遍增幅；新路径面向解码和小批量，提示处理不变，其他型号与 Windows 尚未得到同等验证。

原文：[SYCL quantized KV DPAS，PR #31125](https://github.com/ggml-org/llama.cpp/pull/31125)

## Apple

<a id="llamacpp-metal-mxfp4"></a>
### Metal：优化 MXFP4 解码与小算子的并行执行

**已合入 · 10-29。** llama.cpp 用更轻的位操作展开 FP4，并改善权重读取；同时调整逐元素和 GLU 算子的线程分配。在 M3 Ultra 的 Qwen3-4B MXFP4 示例中，生成吞吐由 131.7 升至 154.4 token/s，提示处理基本不变。增幅来自多项改动共同作用，不能全部归给 FP4 解码；这也不意味着 Apple GPU 新增了原生 FP4 矩阵硬件。

原文：[Metal MXFP4 与线程组优化，PR #31075](https://github.com/ggml-org/llama.cpp/pull/31075)

## 跨平台观察

| 本周平台进展 | 主要收益来源 | 判断时要保留的区别 |
|---|---|---|
| [NVIDIA Spark](https://developer.nvidia.com/blog/3-ways-to-boost-moe-inference-on-nvidia-dgx-spark/) | 减少权重流量，并与投机解码组合 | 真实任务与合成负载的增幅不同 |
| [AMD gfx1250 / Triton](https://github.com/triton-lang/triton/commit/8afd743d38de3937f8a2874b48dfcd781312342f) | 让格式和分组布局匹配硬件指令 | block32 与 block16 可能走不同路径 |
| [AMD RDNA / SGLang](https://github.com/sgl-project/sglang/pull/41389) | 展开压缩权重，扩大模型兼容性 | W4A16 不等于原生 W4A4，单请求不一定更快 |
| [Intel Xe2 / SYCL](https://github.com/ggml-org/llama.cpp/pull/31125) | 量化缓存直接参与整数点积 | 当前主要改善解码，不覆盖所有显卡和系统 |
| [Apple Metal](https://github.com/ggml-org/llama.cpp/pull/31075) | 低成本解码与更合理的线程组织 | 软件优化不能写成硬件新增格式 |
| [昇腾 / SGLang](https://github.com/sgl-project/sglang/pull/46212) | block FP8 模型与 NPU 算子衔接 | 原始 block FP8 与重新量化 MXFP8 应分别评价 |

这些案例共同支持一个判断：比较低比特平台时，除了格式名称和峰值算力，还应关注缩放布局、数据搬运、可用内核和框架调度是否已经接通。
