## GFX1250-strict：WMMA 与 scaled upcast 打开不同边界｜TRITON-GFX1250-MX｜主分支提交｜10-28 UTC｜Triton / 匹配 LLVM

**结论：** Triton 在 LLVM 更新后移除过时的 strict WMMA 限制，同时为 block32 scaled upcast 启用硬件路径；block16 所需布局仍走软件实现。

**技术机制与证据：** 第一项修改移除 `AccelerateAMDMatmul` 与 WMMA 分组中的旧 gate；回归不再期待 strict 目标的 scaled WMMA lowering 失败。其中 FP4 E2M1 packed operand、E8M0 scale 与 FP32 accumulator 能映射到 `llvm.amdgcn.wmma.scale.f32.16x16x128.f8f6f4`。这是编译器可表达的逻辑 tile 与类型契约，不是测出了硬件每周期物理 issue 大小。[WMMA diff 与 MLIR 测试](https://github.com/triton-lang/triton/commit/96ffafdd35cbd70f0a12a81ba2b3d1acb43888a2)。

第二项修改按布局决定 scaled upcast 是否可使用硬件指令。scale 与元素的 lane/register 分布决定需求是 block32 还是 block16；strict 仅支持前者，因此“具有 scaled-upcast 硬件能力”不是整个算子无条件走硬件的充分条件。修改同时涉及目标特征、合法性检查和 LLVM lowering，测试分别约束合法指令与软件退路。[scaled upcast diff](https://github.com/triton-lang/triton/commit/8afd743d38de3937f8a2874b48dfcd781312342f)。

**边界与影响：** 两项共同说明 operand 格式、scale 粒度和编译布局必须匹配，单看 `dot_scaled` 或张量 dtype 看不出最后路径。scaled upcast 本身是转换能力，不能与原生低比特矩阵乘吞吐混为一谈；FP32 accumulator 类型也不独自证明所有数值边界与 BF16 reference 相同。当前证据是主分支实现和编译测试，尚缺统一 kernel 性能、框架默认启用及真实模型收益；使用固定 LLVM/Triton 的框架必须跟踪依赖升级。这里不将 gfx target 擅自等同于某个零售型号，也不据代码文件名推导整代产品规格。跨平台可推广的是能力声明需细化到 scale/layout；AMD WMMA 细节不能套用 NVIDIA TMEM/TMA 术语。

这里还有一个容易遗漏的成本：软件 fallback 即使数值正确，也可能新增转换指令、寄存器占用或中间数据搬运。因此编译通过只解决了可用性的一部分，不能把移除 gate 自动翻译为某个百分比的收益。对于默认走另一库后端的框架，Triton 主分支新增能力甚至可能尚未进入实际模型路径；适配链最后两环仍需独立证据。

## Rubin Adaptive Compression 观察项

本轮检查 CUTLASS 窗口内提交、Triton 及 NVIDIA 官方架构检索，并发现若干框架 SM107 适配候选；未获得足以更新 Adaptive Compression 物理机制判断的窗口内证据。保留原专题，不把产品命名与某段稀疏压缩代码强行对应。此前已公开的[Rubin 架构说明](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)属于背景来源，不列为本周新事件。待验证项仍是 dense/sparse MMA 与压缩器的关系、mask/scale descriptor、物理/逻辑 K、执行工作减少及端到端收益；zero-gating 的节电或逻辑 tile 本身不足以回答这些问题。
