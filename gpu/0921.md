有实质性新进展，主要来自 **CUDA 13.4 Update 1 / CUDA 13.4.2 对 Rubin NVFP4 cuBLAS 路径的修复与进一步落地**。这次更新没有新增 Adaptive Compression 的公开 API，但首次把此前 Rubin 上的具体 NVFP4 algorithm/stage 异常修掉，因此值得单独记录。

### 发生了什么变化

NVIDIA 在 2026 年 9 月中旬发布了 CUDA 13.4 Update 1；CUDA Archive 当前将 **CUDA 13.4.2**列为最新 13.4 版本，而 Nsight Compute 2026.3 Update 1 在 **9 月 16 日**明确加入对 CUDA 13.4 Update 1 的支持。该 Toolkit 中 cuBLAS 已更新到 **13.8.0.4**。([NVIDIA Developer][1])

最值得关注的是两个 **Rubin/B300 专属 NVFP4 修复**。第一，`cuBLASLt Grouped GEMM` 在 NVFP4 输入、waves > 3、`CUBLASLT_MATMUL_STAGES_768xAUTO` 时可能产生错误结果；第二，普通 `cublasLtMatmul()` 在 NVFP4 输入下，如果使用 **algorithm ID 66 + `STAGES_768xAUTO`** 也可能产生错误结果。这两个问题现在都已经修复。([NVIDIA Docs][2])

与此同时，本轮没有看到新的 PTX ISA 版本：仍然是 **PTX 9.4**。`spcompress/spdecompress`、`tcgen05.ld{.red}.spcompress`、2:4 sparsity、Zero-Column Mask Descriptor、Rubin 的 `v1` sparsity version 以及 B collector 约束都没有出现新的公开语义。Transformer Engine 也仍停留在此前的 **v2.19 Rubin SM107a support**，没有新增公开的 `AdaptiveCompression` recipe/API。([NVIDIA Docs][3])

### 证据可靠性与来源等级

这是 **一级官方证据**：CUDA/cuBLAS Release Notes、CUDA Archive、PTX ISA 和 NVIDIA Transformer Engine 官方仓库。

**已确认事实**是 Rubin 已经存在实际投入 cuBLAS 分发的 NVFP4 kernel，且这些 kernel 内部存在明确的 algorithm ID、pipeline stage 和 wave 调度差异；这不再只是 PTX 能力预留。尤其是 `algorithm 66 + 768xAUTO` 能在 Rubin 上触发特定 correctness bug，说明这一 kernel family 已经走到了真实执行和调优阶段。([NVIDIA Docs][2])

**强证据推断**是 Rubin 的低比特实现明显依赖较复杂的内部 staging / pipeline / TMEM-SMEM 数据流，而非简单的一条 `mma`。这与此前 CUTLASS 暴露的 Rubin 更大 TMEM、328 KB SMEM、B collector reuse、FP4 block-scaled GEMM 方向一致。([GitHub][4])

**仍未证实的假设**：不能把 `algorithm 66`、`STAGES_768xAUTO` 或这次 cuBLAS 修复直接等同于 Adaptive Compression，也没有证据证明其中使用了 `spcompress`。

### 对可能技术路线的含义

这次更新更加强化了一点：**Rubin Adaptive Compression 很可能最终不是一个孤立的新算子，而是嵌入 GEMM/Transformer kernel mainloop 中的数据路径机制。**

目前公开 PTX 已经给出非常清晰的动态 2:4 路径：

`TMEM/dense data → tcgen05.ld{.red}.spcompress → compressed data + metadata → tcgen05.mma.sp`

其中 `.spcompress` 明确只能做 `.sp::2:4`，并且可以直接在从 Tensor Memory load 时 inline 完成 compression；选择标准由 row reduction/operator 决定。([NVIDIA Docs][5])

而这次 cuBLAS 暴露出的 **768-stage / waves / algorithm-specific behavior** 更像是在告诉我们，实际库实现已经围绕 Rubin Tensor Core pipeline 做深度软件调度。这支持“Adaptive Compression 最终由 TE/cuBLAS/CUTLASS kernel 自动选择并融合，而不一定暴露给用户一个独立压缩 kernel”的路线。

但需要特别注意：**Zero-Column Mask 仍然不像 2:4 sparse metadata。** 它依然描述的是 B 矩阵整列置零，而且由 `Start Count / First Span / Skip Span / Use Span / Column Shift` 构造周期性 column mask；M=128/64/32 时又分别拆成 1/2/4 个 sub-mask。这依然更像 block/column-level gating，而不是 arbitrary 2:4 metadata。([NVIDIA Docs][5])

另外一个此前判断仍值得保留：Rubin 对 sparsity metadata 确实出现了 **代际变化**。PTX 9.4 明确规定 `.kind::mxf4/.kind::mxf4nvf4` 的 instruction descriptor 中，旧架构使用 sparsity version `v0`，而 **SM107a 必须使用 `v1`**，否则行为未定义。([NVIDIA Docs][5]) 这不是本轮新增，但结合已经进入 cuBLAS 真实 kernel 的事实，它越来越像一个应该重点逆向的接口。

### 与此前判断相比是否需要修正

**核心判断不需要修改，但需要提高“软件栈已经进入实装阶段”的置信度。**

此前我的判断是：

`spcompress + sparse MMA` 很可能承担 activation/dynamic 2:4；

`B collector + LUT/decompression` 更可能承担 B/weight representation compression；

`Zero-Column Mask` 是另一套更粗粒度的 column/block skip 机制。

这三个判断目前都没有被新证据推翻。

真正需要更新的是时间线：**Rubin 已经不再只是“PTX 定义好了未来能力”，而是 cuBLAS 中已经存在可执行、可调度、正在修 correctness bug 的 Rubin NVFP4 kernel family。** 这意味着下一步最有价值的信号将不再是再等一条宣传稿，而是监控 **CUTLASS 后续版本是否公开 SM107 sparse GEMM / `spcompress` primitive、TE 是否开始调用这些路径，以及 cuBLAS 是否出现 Rubin-specific sparse/Adaptive Compression algorithm attributes**。

本轮我会把整体状态从此前的“ISA 强证据阶段”提升为：

**Adaptive Compression 本体：仍未公开。
硬件 primitive：已确认。
Rubin low-bit software kernel path：已进入实际部署和稳定化。
`spcompress → mma.sp` 是否就是 TE3 Adaptive Compression 主路径：仍属于强证据推断，而非确认事实。**
