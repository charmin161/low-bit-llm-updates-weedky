有，**本轮有一项我认为达到“实质性进展”阈值的官方代码落地，以及两项值得同步的辅助信号**。但先给结论：**PTX 层没有比 9.4 更新的 adaptive-compression 指令披露；真正的新变化来自 cuDNN Frontend，Rubin 的 NVFP4/UE5M3 + MoE activation-fusion 路线进一步从“原型”走向了实际 kernel。与此同时，公开的 Rubin SDPA 仍然没有接入 `spcompress`，这反而帮助我们更明确地区分“已经公开的硬件能力”和“当前开源 attention kernel”。**

### 1. 发生了什么变化

**最重要的新进展：8 月 19 日 NVIDIA 已合并 cuDNN Frontend PR #637，加入 Rubin SM107 专用的 `Grouped GEMM + SwiGLU + RHT + NVFP4 quantization` 融合 kernel。** 它不是单独的量化实验，而是一条完整 MoE activation pipeline：

```text
block-scaled Grouped GEMM
        ↓
      SwiGLU
        ↓
 optional RHT
        ↓
 NVFP4 quantization
        ↓
row/column quantized activation
+ swizzled scale factors
```

整个过程在一个 kernel 内完成，目的就是避免 BF16 activation 落地以及单独 RHT、quantize kernel 带来的额外显存往返。PR 于 **2026-08-17 22:46 UTC** 创建，**8 月 19 日 04:29 UTC 合并**，新增约 9.5K 行代码。

这条 kernel 的约束对我们尤其有用：`sf_vec_size` **固定为 16**；而 `sf_fp8_dtype_override="e5m3"` 只允许在 **Rubin SM107** 上使用，可以把 FP8 scale storage 解释为 **UE5M3**。也就是说，“16-value scale block”目前又获得了一份 Rubin 实际 kernel 级证据。

这里有一个需要特别准确区分的细节：这份公开文档明确显示 **A/B 的 block scale 可以通过 override 使用 UE5M3**；而当前 NVFP4 输出 `D/RHT` 的 `SFD/SFRHT` 文档仍写作 E4M3。因此不能简单表述成“Rubin 所有 NVFP4 scale 都已经换成 E5M3”。

第二项新信号来自 **8 月 18 日新开的 cuDNN Frontend PR #651**。它给 Rubin SM107 的 FP8 SDPA 加了一个 Rubin-only 的 `softmax_precision="fp16"` 路径，使用 packed `EX2.F16x2` 计算 exponent，然后直接转成 packed FP8 probability；而 **softmax row sum 仍然通过 `P × ones` MMA 完成**。

这个 PR 对 adaptive compression 的意义反而在于“它没有做什么”：当前公开的 SM107 SDPA 仍然是 **dense P** 路径。最新的 Rubin FP8 kernel 代码明确使用：

```text
S_acc in TMEM
    ↓
tcgen05.ld.red.f32.max
    ↓
dense Softmax
    ↓
packed FP8 P
    ↓
P × ones MMA → Σ
    ↓
P × V
```

其中 Rubin 已使用 576-column exclusive TMEM、K=64 dense FP8 MMA，以及 TMEM load + max reduction，但仍没有看到 `tcgen05.ld.red.spcompress` 被接入这条公开 kernel。

我同时检查了当前公开的 **cudnn-frontend、TransformerEngine 和 CUTLASS** 源码，尚未检索到 `spcompress` 的实际调用。因此，截至目前，**PTX 9.4 已经公开 adaptive compression primitive，但 NVIDIA 的开源 attention kernel 还没有把这条路径公开出来**。这一点比单纯知道 PTX 指令存在更重要：ISA capability 和 OSS kernel adoption 现在可以明确分层看待。

### 2. 证据可靠性与来源等级

这次 #637 我给 **A+ 级**：NVIDIA 官方 `cudnn-frontend`，而且已经 merge，不是 Draft，也不是设计说明。它直接写明该 kernel 用于 Rubin MoE training recipe，且 Rubin-only 的 UE5M3 override、16-element scale vector 都已经进入公开 API/代码。

#651 我给 **A 级来源、B 级成熟度**：同样是 NVIDIA 官方代码，但截至检查时仍为 open PR，并且 Rubin E2E 测试在 PR 描述中仍标注为等待 Rubin board 验证。

TransformerEngine 的 UE5M3 PR #3325 也出现了一个小的成熟度变化：它现在已经**不是 Draft**，截至 8 月 19 日扩展到 **19 commits / 57 files**；但 PR 描述仍明确写着 **proof-of-concept，quantization available，GEMM not yet available**。因此我不会把它算成另一项独立突破，只能说明 TE 上层接口正在继续收敛。

### 3. 对可能技术路线的含义

这次最明显的变化，是我会把 Rubin 第三代 Transformer Engine 的技术图进一步明确拆成 **三条协同但正交的路径**：

```text
A. 数值表示 / block scaling
   FP4 + block16 scale
   UE4M3 / Rubin UE5M3
              │
              ▼
       block-scaled MMA

B. activation fusion
   GEMM → SwiGLU → RHT → NVFP4 quant
              │
              ▼
   避免 BF16 materialization / HBM traffic

C. attention adaptive compression
   dense QK score in TMEM
              │
              ▼
   tcgen05.ld.red.spcompress
              │
       cdata + mdata + redval
              │
              ▼
        sparse P×V MMA
```

A+B 现在已经有实际 cuDNN Rubin kernel 证据；C 则目前仍然是 **PTX ISA 已确认、公开 production/open-source kernel 尚未出现**。PTX 9.4 仍明确新增 `sm_107[a/f]`、`.spcompress` for `tcgen05.ld/ld.red`、`spcompress/spdecompress`，以及 UE5M3 作为 `tcgen05.mma` / `tcgen05.mma.sp` scale type。([NVIDIA Docs][1])

这让我对一个此前判断的置信度进一步提高：**Rubin adaptive compression 并不是“FP4 block scale 做得更聪明”本身。** `block16 + UE5M3 + RHT + NVFP4` 是 precision/quantization path；`2:4 + mdata + sparse MMA` 是 activation sparsity path。它们可以在 TE3 中组合，但硬件语义是分开的。

还有一点很值得注意：#637 的 RHT 是在 activation 量化前做 **16-wide orthonormal Hadamard transform**，明确目的之一是 spread outliers，然后再量化为 NVFP4。 这进一步说明 Rubin 对 16-value scale block 的处理思路是：

```text
先改善 block 内数值分布
       ↓
再做 block16 quantization
```

而不是把“16-value block”直接和 attention 的“每 4 个取 2 个”绑定起来。**scale block=16 与 sparsity group=4 应继续看作不同的硬件粒度。**

### 4. 与此前判断相比，哪些需要修正

**核心 adaptive-compression 判断不需要推翻，但需要补上一个很重要的层级区别。**

此前 PTX 9.4 已经让我们把：

> “compression 很可能发生在 TMEM load 边界”

提升到 ISA 基本确认。

本轮之后，我会把结论进一步写成：

> **Rubin 硬件/ISA 已明确提供 TMEM → 2:4 compressed data + metadata 的能力，但 NVIDIA 当前公开的 cuDNN SM107 SDPA kernel 仍使用 dense TMEM Softmax/P 路径；adaptive-compression kernel 很可能尚未进入公开 FROST 代码，或者仍存在于内部/其他尚未公开实现中。**

这比之前默认“PTX capability ≈ cuDNN 已经实际用上”更加严谨。

另外，**cuBLAS 暂时没有跟上这个 Rubin-only UE5M3 暴露速度**。CUDA 13.4 Developer Preview 确实已经带 **cuBLAS 13.7.0.10**，但当前公开 cuBLASLt 文档的 FP4 block scaling 仍写作：

```text
CUBLASLT_MATMUL_MATRIX_SCALE_VEC16_UE4M3
```

而且文档中没有 UE5M3 scale mode；相反，PTX 9.4 已经允许 UE5M3 作为 Tensor Core scale type。([NVIDIA Docs][2])

因此我目前更倾向于：

> **Rubin 专属新数值格式和融合能力会先在 PTX + CuTeDSL/cuDNN FROST 暴露，cuBLASLt 的公共抽象层可能稍后再跟进。**

这是**强证据推断**，不是 NVIDIA 已宣布的 API 路线。

最后，本轮**没有发现比 PTX ISA 9.4 更新的 PTX revision，也没有新的 2:4 metadata layout / `spcompress` descriptor 约束**。当前 Developer Preview 仍明确标识为 **PTX ISA 9.4**。([NVIDIA Docs][1])

所以这轮可以浓缩成一句：

**Rubin 的 “block16 + UE5M3 + RHT + NVFP4” 已经开始进入真正的融合 MoE kernel；但 attention 2:4 adaptive compression 仍停留在“PTX 9.4 硬件接口已公开、OSS SDPA 尚未接入”的阶段。这个分离现在比上次更加明确。**
