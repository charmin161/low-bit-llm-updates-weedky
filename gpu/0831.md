有一项**需要通知的实质性进展**，而且我先纠正上一轮检查：这项核心证据其实已经随 **CUTLASS 4.8.0** 在 **2026 年 8 月 25 日**发布，并于 **8 月 26 日 09:34 UTC** 合入 NVIDIA/cutlass 主线；上一轮 8 月 26 日晚的检查漏掉了它。它不是这几天才出现，但它**实质性改变了上一轮“只有 PTX ISA、尚无公开 DSL 支持”的结论**。([NVIDIA Docs][1])

### 发生了什么变化

最关键的变化不是又多了一条 PTX，而是 **NVIDIA 已经把 Rubin adaptive compression 从 PTX 指令提升成了公开 CuTe DSL 的一等硬件 primitive**。

CUTLASS 4.8 当前源码的 `cutlass/cute/nvgpu/tcgen05/copy.py` 新增了两个明确的操作：

```text
LdSPCompress32x32bOp
LdRedSPCompress32x32bOp
```

前者对应：

```text
tcgen05.ld.spcompress
```

后者对应：

```text
tcgen05.ld.red.spcompress
```

NVIDIA 源码注释直接称它们为：

* `TMEM load Sparse Compression Operation`
* `TMEM load Reduce and Sparse Compression Operation`

并且底层不是复用普通 SM100 TMEM copy atom，而是专门构造：

```text
CopyAtomSM107TmemLoadSPCompressType
```

也就是 **SM107/Rubin 专属的 CuTe/MLIR atom**。

我进一步对比了 CUTLASS 4.8 合入前的父提交 `7107b055...`：同一个 `copy.py` 中**没有** `LdSPCompress32x32bOp`。该文件的 Git 历史也显示，下一个修改它的正是 **2026-08-26 的 CUTLASS 4.8 dev update #3551**。因此可以确认，这不是此前已经存在很久、只是我们没注意到的普通 wrapper，而是 **4.8 新公开的 Rubin 软件抽象层**。

这与 PTX 9.4 完全对上。当前 CUDA 13.4 Developer Preview 仍然明确是 **PTX ISA 9.4**，release notes 同时列出 `sm_107/a/f`、`tcgen05.ld{.red}.spcompress`、`spcompress/spdecompress` 和 UE5M3 scale for `tcgen05.mma{.sp}`。([NVIDIA Docs][2])

### 证据可靠性与来源等级

这一项我给 **A+ 级：官方源码级确认**。

现在证据链已经变成：

```text
NVIDIA Rubin 架构描述
        ↓
PTX ISA 9.4
tcgen05.ld.red.spcompress
        ↓
CUTLASS 4.8 CuTe DSL
LdRedSPCompress32x32bOp
        ↓
SM107-specific MLIR atom
CopyAtomSM107TmemLoadSPCompressType
```

所以已经不是“从 PTX 猜硬件怎样实现”，而是 **NVIDIA 官方编译器/DSL 栈明确把它建模成 TMEM load/copy primitive**。

不过要保持一个重要边界：我检查当前公开 CUTLASS 源码时，`LdRedSPCompress32x32bOp` 的代码搜索仍只找到它的**定义**，没有找到公开 attention example 实际调用它；cuDNN Frontend 当前公开的 Rubin FP8 SDPA 路径也仍未检索到 `spcompress` 调用。因此：

> **ISA + DSL/compiler primitive 已公开；production/open-source SDPA consumer 仍未公开。**

这一层级现在可以非常明确地区分。

### 对可能技术路线的含义

这次证据让我对我们之前画的数据流置信度进一步提高：

```text
Q × Kᵀ
   ↓
FP32 Score in TMEM
   ↓
┌────────────────────────────────┐
│ LdRedSPCompress32x32bOp        │
│                                │
│ → tcgen05.ld.red.spcompress    │
│ → SM107 TMEM-load atom         │
└───────────┬────────────────────┘
            │
      ┌─────┼──────┐
      ↓     ↓      ↓
    cdata  mdata  redval
    2:4值   索引    row max
      │      │
      └──┬───┘
         ↓
 compressed softmax
         ↓
 tcgen05.mma.sp(P,V)
```

其中有两个新的细节尤其有价值。

第一，CuTe DSL 把它归类在 **`tcgen05.copy` / TMEM load** 体系，而不是 MMA 体系。这进一步强化：

> **adaptive compression 发生在 TMEM → register/operand 的数据搬运边界，而不是 Tensor Core 在 MMA 内部临时决定“这次只执行一半 K”。**

所以此前讨论的“动态 K issue / 动态缩窄 Tensor Core K”路线，我会继续下调概率；目前证据明显更支持：

```text
fixed MMA datapath
+
operand-side compression
+
metadata-driven sparse MMA
```

第二，两个新 class 的 API 中都带有：

```text
TmemLoadRedOp
```

其枚举包括：

```text
MAX
MAXABS
MIN
MINABS
```

而 `LdSPCompress32x32bOp` / `LdRedSPCompress32x32bOp` 的默认值都是：

```text
MAX
```

这与 attention 的物理语义高度吻合：

```text
每4个 attention logits
        ↓
保留数值最大的2个
```

而不是：

```text
保留绝对值最大的2个
```

因为 softmax 关心最大的正向 logit，而一个绝对值很大的负数应该被淘汰。

但这里必须严格分类：

* **已确认事实**：CuTe DSL primitive 支持 `MAX/MAXABS/MIN/MINABS`，默认参数是 `MAX`。
* **强证据推断**：Rubin attention adaptive compression 最自然会选 `MAX`。
* **仍未确认**：NVIDIA 最终 production SDPA kernel 是否实际实例化 `redOp=MAX`。目前还没有公开调用点证明这一点。

### 与此前判断相比，需要怎样修正

需要修正一条重要表述。

此前我们说：

> PTX 9.4 已经公开 adaptive-compression ISA，但 NVIDIA OSS 中还没有对应的软件 primitive。

现在应改成：

> **PTX 9.4 + CUTLASS 4.8 CuTe DSL 已经从 ISA 到编译器 primitive 全部公开；目前唯一缺失的是公开的真正 attention kernel consumer。**

也就是说，公开程度已经从：

```text
Architecture
   ↓
PTX
   ↓
?????
   ↓
SDPA
```

推进到了：

```text
Architecture
   ↓
PTX 9.4
   ↓
CuTe DSL
LdRedSPCompress32x32bOp
   ↓
SM107 MLIR atom
   ↓
[尚未公开的 SDPA 接入]
```

这对硬件位置判断非常关键。

另外，CUTLASS 4.8 还正式把 Rubin 的 **NVFP4 + UE5M3** 推进到了 Operator API：官方 changelog 明确列出 Rubin block-scaled GEMM 支持 `{MXFP4,NVFP4} × {MXFP4,NVFP4}`，并特别注明 **NVFP4 的新 UE5M3 scale-factor dtype**。所以 UE5M3 已经不能再视为仅仅 TransformerEngine #3325 的实验性 recipe；底层 CUTLASS public operator stack 已经正式出现对应支持。([NVIDIA Docs][1])

不过 **TE #3325 截至 2026 年 8 月 30 日仍然是 open、非 Draft，尚未 merge**；只是现在描述已经明确为 native UE5M3 quantization + cuDNN Frontend GEMM，而且功能/文档/测试 checklist 全部完成。 因此“UE5M3 最终成为 TE3 默认 NVFP4 scale、以及默认是否关闭 second-level FP32 scale”仍不能直接下结论。

本轮**没有发现比 PTX 9.4 更新的 PTX revision，也没有发现新的 cuBLAS adaptive-compression API 或新的 sparsity metadata descriptor 规则**。zero-column-mask 与 2:4 sparsity metadata 是两套机制的判断也不需要修改。

所以这轮最重要的结论可以压缩为一句：

> **Rubin adaptive compression 已经从“架构说明 + PTX 指令”进一步落到了 NVIDIA CUTLASS 4.8 的 SM107 专用 CuTe DSL/MLIR primitive：`LdRedSPCompress32x32bOp → CopyAtomSM107TmemLoadSPCompressType`。现在缺的已经不是软件抽象，而只是 NVIDIA 公开真正使用它的 SDPA kernel。**

这会让我把“**compression unit 位于 TMEM load/operand-preparation datapath**”从此前的高可信判断，再提高到接近确定；但“softmax 如何直接消费 compressed representation、metadata 如何跨越 softmax 并直接喂给第二次 sparse MMA”仍然是接下来最关键的未公开部分。
