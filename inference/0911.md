# 低比特大模型推理周报｜2026-09-04—2026-09-10

这一周低比特推理有几个非常明确的变化。最重要的不是又多了一个 FP4 kernel，而是**低比特开始被直接写进模型架构本身**：DeepSeek-V4.1-Flash 把 CSA2、跨层 KV/Indexer 复用、CED、FP4 KV 与 FP4 expert 一起设计；同时框架侧则越来越证明，所谓“NVFP4/MXFP4”并不是一个单独 dtype，而是 **value format + scale format + scale granularity + global scale 语义 + activation format + physical layout + consumer kernel** 的完整契约。vLLM 和 TensorRT-LLM 本周的多个 correctness 修复都正好说明了这一点。([深度求索][1])

另一个很强的趋势是**checkpoint 格式与硬件执行格式正在解耦**：AMD 已经正式展示 NVFP4 checkpoint 在模型加载阶段逐层转成 MXFP4，然后完全使用 MI350X/MI355X 原生 MXFP4 路径服务；而 vLLM 的 NVFP4 KV 工作则说明，即使存储格式已经更低 bit，如果中间仍发生 `FP8 → BF16 → FP4` 之类的 round-trip，性能仍可能比 FP8 差，真正消掉 conversion 后才反转。([ROCm Blog][2])

# A. 本周最重要的 9 项低比特进展

## 1. DeepSeek-V4.1-Flash：FP4 KV 已经从“部署优化”上升成模型架构的一部分

**状态：[正式发布]｜2026 年 9 月 10 日**

DeepSeek 发布了 **V4.1-Flash，552B MoE**。新 Causal Encoder–Decoder 架构在输入阶段只激活约 **8B 参数**、输出阶段约 **16B 参数**。官方给出的系统级结果是：相较上一代，KV Cache 只需约 **1/4 HBM** 和 **1/8 SSD 存储**。这里尤其不能简单理解成“FP4 KV 带来 4×/8×”：这是 CED、SWA Bounded Replay、CSA2 的跨层复用以及 FP4 KV 等机制共同产生的系统结果。([深度求索][1])

其中 **CSA2（Compressed Sparse Attention 2）**把 attention layer 静态分成 Full、Reindex、Reuse 三类：不同层可以共享 main KV 和 indexer K，也可以复用 Top-K sparse-attention indices；Hierarchical Sparse Indexer 又把后续 indexer 的候选范围限制在前面层生成的 candidate pool。再叠加 **main KV 的 FP4 E2M1、每 16 channels 一个 E4M3 scale**，官方给出的 global KV footprint 是 **890 bytes/token，约为 DeepSeek-V4-Flash 的 1/4**。([Hugging Face][3])

而且低比特不只在 KV。官方 `config.json` 显示 checkpoint 本身已经是 heterogeneous quantization：全局 quant config 使用 block-scaled FP8、`scale_fmt=ue8m0`，同时 `expert_dtype=fp4`。所以 V4.1-Flash 不是“BF16 模型出来之后再做一个 NVFP4 版本”，而是**权重、KV、attention 架构和推理执行从设计阶段就已经混合低比特化**。([Hugging Face][4])

我认为它和当前 vLLM/SGLang 里的 post-hoc FP4 KV 最大的不同在于：传统路径通常是

`既定 attention architecture → 把 KV datatype 从 BF16/FP8 改成 FP4`

而 V4.1-Flash 更接近

`先减少需要保存/索引的 KV → 再减少每份 KV 的 bit 数 → 再让层间复用 index/KV`

因此未来评价低比特 KV Cache，单独比较“FP8 vs FP4 bytes/token”会越来越不够。

## 2. SGLang v0.5.19：Hopper 也开始把 MXFP4 MoE 从 W4A16 推向 W4A8

**状态：[正式发布]｜v0.5.19，9 月 5 日**

SGLang v0.5.19 正式提供 **SM90/Hopper 上的 MXFP4 W4A8 MoE**：

`MXFP4 weight + FP8 activation`

通过：

`--flashinfer-mxfp4-moe-precision fp8`

显式启用，并要求 FlashInfer 0.6.18。需要注意，底层 PR #34967 是 9 月 1 日合入，但能力在本周 9 月 5 日进入正式 release，因此我把它记在本周“正式发布”，而不是把 PR 日期说成本周。([GitHub][5])

DeepSeek-V4 的 TP4 GSM8K 测试：

| 路径                     |     GSM8K |          总延迟 | Output throughput |
| ---------------------- | --------: | -----------: | ----------------: |
| W4A16：MXFP4 W + BF16 A |     0.985 |     37.301 s |     611.809 tok/s |
| W4A8：MXFP4 W + FP8 A   | **0.985** | **32.952 s** | **683.574 tok/s** |

也就是端到端 **+11.7% output throughput / -11.7% latency**，这组实验中 GSM8K 没变化。更纯粹的 MoE kernel benchmark 中，W4A8 相比 W4A16 在不同 token count 上约 **1.63×–2.08×**，大 token 数接近 2×。([GitHub][6])

这里要特别区分三种东西：

`W4A16 = MXFP4 weight + BF16 activation`

`W4A8 = MXFP4 weight + FP8 activation`

`W4A4 = FP4 weight + FP4 activation`

Hopper 这次新增的是 **W4A8 mixed-input path**，不是 Blackwell 那种 native FP4 W4A4 Tensor Core 路径。它说明即使没有 Blackwell FP4 Tensor Core，**activation 从 BF16 降到 FP8 本身仍然可以明显改善 MXFP4 MoE 的 data movement / compute efficiency**。([GitHub][6])

对 B200 来说，这反而提出了一个有价值的问题：在实际 decode shape 下，**W4A16、W4A8 和 native W4A4 三条路径的 crossover 到底在哪里？** 并不能简单假设 W4A4 在所有 M/N/K 上都一定赢。

## 3. AMD：NVFP4 checkpoint 可以“在线转码”为 MXFP4，再完全走 MI355X 原生 4-bit 硬件

**状态：[AMD 官方工程实践]｜9 月 8 日**

这是本周最值得关注的**跨硬件低比特 portability**工作。

NVFP4 与 MXFP4 的底层值都是 E2M1，但 scale contract 完全不同：

|                            | NVFP4    | MXFP4             |
| -------------------------- | -------- | ----------------- |
| block size                 | 16       | 32                |
| block scale                | FP8 E4M3 | E8M0 power-of-two |
| tensor global scale        | FP32     | 无                 |
| MI350X/MI355X native 4-bit | 否        | **是**             |

所以不能把 NVFP4 packed bytes 直接送入 AMD MXFP4 MFMA。([ROCm Blog][2])

AMD/SGLang 的解决方式是：

`NVFP4 checkpoint`
→ `加载一层`
→ `该层临时 dequant BF16`
→ `requant MXFP4`
→ `直接写入预分配 MXFP4 storage`
→ `释放 BF16 intermediate`
→ `下一层`

因此峰值额外内存只与**单层**大小相关，不需要在内存中产生一份完整 BF16 frontier model。这个转换也只在启动时做一次，serve 时不再发生 NVFP4→MXFP4 conversion。([ROCm Blog][2])

稳态吞吐与原生 AMD MXFP4 checkpoint 基本处在 run-to-run noise 内：

* MiniMax-M2.7：3516.0 vs 3491.2 tok/s；
* Qwen3.5-397B-A17B：2963.2 vs 2974.4；
* DeepSeek-R1：2799.0 vs 2773.2；
* Kimi-K2.6：2148.8 vs 2170.4。

差异均在约 ±1%。代价主要发生在启动阶段，例如 DeepSeek-R1 +34 s、Kimi-K2.6 +55 s、Qwen3.5 +26 s。([ROCm Blog][2])

准确率方面不能说“数学无损”。MXFP4 的 block=32、E8M0 scale 本来就比 NVFP4 更粗，AMD 也明确指出 requantization 原理上不是 lossless。GSM8K 对原始高精度模型的 recovery 约 **98.7%–100.7%**；与 emulated NVFP4 在 AIME25/GPQA 上的差别落在其多 seed 波动范围内。([ROCm Blog][2])

我认为这件事的长期价值非常大：

> **模型发布格式不必再等于最终硬件执行格式。**

未来 Hugging Face 完全可能只提供一份 canonical low-bit checkpoint，NVIDIA、AMD、甚至其他 accelerator 在 load-time 把它转换成本机 native block-scaled representation。

## 4. vLLM：NVFP4 KV 原本 prefill 比 FP8 慢 18%，消掉 BF16 round-trip 后反而快 19%

**状态：[已合入 main]｜PR #55031，9 月 8 日**

这是本周最值得在 B200 上直接复现的一项。

PR 修复了 NVFP4 KV 的类型转换开销，并让 `AttnQuantFusionPass` 可以让 TRTLLM-gen FMHA 的输出**直接写成 FP8/NVFP4 o_proj 输入格式**，从而删除：

`attention FP8 output`
→ `BF16`
→ `再次 quant`
→ `o_proj`

中间这次高精度 round-trip。([GitHub][7])

Qwen3-32B benchmark 中，以 FP8 KV 为基准：

| 场景                          | NVFP4 原路径 | fix 后 | fix + output quant fusion |
| --------------------------- | --------: | ----: | ------------------------: |
| Prefill：4×2048              |      +27% |  +18% |                  **-19%** |
| Decode：64×2048 ctx, 1 token |       -4% |   -8% |                  **-15%** |

表中正负号是 PR 相对 FP8 基线的计时变化。最值得注意的并不是 19% 这个数字本身，而是**同一个 NVFP4 datatype，从“比 FP8 慢”变成“比 FP8 快”，关键变化并不是 GEMM 或量化格式，而是删除了一次 conversion pipeline。** ([GitHub][7])

这说明以后比较 FP4/FP8 KV Cache 最好把时间拆成：

`cache read`

* `dequant`
* `attention`
* `attention output conversion`
* `o_proj input quant`
* `o_proj`

否则很容易把“格式本身慢”与“当前 producer/consumer interface 不匹配”混为一谈。

## 5. FlashInfer：MLA KV 开始采用“CKV 用 NVFP4，RoPE KPE 保留 FP8”的结构化混合精度

**状态：[已合入 main]｜PR #4676，9 月 8 日**

FlashInfer 新增 `nvfp4_quantize_append_paged_mla_kv_cache`，给 MLA paged KV Cache 增加原生 **quantize-on-append** 路径。

512-dim compressed KV：

`BF16/FP16 CKV`
→ `E2M1 packed FP4`
→ 每 16 channels 一个 E4M3 scale`

而 64-dim RoPE KPE **保持 FP8 E4M3**。最终每 token：

* CKV payload：256 bytes；
* CKV scale：32 bytes；
* KPE：64 bytes；
* 合计 **352 bytes/token**。

全 FP8 layout 为 576 bytes/token，所以 footprint 减少 **39%**。([GitHub][8])

为什么不把 KPE 也 FP4？PR 的 DeepSeek-V2-Lite 测量显示 RoPE channels 的 RMS energy 大约比 CKV channels 高 6×。相对 BF16 attention reference：

* 全 FP8：0.074–0.078 relative L2 error；
* **CKV-FP4 + KPE-FP8：0.092–0.102**；
* 全 FP4：**0.174–0.193**。

因此全 FP4 方案被明确否掉。([GitHub][8])

这个结果非常符合近期的趋势：

> 低比特 KV 的正确单位越来越不是“整层”，而是 **KV subspace / consumer**。

但当前状态需要明确：**#4676 只合入了 cache-write / append path。Dense MLA decode 还不能消费这个 352-byte packed layout，遇到该 cache 会显式报错；decode consumer 是后续工作。** 所以现在还不能把它称为完整的端到端 NVFP4 MLA attention。([GitHub][8])

## 6. vLLM + TensorRT-LLM 连续暴露 scale correctness：现在“scale 语义”本身就是低比特 ABI

**状态：[两项均已合入 main]｜vLLM #55643：9 月 8 日；TRT-LLM #18772：9 月 9 日**

vLLM #55643 修了两个非常危险的 NVFP4 fusion bug。

第一个是 **scale buffer physical layout 分配错误**。SiLU+mul FP4 producer 按逻辑元素数给 scale 分配空间，但 kernel 实际写的是 Tensor Core swizzled SF layout。对于 `M=1,N=14336`：

**只分配 896 bytes，却写入 114,688 bytes。**

很多时候 OOB 写仍落在 CUDA caching allocator 的已映射区域，所以表现不是 crash，而是**静默破坏旁边 tensor，输出错误文本**；只有逃出 segment 才出现 illegal memory access。([GitHub][9])

第二个更有代表性：producer 传入了 `input_global_scale`，而 consumer GEMM 的 alpha 语义需要 activation quantizer 使用的是 **inverse global scale**。方向传反后，最终输入误差会多出一个 `input_global_scale²` 因子。原有测试因为 scale 恰好设成 1.0，完全测不出来。([GitHub][9])

TensorRT-LLM #18772 则修的是另一个 scale contract：NVFP4 MoE checkpoint 的 gate `w1` 和 up `w3` 可以各自有不同的 `weight_scale_2`。此前 loader 会取二者 max 合并成一份 scale；现在 TRTLLM-Gen 能保留 **gate / up 独立 global scale**，只有不支持 dual scale 的 backend 才继续 reconcile。([GitHub][10])

这两项合在一起说明，一个更准确的低比特“格式”定义应该是：

**value dtype**
× **scale dtype**
× **scale granularity**
× **global-scale direction/semantics**
× **physical swizzle/layout**
× **consumer backend**

以后看到 checkpoint 文件名里的 `NVFP4` 四个字，实际上远远不够。

## 7. KBBQ：对 FP4 来说，“越彻底把 spectrum 摊平”并不一定越好

**状态：[论文]｜arXiv:2609.08135，9 月 8 日**

KBBQ 是本周我认为**最值得深入读的 FP4 quantization 论文**。

它建立了 floating-point quantization 的二阶 noise law，引入 participation factor \(\kappa\)，然后重新审视 WUSH 一类 spectrum-flattening transform。关键发现是：理论上把 \(\kappa\) 推到极限的“完全 flattening”，在实际 block-scaled FP4 quantizer 上并不一定对应最优 downstream accuracy。([arXiv][11])

KBBQ 加入一个 brake 参数 \(\lambda\)：

* \(\lambda=0\)：不走向 flattening optimum；
* \(\lambda=1\)：完整 WUSH；
* 中间值：只做部分 spectrum correction。

Qwen3-4B、native NVFP4 W4A4 的 ablation：

* BF16：70.67；
* \(\lambda=1\) WUSH：64.51；
* \(\lambda=0.5\)：65.61；
* **\(\lambda=0.75\)：66.44**。

也就是说最佳位置出现在 interior，而不是理论 flattening 终点。([arXiv][11])

更有意义的是，论文在四个模型 × NVFP4/MXFP4 共 8 个 model-format pair 中，RTN-KBBQ **8/8 均优于 identity，7/8 优于 WUSH**，收益从 0.5 到 7.1 个平均分点。NVFP4 是直接在 **GB200 + Transformer Engine block scaling 上 native 执行**，MXFP4 才是 fake quant。KBBQ 不改变 inference kernel、storage layout 或 arithmetic，因此没有 deployment-time overhead。([arXiv][11])

这和之前“Hadamard/rotation 一定越 flatten 越好”的直觉形成了一个很重要的修正：

> 对 block-scaled floating point，优化对象不是简单的 tensor max，而是 **量化噪声与 dot-product energy alignment**；过度 flatten 可能反而偏离真实 quantizer 的最佳点。

## 8. AMD AITER：MiniMax-M3 在 MI355X 上继续优化 A16W4，而不是强制所有路径都 W4A4

**状态：[已合入 main]｜AITER #5395，9 月 10 日**

AITER 为 gfx950/MI355X 的 MiniMax-M3 MXFP4 增加并调优 **A16W4，也就是 BF16 activation × MXFP4 weight** 的 FlyDSL SwiGLU MoE 路径。

M=1–256 的生产算子测试相对 CK-Tile default 全部获益，几何平均 **1.110×**；例如：

* M=4：1.188×；
* M=64：1.116×；
* M=256：1.081×。([GitHub][12])

但 MiniMax-M3 MXFP4、TP4、MI355X、8K input / 1K output、C64 的完整模型只从：

**2670.50 → 2702.36 output tok/s，约 +1.19%**

mean TPOT 22.71 → 22.44 ms，约 -1.2%。([GitHub][12])

这再次说明两个现实问题。第一，**micro-MoE 11% 并不会自动转化成 11% serving throughput**。第二，即使硬件本身有 MXFP4 W4A4 能力，W4A16 仍然可能是某些 shape / activation-sensitive 模型的重要 operating point；低比特 backend 不会简单收敛成唯一一条 W4A4 路径。

## 9. BeaconKV：不是数值量化，但它展示了“先决定存哪些 KV，再决定用多少 bit”可能比单独量化更重要

**状态：[论文]｜arXiv:2609.04971，9 月 4 日**

BeaconKV 严格来说不是 FP4/INT4 quantization，而是 **KV eviction/compression**，但我仍把它纳入这一期，因为它与低比特 KV 是高度正交、可组合的方向。

论文针对长 CoT reasoning 中的 **Thought Revisiting Tokens**：未来 query 经常会重新关注很久以前的规划/关键推理节点，单纯根据最近 query 判断 KV 重要性容易误删这些 token。BeaconKV 维护一小组 representative “beacon queries”，用 continual farthest-point sampling 捕捉这类全局 query cluster。([arXiv][13])

四个开源 reasoning model 上，论文报告：

* peak KV memory 最多 **5.8× reduction**；
* throughput **>4.3×**；
* 基本保持 full-cache accuracy；
* 在激进 memory budget 下，相比已有 compression method 最大 accuracy gain 达 **31.7 pp**。一个具体例子中，2K KV budget 把 peak memory 从 77.0 GB 降到 13.3 GB，throughput 从 82.3 增到 356.4 tok/s。([arXiv][13])

它给低比特 KV 的启示不是“用 BeaconKV 替代 FP4”，而是未来更可能出现两维压缩：

`Token selection：哪些 KV 值得留下`
×
`Numerical compression：留下的 KV 用 BF16 / FP8 / FP4 / INT4 中哪一种`

后者是基于两类技术可以组合得到的工程推断，不是 BeaconKV 已经验证的实验。

# B. vLLM / SGLang / TensorRT-LLM / FlashInfer / AITER 等框架更新

## vLLM

本周没有新的正式 tagged release 达到需要单列的程度，但 main 上的 NVFP4 变化非常密集。

除了前面的 **#55031 NVFP4 KV output-quant fusion** 和 **#55643 scale correctness**，PR **#51925 于 9 月 9 日合入**，把 Qwen3-30B 类路径中的：

`residual add + RMSNorm`
→ `FP16/BF16 intermediate`
→ `FP4 conversion`

融合为 FlashInfer add-RMSNorm-NVFP4 producer。一次 forward 替掉 **47 个 add-RMSNorm kernel，并进一步消掉 47 个 FP4 conversion launch**。([GitHub][14])

但 GB200 端到端 request latency 只改善约 **0.76%–1.02%**，GB300 约 0.79%–1.10%，并且目前默认关闭。这个例子非常适合校准预期：**减少 94 次 kernel launch 是很漂亮的 trace 优化，但如果这些 kernel 本来就只占总时延的一小部分，E2E 依然只有 1%。** ([GitHub][14])

另外，本周 vLLM 还有一个值得列入低比特测试风险的例子：旧版 v0.26.0 的 Gemma-4-26B-A4B-NVFP4 在 B200 TP2 上可因 gated-MoE end-padding 产生 silent corruption；issue 本周被重新复现，但根因修复实际上已经在更新的 upstream #48624 中。因此它更适合作为“旧环境升级理由”，而不是新 bug。([GitHub][15])

v0.5.19 除 W4A8 外，还包含几项和低比特系统密切相关的更新：

`weight precision`

* `activation precision`
* `KV precision`
* `EP communication precision`
* `host-tier cache`

一起优化。

## TensorRT-LLM

除了 **#18772 独立 gate/up NVFP4 scale**，本周 PR **#18823 于 9 月 9 日合入**，解决 Qwen3.8-Flash-Next 的 ModelOpt mixed-precision NVFP4 checkpoint 加载问题。这个所谓“NVFP4 checkpoint”实际上包含：

* routed experts：**NVFP4**；
* PLE n-gram table：**FP8**；
* MTP experts：**block-scaled FP8**。

所以全局 `MIXED_PRECISION` 只是顶层描述，真正 runtime 必须按 layer/module 解析格式。([GitHub][16])

在 B200 上，修复后的测试包括 GSM8K **95.83**、MMLU **87.60**、MMMU **58.56**；更完整的 4×B200测试中，NVFP4 ADP4 peak 约 51.5 GiB/GPU，对应 FP8 62.9 GiB、BF16 77.0 GiB。这里主要是 loader/correctness 验证，不是性能 PR。([GitHub][16])

另一个 Rubin 状态非常值得记住：**#18674，9 月 5 日 merged**。当前 TRTLLM-gen 在 **SM107/Rubin 还没有 NVFP4 KV-cache kernel**，因此如果用户请求 NVFP4 KV，框架会显式 warning 并回退 FP8，而不是尝试不存在的 kernel。这个结论只能理解成**当前 TRT-LLM 软件栈成熟度**，不能外推成 Rubin 硬件本身不支持 NVFP4 KV。([GitHub][17])

## FlashInfer

除 #4676 外，本周 9 月 10 日又合入了两条值得关注的 Blackwell NVFP4 路径。

**#5036** 把 CAKE NVFP4 warp-decode 扩展到 **SM100/B200**，同时保留 SM103/B300，并加入 standalone SiLU。96 个新 B200 route + 96 个 B300 retained route 均通过 correctness；在可比较的 SwiGLU 路径上，对官方 baseline 的几何平均是约 **1.090×**，但存在 **6 个 regression case**，范围甚至低至 0.929×，因此它非常明确地需要 tactic/shape gating，而不是无条件默认。([GitHub][18])

**#5076** 则把此前的 **NVFP4 SVDQuant** CAKE GEMM 扩到 **SM100 和 SM103**。它把 NVFP4 主 GEMM 与 low-rank correction、可选 bias 集成到生成式 CUDA backend 中；目前必须显式 `backend="cake"`，只支持 catalog 中的固定 `(M,N,K,rank,bias)` tuple，并要求 CUDA ≥13.0。B200/B300 API 验证已通过，但这个最终 PR 没有重新跑一轮完整 GPU performance measurement，因此不应该凭旧数据宣称新的性能提升。([GitHub][19])

这两条路径说明 FlashInfer 仍同时维持两种路线：

**generic/autotuned block-scaled kernels**
和
**model/shape-specialized generated kernels**。

短期看，后者不会被前者完全替代。

# C. 本周新论文

这一期我只保留两篇主论文，避免为了“论文栏”凑数量。

### KBBQ：FP4 rotation 需要“刹车”

上面已经详细分析。最值得带走的结论是：**对 FP4 来说，理论上最彻底的 spectrum flattening 不等于实际最优 quantization point**。KBBQ 的 \(\lambda\) 本质是在 transform theory 与真实 finite FP4 grid 之间加入可调节的 correction strength，而且它最终可以被 fold 回模型，不增加 runtime 成本。([arXiv][11])

### BeaconKV：低 bit 可以和 token eviction 正交组合

BeaconKV 的价值不在 datatype，而在它提醒我们：long reasoning 的 KV redundancy 不是均匀的。未来一种很自然但**尚未被该论文验证**的组合设计是：

`Beacon / sparse policy 筛出需要保留的 KV`
→ `关键 token FP8/BF16`
→ `普通 retained token FP4/INT4`

这会把“是否保存”和“保存多少 bit”从一个决策拆成两个决策。([arXiv][13])

# E. 我建议下一步在 B200 / Blackwell 上优先验证的 6 个方向

## 1. 最高优先级：复现 vLLM #55031 的“NVFP4 KV + attention-output quant fusion”

建议不要只跑 FP8 与 NVFP4 两组，而是完整做：

```text
A. FP8 KV

B. NVFP4 KV
   no output-quant fusion

C. NVFP4 KV
   + fuse_attn_quant
```

分别 sweep：

`prefill token = 1K / 4K / 8K / 32K`

`decode context = 2K / 8K / 32K / 128K`

`batch/concurrency = 1 / 8 / 32 / 64`

Nsight 中重点看：

`FMHA output`
→ `BF16 materialization`
→ `FP4/FP8 quant`
→ `o_proj`

B/C 之间是否真正消失了 BF16 HBM round-trip。#55031 的结果说明这个中间 plumbing 足以把 NVFP4 从比 FP8 **慢 18%**翻到比 FP8 **快 19%**，非常适合做一次完整归因。([GitHub][7])

---

## 2. DeepSeek-V4.1-Flash：不要先问“FP4 KV 快多少”，先拆清楚 890 bytes/token 到底由谁贡献

等 B200 的优化 inference path 稳定后，我建议首先做数据流审计：

```text
CED cross-layer KV source
CSA2 Full / Reindex / Reuse layer
Indexer-K reuse
Top-K index reuse
FP4 main KV
SWA replay
```

记录每个机制分别减少：

`resident KV bytes`
`index bytes`
`SSD persistent bytes`
`read bytes/token`
`re-index work/token`

官方本身已经说明目前还会继续与开源社区推进 inference support，所以短期第一目标应是**确认实际 vLLM/SGLang backend 走到哪个 native kernel**，而不是把 API 端的 1/4 HBM 直接当作 B200 本地部署已经复现。([深度求索][1])

我尤其建议确认 FP4 KV consumer 是否始终 native 读取，还是某些 CSA2/Reindex 路径还需要 staging 到 FP8/BF16；这会直接决定 890 bytes/token 在实际 bandwidth 上能兑现多少。

---

## 3. FlashInfer #4676：先测 append，再等 decode consumer 后做完整 KV path

当前可以立即测：

`FP8 MLA cache append`

vs

`CKV-NVFP4 + KPE-FP8 append`

测：

* append kernel latency；
* bytes/token；
* scale generation；
* page-size sensitivity；
* cache write bandwidth；
* quantization error。

但是**不要现在就拿它做 E2E decode 性能结论**，因为 PR 明确还没有 dense MLA decode consumer。([GitHub][8])

后续 decode support 一旦合入，再完整比较：

```text
FP8 resident → FP8 MLA

vs

FP4 CKV + FP8 KPE resident
→ native mixed MLA
```

我预计真正有研究价值的问题会是：**KPE 保 FP8 的 64 channels 是否足够，还是不同 layer/head 需要不同 precision 分配。**

---

## 4. 在 B200 上画出 W4A16 / W4A8 / W4A4 的真实 crossover 图

SGLang 本周已经证明 Hopper：

`MXFP4 W + FP8 A`

明显优于：

`MXFP4 W + BF16 A`。([GitHub][6])

但 B200 多了一条真正 native：

`NVFP4/MXFP4 W + FP4 A`

所以建议同一模型、同一 MoE shape，测试：

```text
W4A16
W4A8
W4A4
```

M sweep：

`1, 2, 4, 8, 16, 32, 64, 128, 256, 512`

同时记录：

* standalone activation quant cost；
* fused quant+GEMM；
* scale generation；
* Tensor Core active；
* HBM bandwidth；
* total expert latency。

这样才能判断：

> W4A4 的更高 Tensor Core density，什么时候能够真正抵消 dynamic FP4 quantization 和 scale plumbing 的成本？

这是目前单纯看 kernel peak FLOPS 回答不了的问题。

---

## 5. 做一套专门的“Scale Poison Test”，它现在比普通 random correctness test 更必要

本周 vLLM #55643 和 TRT-LLM #18772 基本是在提醒所有低比特 backend：普通 unit test 很容易在 `scale=1`、M 正好对齐时把真实 bug 全藏掉。([GitHub][9])

我建议固定加入这些 case：

```text
M = 1 / 17 / 127 / 128 / 129

input_global_scale =
0.125 / 0.37 / 1.0 / 3.7 / 8.0

gate_scale != up_scale

N/K 不满足 128 tile 对齐

scale tensor 带额外 backing storage

CUDA Graph + eager 双模式
```

并检查：

`quant value`
`scale bytes`
`scale pointer`
`scale stride`
`global scale direction`
`consumer alpha`

同时开 Compute Sanitizer 的 memcheck/racecheck/synccheck。

这套测试对于 NVFP4 可能比单纯“BF16 output allclose”更容易发现 production-only corruption。

---

## 6. KBBQ：直接在 B200 native NVFP4 上验证“大模型/MoE 是否仍存在 interior optimum”

论文的 NVFP4 已经是 GB200 native Transformer Engine W4A4，所以它不是 fake-quant artifact。([arXiv][11])

但当前模型规模只到 8B。我建议下一步直接做：

```text
Identity
Hadamard / Haar
WUSH λ=1
KBBQ λ=0.25
KBBQ λ=0.5
KBBQ λ=0.75
GPTQ
GPTQ + KBBQ
```

用完全相同的 NVFP4 kernel 和 storage，在：

* 30B dense；
* 30B-A3B MoE；
* 70B；
* 一个 NVFP4 frontier MoE

上对比。

这样性能可以视为恒定变量，只看 accuracy / calibration cost。如果大 MoE 上仍稳定出现 \(\lambda<1\) 的 optimum，那会对目前“rotation 就是尽量 flatten”的 recipe 产生相当直接的影响。

---

### 跨平台额外实验

如果同时有 MI355X 环境，本周 AMD 的 online requant 很适合做一个 checkpoint-portability 实验：

`同一 NVFP4 source`
→ `NVIDIA native NVFP4`

vs

`AMD load-time NVFP4→MXFP4`
→ `native MXFP4`

不要只比 GSM8K，最好逐层抓 weight reconstruction error、activation error、最终 logit drift，再跑 AIME/GPQA/LongBench。AMD 已经发现即使 greedy trace 100% 会发生路径分叉，最终答案仍大部分一致，这种“trajectory divergence but task-level parity”本身就很值得量化研究。([ROCm Blog][2])

# 本周三个最重要的趋势判断

**第一，低比特正在成为模型 architecture primitive，而不再只是 deployment option。** DeepSeek-V4.1-Flash 最明显：CSA2、CED、KV reuse、FP4 KV 和 FP4 experts 从一开始就共同设计。未来最强的低比特推理方案，很可能不再是“拿一个 BF16 Transformer 再优化”，而是模型训练阶段就决定哪些 state 值得保存、保存几份、用多少 bit。([深度求索][1])

**第二，“NVFP4”这个名字的信息量已经严重不够。** 本周同时出现了 16-value E4M3-scaled FP4 KV、UE8M0 expert FP4、独立 gate/up global scale、Tensor Core swizzled SF layout，以及 W4A16/W4A8/W4A4 三种不同 activation contract。今后分析一个 low-bit checkpoint，我建议固定描述成：

`Weight format × Activation format × Scale format × Scale granularity × Global scale × Layout × Kernel backend`

而不是只写“这是 NVFP4 模型”。([Hugging Face][4])

**第三，当前低比特 inference 很多最大的收益已经不是来自“再降一 bit”，而是来自消灭格式转换。** AMD 把 checkpoint 只在加载时转换一次；vLLM 把 attention output 直接交给 low-bit o_proj；add-RMSNorm 直接生成 FP4；FlashInfer 在 append 时直接写 packed KV。整个生态正在从“优化单个量化 kernel”转向：

**producer 直接生成 consumer 所需要的最终 representation。**

我认为这会是接下来几周最值得持续盯的一条主线。([ROCm Blog][2])
