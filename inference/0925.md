# A. 本周最重要的 9 项低比特进展

## 1. CUTLASS 4.8：Rubin SM107 的 FP4 执行契约开始真正公开

**状态：[正式发布]｜CUTLASS 4.8.0｜9 月 22 日**

[CUTLASS 4.8.0 Release](https://github.com/NVIDIA/cutlass/releases/tag/v4.8.0?utm_source=chatgpt.com)

这是我认为**本周最值得长期跟踪**的一项，尤其对于 Rubin。

CUTLASS 4.8 正式加入初步 Rubin/SM107 支持。CuTe DSL/Primitives 层公开的能力包括：

- FP8 Tensor Core：`MMA_K=64`
- FP4 Tensor Core：**`MMA_K=128`**
- B collector reuse
- TMEM 从 512 COL 扩展到 **576 COL**
- shared memory 提升到约 **328 KB**
- FP8/FP4 mixed-precision throughput enhancement
- **FP4 2:4 sparsity**
- asynchronous sparse MMA / atomic TMA reduce-store 等新 primitive。:chatgpt-content-reference{index="2"}

低比特部分更值得注意。Rubin 的示例已经包括 **FP4/FP6/FP8 mixed-precision block-scaled GEMM**，以及 **UE5M3 / block-32 scale-factor**；CuTe extension 还明确提供 higher-throughput FP8/FP4 block-scaled GEMM + UE5M3 scale。Operator API 的 Rubin preview 则覆盖：

`MXFP8 × MXFP4/MXFP8`

以及

`MXFP4/NVFP4 × MXFP4/NVFP4`

并明确写到 **NVFP4 的新 UE5M3 scale-factor dtype 支持**。:chatgpt-content-reference{index="3"}

这里我建议特别谨慎理解：**这不能直接推导为“Rubin 把现有 NVFP4 的 block=16、E4M3 scale 全部改成 block=32/UE5M3”**。CUTLASS 公布的是 Rubin block-scaled MMA 软件接口中新增的 scale-factor 选择和示例，并没有说明所有 NVFP4 路径统一改变语义。

但它已经是一个非常强的信号：

> Rubin 的低比特能力不是简单把 Blackwell 的 FP4 MMA 搬到 SM107，而是在 **MMA K 维度、scale-factor representation、sparse MMA、collector、SMEM/TMEM** 多个层级同时扩展。

特别是 **FP4 2:4 sparsity** 已经直接进入 CuTe primitive。对你持续跟踪的 Rubin adaptive compression，这条比营销材料更值得盯：后续应重点看 **scale descriptor、sparse metadata、MMA issue granularity 和 PTX/SASS contract** 怎么继续暴露。:chatgpt-content-reference{index="4"}

## 2. LLM-Compressor 0.14：NVFP4 的竞争进一步转向 local-scale search

**状态：[正式发布]｜v0.14.0｜9 月 22 日**

[LLM-Compressor v0.14.0](https://github.com/vllm-project/llm-compressor/releases/tag/0.14.0?utm_source=chatgpt.com)

这一版非常实质。

GPTQ 首先进行了大幅工程重写：新的 Triton quantization kernel 相对原 eager 实现约 **15× faster end-to-end**；相同 shape 的 layer 可以 batch quantization，单 batch 约 1.67×，在部分拥有大量同 shape expert 的 MoE workload 上，官方报告 **最高约 30× E2E quantization speedup**。Hessian offloading 被移除，旧 eager 路径本身也加速约 1.5–2×。:chatgpt-content-reference{index="6"}

但我更关注 NVFP4 部分。

MSE/iMatrix observer 新增 expanded grid search，用来寻找**更优的 NVFP4 local scale**。官方明确说，这个 search space 是 **Four-Over-Six 风格 scale search 的超集**。新的 Triton MSE grid-search kernel 又把 observation 时间缩短约 **10×**，full evaluation 时和 eager path bitwise parity。:chatgpt-content-reference{index="7"}

也就是说，NVFP4 PTQ 的演进路径越来越清楚：

`固定 absmax scale`

→ `4/6 二选一`

→ `更大的离散 hardware-valid scale search space`

→ `activation/Hessian-aware local scale search`

而最终导出的 FP4 value format 和 serving Tensor Core kernel完全可以不变。

这和前几周 H-Scale、ModelOpt local-Hessian/4over6 的趋势完全一致：**NVFP4 接下来很大一部分精度竞争会发生在 scale selection，而不是再发明一个新的 4-bit value code。**

此外 Model-Free PTQ 现在加入 dynamic memory-aware scheduling、**mixed precision 和 KV-cache quantization**，并统一成 `ModelFreePtqConverter`；新例子覆盖 GLM-5.2 MXFP4×MXFP8、DeepSeek-V4 MXFP4–MXFP8、NVFP4A16、FP8 Attention、W2A16/W4A16 mixed MoE 等。:chatgpt-content-reference{index="8"}

## 3. Disaggregated Quantization：prefill 和 decode 不应该被迫用同一种量化格式

**状态：[论文]｜arXiv:2609.26333｜9 月 22 日**

[Disaggregated Quantization 原文](https://arxiv.org/abs/2609.26333?utm_source=chatgpt.com)

这是本周我认为**概念上最重要的论文**。

作者的核心判断非常合理：

**Prefill 更偏 compute-bound。**

所以更需要：

`低精度 activation + 低精度 weight`
→ Tensor Core compute-native format

而：

**Decode 更偏 memory-bandwidth-bound。**

所以更需要：

`尽可能紧凑的 weight`
→ 即使 arithmetic 没那么激进也可以。

因此它不再要求同一份 checkpoint 同时服务 prefill 和 decode，而是使用：

`Prefill checkpoint`
+
`Decode checkpoint`

分别优化。:chatgpt-content-reference{index="10"}

一个非常有意思的结果是：作者发现**只在 decode 阶段取消 activation quantization**，能够改善 decode-heavy task accuracy，同时并不会增加实际推理成本——因为 decode 本来就更受 weight memory traffic 限制，而不是 activation Tensor Core FLOPS。:chatgpt-content-reference{index="11"}

更激进的版本则训练单独的 compute-native prefill weight。论文针对已经发布的 Qwen3.8-27B GGUF decoder，使用 **NVFP4 prefiller** 后，对其 1-bit decode setting 报告：

- MMLU-Pro：**+32.5 percentage points**
- MMMU-Pro：**+35.3 points**

而 decode checkpoint 本身完全不用修改。:chatgpt-content-reference{index="12"}

问题当然是多了一份 weight。

论文因此设计 **Offloaded Disaggregated Prefill（ODP）**：

`decode weights resident`
+
`prefill weights 从 SSD stream`

长 prompt 可以 amortize weight-loading cost。在 27B、8K prompt、llama.cpp 上，相比 weight-only baseline，TTFT **1.78× faster**。论文还在 vLLM 下验证了 disaggregated serving，并把 shared-weight format disaggregation 的 PTQ 验证扩展到 **2.8T 参数模型**。:chatgpt-content-reference{index="13"}

### 和 NVFP4 / MXFP4 常规方案有什么本质不同？

过去我们的思路通常是：

> “给模型找到一个最好的量化格式。”

DQ 的思路变成：

> “不存在一个对整个 autoregressive lifecycle 都最好的量化格式。”

所以未来完全可能出现：

`Prefill：W4A4 NVFP4 / MXFP4`

`Decode：W2A16 / W3A16`

`KV：FP8 / FP4`

甚至对应不同 kernel/backend。

我认为这个思路对 disaggregated prefill/decode serving 很可能非常重要。

代价则是明显的：**checkpoint 数量、存储、load/stream、权重版本一致性和 scheduler complexity 全部增加。**

## 4. vLLM v0.30.0：DeepSeek-V4.1 的整份 KV 开始直接以 MXFP8 保存

**状态：[正式发布]｜v0.30.0｜9 月 22 日**

[vLLM v0.30.0](https://github.com/vllm-project/vllm/releases/tag/v0.30.0?utm_source=chatgpt.com)

本周 vLLM 正式发布 v0.30.0，其中最值得关注的低比特变化是 **DeepSeek-V4.1-Flash 在 SM100 上通过 FlashMLA V4.1 record 将 whole KV 存为 MXFP8**。:chatgpt-content-reference{index="15"}

量化框架本身也进一步模块化：

- 可以用 `quantization_config.targets` 只在线量化指定模块；
- 支持 partially pre-quantized checkpoint；
- 增加 **W4A16 DSA + `nvfp4_fp8_ds_mla` KV cache**；
- SM100/SM103 上 FlashInfer CuTeDSL **NVFP4 W4A16 默认优先于 Marlin**；
- NVFP4 进入 torch linear backend；
- 支持 per-quantization backend override；
- AutoRound CUDA 支持扩展到 **2/3/5/6/7-bit**。:chatgpt-content-reference{index="16"}

这里非常值得注意的一点是：

> vLLM 已经开始把“量化方法”和“执行 backend”明显解耦。

例如同样是 NVFP4 weight-only W4A16，在不同 GPU、M/N/K、模块上可以选择 CuTeDSL、Marlin 或其他 backend，而不是 `NVFP4 == 某一个 kernel`。

另一个对大型 FP4 checkpoint 很实用的新功能是 **Fast Start**：后台 persistent GPU weight-cache daemon 保存**已经完成 quantization + TP sharding 的 weights**，engine 重启时直接通过 CUDA IPC map，而不是重新从 disk load/quantize。v0.30 已支持 FP4 checkpoint 和 multi-node TP。:chatgpt-content-reference{index="17"}

对于几百 GB～TB 级低比特 MoE，这种优化解决的已经不是 token latency，而是**模型重启和弹性调度的分钟级成本**。

## 5. FlashInfer 0.7：正式把低比特 execution contract 写进 API

**状态：[正式发布]｜v0.7.0｜9 月 22 日**

[FlashInfer v0.7.0](https://github.com/flashinfer-ai/flashinfer/releases/tag/v0.7.0?utm_source=chatgpt.com)

FlashInfer 0.7 把 `MoELayer` 升为正式 API，同时引入一个我认为非常正确的设计：

`QuantConfig(weight=...)`
`QuantConfig(activation=...)`
`QuantConfig(output=...)`

也就是说，precision 不再用模糊的“这是个 MXFP4 模型”表示，而是明确表达 execution contract。

例如：

`weight=MXFP4`

代表可以是：

**MXFP4 W + BF16 A = W4A16**

而再加：

`activation=MXFP8`

则明确变成：

**MXFP4 W + MXFP8 A = W4A8**。:chatgpt-content-reference{index="19"}

这实际上非常符合最近几个月低比特生态暴露出的各种 bug：只看 checkpoint 名称里的 `NVFP4` / `MXFP4` 根本不足以决定 kernel。

0.7 的 Expert Parallel 也值得关注。B200 上增加 W4A8 split backend，dispatch payload **直接 packed 成 MXFP8**；NCCL-EP path 已支持 CUDA Graph。也就是说：

`MXFP8 quant`
→ `NCCL communication`
→ `MXFP4 MoE`

低比特仍然在继续向**通信格式**扩展。:chatgpt-content-reference{index="20"}

Sparse attention / KV 侧，DeepSeek-V4 Flash 在 SM120/SM121 上已经支持：

`kv_cache_format="nvfp4"`

MiniMax-M3 的 CAKE sparse-attention kernel 在 B200 11 个可比较 case 上，release note 报告对 baseline 的几何平均 **2.45× kernel speedup**。:chatgpt-content-reference{index="21"}

### 但这一版有一个非常重要的 correctness warning

FlashInfer 明确警告：

SM100/SM103 上 CUTLASS `gemm_fp8_nt_groupwise`，当

`M <= 32`

且 scale granularity 为：

`(1, 128, 128)`

时，可能**间歇性产生错误输出**。

这个问题在 **0.7.0 仍然存在**。:chatgpt-content-reference{index="22"}

这对 B200 decode/small-M workload 很重要。不是性能 regression，而是 silent/incorrect output 风险。

## 8. AMD：GLM-5.2-MXFP4 告诉我们，低比特权重省出来的 HBM 也可能被并行策略重新吃掉

**状态：[AMD 官方工程实践]｜9 月 21 日**

[AMD：Serving GLM-5.2-MXFP4 on MI355X](https://rocm.blogs.amd.com/artificial-intelligence/glm52-mxfp4-mi355/README.html)

AMD 本周专门分析了 **4×MI355X、SGLang、TP4、GLM-5.2-MXFP4** 的 Prefill Context Parallelism。

长 prompt 下结果很好：

40,960 / 61,440 token prompt、concurrency ≥16 时，开启 CP 后：

- total throughput：**+43%～+54%**
- TTFT：约 **1.5×～2.3× faster**

但 1024-token prompt 下：

- throughput 反而 **下降 8%～18%**。:chatgpt-content-reference{index="29"}

原因很值得低比特部署关注。

开启 CP 后 `attn_tp_size=1`，attention weight 不再 TP shard，而是在四张卡上复制。每 rank 的 weight footprint：

**101.45 GB → 120.13 GB**

多了 **18.68 GB/GPU**。

结果直接吃掉 KV cache，少了：

**199,744 tokens 的 KV pool capacity。** :chatgpt-content-reference{index="30"}

这项本身不是一个新量化算法，但系统意义很强：

> **MXFP4 把 weight 压小，不代表这些省出来的显存最终都会给 KV Cache。**

并行策略、replication、workspace、CUDA Graph pool 都可能重新占掉它。

所以长上下文低比特优化最好统一看：

`weight bytes`
+
`KV bytes`
+
`parallel replication`
+
`communication`
+
`workspace`

而不是只看 checkpoint size。

## 9. SPHQuant：2～3 bit weight-only 开始从 scalar quantization 转向几何编码

**状态：[论文]｜arXiv:2609.24875｜9 月 21 日**

[SPHQuant 原文](https://arxiv.org/abs/2609.24875?utm_source=chatgpt.com)

SPHQuant 针对极低 bit weight-only VLM/LLM backbone。

它不再直接对 Cartesian weight 做 scalar/group quantization，而是将每个 **8D weight vector** 分解为：

`coordinate signs`
+
`radius`
+
`positive unit direction`

其中 outlier magnitude 集中到 radius，因此给 radius 分配更高 precision；direction 则使用小型 codebook，并通过 angular parameterization fine-tune。:chatgpt-content-reference{index="32"}

执行侧作者专门设计 GEMV kernel：

- direction codebook 放 shared memory；
- radius bits 做紧凑 packing；
- 不需要 rotation runtime。

RTX A6000 上，相对 QTIP，论文报告 decode throughput **+30.3%**，同时保持与主流 extreme-low-bit 方法相近的模型质量。:chatgpt-content-reference{index="33"}

这条线与 NVFP4/MXFP4 很不一样。

FP4 是：

`hardware-native 4-bit floating value + block scale`

SPHQuant 更接近：

`vector codebook + radius/sign encoding + custom GEMV`

所以它的上限取决于 custom kernel，而不是 Tensor Core 原生 datatype。

我认为它更值得作为 **2～3 bit decode memory-bound 路线**跟踪，而不是与 NVFP4 W4A4 正面比较。

## CASA：低于 3 bit 后，单个 scalar sensitivity 已经不足以决定谁该多分 bit

**论文：Beyond Scalar Sensitivity: Activation-Aware Mixed-Precision LLM Quantization with Cross-Layer Refinement**

**提交：9 月 22 日**

[CASA 原文](https://arxiv.org/abs/2609.25916?utm_source=chatgpt.com)

很多 mixed-precision quantization 会给每个 matrix 算一个 scalar sensitivity，然后做 Multiple-Choice Knapsack：

`这个 layer 2 bit`
`那个 layer 3 bit`
`重要 layer 4 bit`

CASA 指出问题是：把完整 activation/Hessian geometry 压成一个 scalar 会严重失真。作者证明，相对完整 activation-aware quadratic，最佳 scalar proxy 的 distortion bound 可以达到：

\[
\sqrt{\kappa(A)\kappa(B)}
\]

而真实 LLM module 中，这个 bound 的量级可以从 **10¹ 到 10¹³**。:chatgpt-content-reference{index="46"}

方法分两阶段：

第一阶段使用 Kronecker-factored activation-aware sensitivity 分配 bit；

第二阶段再通过 cross-layer end-to-end loss 做 local search。

实验显示它在多个模型和 bit budget 下比 scalar-proxy baseline 有更低 perplexity，优势在 **<3 bits/weight** 时最明显。:chatgpt-content-reference{index="47"}

这篇论文对 4 bit 未必马上带来巨大影响，但对未来 **W2/W3 mixed precision MoE** 很有价值。

因为低于 3 bit 后，问题已经越来越不是：

> “哪个 tensor 的 max 比较大？”

而是：

> “量化这个 module 的误差，沿完整网络传播后到底影响什么？”

### 5. 对 DeepSeek-V4.1 的 MXFP8 KV，重点拆 scale traffic

\text{Scale Metadata Overhead}

# 本周我的三个核心判断

**第一，Rubin 的低比特升级已经开始从“推测”进入可观察的软件接口。**

CUTLASS 4.8 首次把 FP4 `MMA_K=128`、FP4 2:4 sparse MMA、UE5M3/block-32 scale-factor、B collector reuse、SMEM/TMEM 扩展放在一起。接下来真正值得跟踪的不是“Rubin FP4 比 B200 快几倍”，而是 **FP4 value、scale、sparsity metadata 与 MMA issue 如何共同组织**。:chatgpt-content-reference{index="57"}

**第二，未来的量化单位很可能不是“模型”，甚至不是“层”，而是“推理阶段”。**

Disaggregated Quantization 把 prefill 和 decode 直接拆成两套权重/格式；vLLM 又允许 targeted online quantization 和 per-quantization backend override。最终系统很可能变成：

`phase × module × weight format × activation format × KV format × backend`

共同决定 precision。:chatgpt-content-reference{index="58"}

**第三，4 bit 本身越来越不是主要研究问题，真正难的是如何把 4 bit 无缝送到 consumer。**

本周最有价值的工作，本质上都围绕这件事：

`NVFP4 local scale search`

`MXFP8 KV record`

`MXFP8-packed EP dispatch`

`explicit W4A16/W4A8 contract`

`Rubin scale-factor primitive`

未来低比特 inference 的关键性能指标，我建议已经可以从单纯的：

**“bit 数 / Tensor Core TFLOPS”**

升级为：

**“从 producer 到 consumer，中间发生了多少次 quant / dequant / repack / scale transform / communication。”**

谁能把这条数据流做成**一次量化、原样存储、原样通信、直接消费**，谁更可能拿到真正的端到端收益。:chatgpt-content-reference{index="59"}
