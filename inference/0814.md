# vLLM / SGLang 低比特推理周报

**时间范围：2026 年 8 月 7 日—8 月 14 日**

本周不是“低比特没有实质更新”的一周，反而有几项相当值得关注的变化。整体趋势很清楚：**SGLang 在 NVIDIA Blackwell 上继续把低比特路径往 FlashInfer / CuTe DSL / TRT-LLM 专用 kernel 收敛；vLLM 则在 MXFP4、NVFP4 online quantization、4-bit KV Cache 以及 AMD MI355X/DeepSeek-V4 上推进得很快。** 本周重要信息全部来自官方 release 或已经 merged 的 GitHub PR，可信度高。([GitHub][1])

版本层面，vLLM 在 **8 月 10 日发布 v0.27.0**，8 月 11 日又发布 **v0.27.1**；SGLang 在 **8 月 8 日发布 v0.5.17**。需要特别区分：下面一些 8 月 10—13 日才合入 SGLang main 的 kernel，例如 MXFP8 CuTe DSL，并不在 8 月 8 日的 v0.5.17 tag 里；vLLM 的 #50074、#51359、#52114 同理都是 v0.27.1 发布后才合入 main。([GitHub][1])

## 一、vLLM：本周最重要的低比特变化

### 1. DeepSeek-V4 MXFP4：TP8 不再把 I384 强行 pad 到 I512

我认为这是本周 vLLM **性能/显存收益最实在的一项**。PR **#51473，8 月 11 日 merged**，针对 ROCm/AITER 下 DeepSeek-V4 的 MXFP4 routed experts。DSV4 expert intermediate size 是 3072，TP8 后每卡实际应持有 **384**；此前通用 MXFP4 分配路径却会把 384 pad 到 512，导致 routed-expert resident allocation 白白膨胀约 **33%**。现在 AITER BF16/SiLU 路径保留原生 I384。([GitHub][2])

8×gfx950 实测非常明显：每 rank 模型显存从 **156.45 GiB → 125.20 GiB**，节省 **31.25 GiB/GPU**；可用于 KV Cache 的空间从 39.31 GiB 增至 71.85 GiB，KV token capacity 从 285.98 万增至 522.66 万，提升 **82.76%**。普通 8K input / 1K output、C64 测试吞吐提升约 2.64%；另一组 C64 sweep 达到 **+5.56% throughput**。([GitHub][2])

更有意思的是 agentic + prefix-cache 场景：一小时 C64 实验里 request throughput 提升 **47.45%**，总 token throughput +34.21%，mean TTFT -39.51%，mean TPOT -25.59%。不过 PR 作者明确说明，这里无法把“更多 KV capacity”和“MoE physical width 减小”两个贡献拆开，所以不能把 47% 简单理解成 GEMM 本身快了 47%。([GitHub][2])

**意义：** 这再次说明低比特 MoE 的性能问题已经不只是“Tensor Core 算得快不快”，**physical layout、padding、sharding 和 quant scale layout 本身就可以吃掉几十 GiB 显存**。这对后续 Rubin 动态压缩、稀疏 expert physical layout 的分析也很有参考价值。

---

### 2. vLLM 正式加入 MI355X 的 TurboQuant 4-bit KV decode 专用 FlyDSL kernel

PR **#47896** 本周合入，AMD 为 gfx950/MI355X upstream 了一条专门的 **TurboQuant 4-bit KV Cache decode kernel**。它不是简单“KV 保存成 INT4 再统一 dequant”，而是针对 TurboQuant 的 key centroid/value 4-bit representation，直接在 decode attention kernel 中完成读取、恢复和 attention 计算。支持 HEAD_SIZE=128，以及 GQA=8/16；MiniMax-M2.5 的 GQA=6 还有专门路径。满足条件时自动选择 FlyDSL，否则回退 Triton。([GitHub][3])

MiniMax-M2.5，32K input / 1K output，TP2、C64、MI355X 的端到端结果中，FlyDSL TQ44 **比 BF16 KV 快 7%**，相对于原来的默认 vLLM TurboQuant 4-bit decode 则约 **4.1×**。GSM8K 上 MiniMax-M2.5 BF16 88.17 → TQ44 87.95，Qwen3-32B 95.45 → 95.15，下降约 0.22/0.30 个百分点。([GitHub][3])

这项工作很值得关注，因为它说明 **4-bit KV Cache 真正要产生性能收益，必须有“压缩格式原生 attention kernel”**。如果仅仅节省 HBM、然后走一个昂贵的通用 dequant path，低 bit KV 未必更快。

---

### 3. Online MXFP4 已经真正进入 vLLM：BF16/FP16 checkpoint 可直接启动后量化

PR **#49347，8 月 7 日 merged**，加入 **online MXFP4 linear + MoE quantization**。现在可以直接对 BF16/FP16 checkpoint 使用：

`--quantization mxfp4`

或者用 online quantization config 指定 linear/MoE 为 MXFP4，而不需要提前生成 MXFP4 checkpoint。实现中统一了 XPU/AITER/Triton fallback quantizer。([GitHub][4])

小规模验证也比较正常：Qwen3-30B-A3B 的 offline MXFP4 GSM8K 为 0.8923、online 为 0.9060；运行时间 18.9s vs 19.2s。Qwen3-1.7B offline/online 分别 0.2896/0.2904。这里不能据此宣称 online 更准或更快，只能说明**在线生成的 MXFP4 权重没有出现明显正确性退化**。([GitHub][4])

对 RL、持续更新权重、BF16 checkpoint → inference worker 的工作流来说，这比普通离线量化更重要。

---

### 4. Online NVFP4 MoE 修复 repeated reload 后出现 NaN/Inf

PR **#50074，8 月 12 日 merged**，解决一个很典型的 online quantization 生命周期问题。此前重新载入 BF16 权重时，`process_weights_after_loading` 不仅重新量化权重，还会替换 MoE kernel/config object；但 CUDA Graph/compiled execution 仍可能引用旧对象，重复 reload 后会执行 stale state，最终产生 non-finite output。现在 kernel/config 生命周期保持稳定，只重新量化和安装新权重。([GitHub][5])

官方 paired test 中，修复后连续 5 次 reload **0 个 non-finite rollout error**；旧实现第 5 次出现 16 个错误，占该 rollout batch **11.1%**。([GitHub][5])

这项对 **RL rollout / weight reload / colocated training-inference** 的实际意义远高于普通 serving。它说明在线 FP4 现在开始进入“反复换权重”的真实训练工作流，而不只是一次性模型加载。

---

### 5. Blackwell FP8 / MXFP4 correctness 仍在快速补洞

PR **#51359** 修复了 DeepGEMM `QuantFP8` 的 UE8M0 scale fast path：在 RTX PRO 6000 SM120 上发现 oracle 可能尚未初始化，同时 packed group path 只应作用于 group_size=128。该路径在 Hopper 上基本 dormant，而 **SM100/SM120 Blackwell 会真正触发**，所以属于典型的“Blackwell 新路径开始大规模被跑起来后暴露出来的问题”。([GitHub][6])

MXFP4 checkpoint 方面，**#51419** 修复了一些 checkpoint 将 `weight_scale` 存成 FP32 时加载进 uint8 容器的问题，同时补了 per-expert quantized checkpoint 的 weight mapping。([GitHub][7])

此外 **#52114，8 月 13 日**加入 Ling 的 hybrid quantization：dense/shared expert 用 block FP8，而 routed experts 用 MXFP4，并针对 main/MTP 模型重新映射 scale metadata。这也是最近越来越明显的趋势：**一个模型不再对应“一种量化格式”，而是不同 component 使用不同格式。** ([GitHub][8])

---

### 6. vLLM v0.27.0 本身也带了几项值得注意的低比特能力

v0.27.0 在 SM100 上进一步集成 **FlashAttention 4 + FP8 KV Cache**，同时支持 head-dim 256；DeepSeek-V4 增加 compact **MXFP4 indexer KV cache**，FlashInfer ≥0.6.14 后还取消了 sparse-MLA 的 q-head padding。Kimi K3 则一次性加入 DeepGEMM 和 compressed-tensors quantized checkpoint 支持。与此同时 PyTorch 升到 2.13、Triton 升到 **3.7.1**，属于需要注意的 breaking environment change。([GitHub][1])

v0.27.1 本身很小，主要新增 **quantized DSpark Markov heads** 支持。([GitHub][1])

# 二、SGLang：Blackwell 低比特 backend 本周变化更值得你关注

### 1. MXFP8 GEMM：SM10x 默认开始转向 FlashInfer CuTe DSL

本周最值得在 B200 上直接测试的 PR 是 **#34042，8 月 13 日 merged**。SGLang 新增：

`--fp8-gemm-backend=flashinfer_cutedsl`

并且对于 **SM10x 的 dense MXFP8 GEMM，auto 现在会自动选择 FlashInfer CuTe DSL**；SM120 仍走 CUTLASS，因为当前没有对应 CuTe DSL kernel。CuTe DSL 路径还接入了 FlashInfer autotune。([GitHub][9])

作者用 Kimi K3 / GLM-5.2 的真实 GEMM shape 做了 benchmark。在 GLM-5.2 的 `M=1, N=16384, K=2048` 上，persistent CUTLASS 是 **31.771 μs**，CuTe DSL tuned 为 **8.266 μs，3.844×**；M=32 时约 3.24×，M=64 时 1.95×，M=256 仍有 1.55×。随着 M 增大优势明显缩小，M=512 约 1.14×。测试 correctness 的机器是 B300/SM103。([GitHub][9])

这组数据非常有信息量：**MXFP8 decode/small-M GEMM 才是 CuTe DSL 最大优势区间**，而不是“大 M 全部几倍”。因此它对 decode latency、MoE 小 token batch、speculative path 的影响可能比纯 prefill 更大。

---

### 2. MiniMax NVFP4：SM100 的 auto MoE backend 改为 `flashinfer_trtllm_routed`

PR **#32229，8 月 10 日 merged**，专门处理 MiniMax-M2/M2.7 NVFP4 的 routing semantics。普通 `flashinfer_trtllm` 不支持该 routing 方式，因此现在在 SM100/SM103 上，MiniMax `modelopt_fp4` + `--moe-runner-backend auto` 会自动选择：

`flashinfer_trtllm_routed`

而不是错误进入普通 TRT-LLM path。([GitHub][10])

更关键的是作者比较了三种可工作的后端。MiniMax-M2.7 NVFP4、GB200 SM100 上，C64 output throughput：

| backend                      |      tok/s |
| ---------------------------- | ---------: |
| flashinfer_cutlass           |     4528.1 |
| flashinfer_cutedsl           |     4936.0 |
| **flashinfer_trtllm_routed** | **5978.6** |

C128 则是 7194.9 / 8346.7 / **9716.7 tok/s**。也就是说 routed TRT-LLM 在这些生产并发下比 CUTLASS 高约 **32–35%**，同时 TTFT 和平均 latency 也最好。([GitHub][10])

这项非常值得关注，因为它说明 **“NVFP4”并不足以确定最佳 kernel，MoE routing semantics 本身也决定 backend**。

---

### 3. Nemotron W4A16-NVFP4：不是所有 NVFP4 都应该走 FP4 Tensor Core W4A4 path

PR **#33543，8 月 7 日 merged**，与 Nemotron 尤其相关。SGLang 现在识别 ModelOpt mixed-precision checkpoint 中的 **W4A16_NVFP4 MoE expert**：普通 NVFP4/W4A4 在 SM100 仍默认 `flashinfer_trtllm`，但 **W4A16 NVFP4 expert 会改走 Marlin**。同时补了 TP shard 后 K/N 不满足 Marlin thread-tile alignment 时对 weight、scale、activation 的 padding。([GitHub][11])

这是一个很重要的概念区分：

**NVFP4 是 weight storage/quantization format，并不自动等于 W4A4 Tensor Core execution。**

如果 activation 仍是 BF16/FP16，即 W4A16，则可能应该走 Marlin 一类 weight-only kernel；只有真正 W4A4/NVFP4 activation path 才适合 FlashInfer/TRTLLM FP4 Tensor Core kernel。([GitHub][11])

---

### 4. FP8 activation quantization 从 AOT kernel 迁到 JIT

PR **#34257，8 月 11 日 merged**，把 CUDA per-token FP8 E4M3 activation quantization 从预编译 `sgl_kernel` AOT 实现迁到了 SGLang 的 lightweight JIT infrastructure，并保留原 API 和 bit-level behavior。([GitHub][12])

性能不是统一大涨，但整体正收益。H200 72 个 shape 几何平均 **1.095×**，58/72 个配置更快；B300/SM103 几何平均 **1.061×**，48/72 更快。B200 已经加入 SM100-specific reduction path 的 bit-exact CI coverage。也就是说，这次更大的价值其实是**降低 AOT wheel 依赖 + 让 kernel 更容易继续针对新架构调优**，而不是那 6–10% 本身。([GitHub][12])

---

### 5. ModelOpt mixed precision 开始把 embedding 也压成 NVFP4

PR **#34222，8 月 10 日 merged**，新增 `ModelOptNvFp4EmbeddingMethod`。此前 checkpoint 如果把 `VocabParallelEmbedding` 标成 NVFP4，SGLang 无法正常 dispatch；现在 embedding table 保持 packed NVFP4，gather 到所需 row 后再解包到 activation dtype。([GitHub][13])

这里作者特别强调：**没有算力加速**，因为 embedding 本质是 row gather，不是 GEMM；收益纯粹来自 footprint。对于 20 万 vocab、几千维 embedding，BF16 → 4 bit 可以省下约 GiB 级显存，而单卡部署时这部分空间可以直接让给 KV Cache。([GitHub][13])

这个方向非常值得关注：低比特已经开始从“只量化 Linear/MoE”扩展到**模型所有 resident tensor 的显存工程**。

---

### 6. HiSparse + FP8 KV + SM120 的 FlashInfer sparse MLA 启动问题修复

PR **#33075，8 月 11 日 merged**。此前 GLM DSA + SM120/SM121 + `fp8_e4m3` KV 时，resolver 正确选到了 `flashinfer_sparse_mla`，但 HiSparse validator 还只允许 `flashmla_kv`，导致 RTX PRO 6000 / RTX 5090 根本无法启动。现在允许 FlashInfer sparse MLA。([GitHub][14])

这是 correctness/配置修复，不是新的性能 kernel，但对后续在 **SM120 上做 DSA sparse attention + FP8 KV** 很重要。

---

# 三、SGLang v0.5.17 本身值得记住的内容

v0.5.17 正式带来了 **Kimi K3 native MXFP4 checkpoint** 支持，并在 GB300、AMD MI35x 上验证；同时加入 `nvidia/MiniMax-M3-NVFP4`。DCP 的 `a2a` 还能将 FP8 KV 直接作为 uint8 byte transport，GB200 上可走 FlashInfer MNNVL `fi_a2a`。([GitHub][15])

另外，DeepSeek-V4 FP8 在 SM90 新增 DeepGEMM MegaMoE A2A 路径，通过 `SGLANG_OPT_USE_DEEPGEMM_MEGA_MOE=1` 打开；AMD 的 DeepSeek-V4 FP4 路径也继续削减 expert padding，release note 给出的 MI355X model weight footprint 从 **159.07 GB → 112.36 GB**。([GitHub][15])

---

# 四、AWQ / GPTQ / INT8 / Marlin / cuBLAS / TE 这一周怎么看

vLLM 本周 AWQ/GPTQ 没有出现新的 NVIDIA GPU 主力 kernel，主要变化是 **s390x CPU 增加 GPTQ/AWQ**；INT8 则有两个 correctness 修复，包括 TritonExperts 的 W8A8 MoE crash，以及 dynamic INT8 W8A8 MoE 被错误构造成 W8A16。([GitHub][16])

Marlin 反而有一个非常明确的新定位，就是上面 Nemotron 的 **W4A16 NVFP4**。从本周几个关键 PR 看，NVIDIA 低比特主线明显不是往“统一用一个 generic GEMM backend”走，而是进一步细化成 **FlashInfer CuTe DSL、FlashInfer TRTLLM routed、Marlin、DeepGEMM、FA4** 等针对 format × architecture × routing × shape 的专用路径。SGLang 甚至已经有 RFC 提议移除 `torchao` inference integration，理由之一就是它的 FP4/MX 支持落后于 SGLang 已有的 FlashInfer/TRTLLM/CUTLASS/Marlin/AITER 专用路径；不过这目前只是 RFC，**尚不能当作已经移除**。([GitHub][17])

本周没有看到 Transformer Engine 或 cuBLAS/cuBLASLt 成为这两个 serving framework 低比特新功能的核心落点；**ModelOpt 是活跃的 checkpoint/quantization format 层，而真正的 serving execution kernel 越来越多地下沉到 FlashInfer、TRTLLM、CuTe DSL、Marlin 和 DeepGEMM。** 这点我认为比某一个单独 PR 更值得持续观察。([GitHub][13])

## 五、值得你进一步跟进 / 测试

结合你目前主要在 B200 上做 NVFP4、MXFP4/FP8 和推理后端实验，我会按下面的优先级测试：

1. **最高优先级：SGLang #34042，B200 上测 MXFP8 CuTe DSL。** 用 GLM-5.2/Kimi K3 的真实 GEMM shape，对比 `auto`、`flashinfer_cutedsl` 和 CUTLASS，尤其分别 sweep M=1/8/32/64/256/512。PR 的性能数据来自 B300/SM103，而 backend rule 覆盖 SM10x，因此 **B200/SM100 的实际收益需要单独验证**。([GitHub][9])
2. **MiniMax NVFP4 backend selection。** 在 B200 上对 MiniMax 系列检查 `auto` 最终解析出的 MoE runner，重点比较 `flashinfer_trtllm_routed`、`flashinfer_cutedsl`、`flashinfer_cutlass`。#32229 明确验证的是 M2/M2.7；对于 M3-NVFP4，不要直接假定完全相同，值得打印最终 backend 做确认。([GitHub][10])
3. **Nemotron NVFP4 要先区分 W4A4 与 W4A16。** 如果 checkpoint 的 expert 实际是 W4A16_NVFP4，SGLang 现在应该走 Marlin；如果是 W4A4，则仍偏向 FlashInfer/TRTLLM。你后续比较 NVFP4 kernel 时最好把这一层显式记录下来，否则很容易把“同叫 NVFP4”的两种执行路径混在一起。([GitHub][11])
4. **B200 上复测 per-token FP8 JIT。** 不只测 standalone kernel，还应测真实 MoE/linear pipeline，因为 microbenchmark 几何平均只有约 6–10% 提升，而且部分 shape 会变慢。可以顺便和 vLLM v0.27.0 的 FA4 FP8 KV Cache 一起观察，区分 activation quant overhead 与 KV bandwidth 收益。([GitHub][12])
5. **如果你接下来做 RL / weight reload，优先拉 vLLM #50074。** Online NVFP4 repeated reload 已经出现过实测 non-finite failure，属于“不一定第一轮暴露、跑几个 rollout 才炸”的问题；同时可以把 #49347 online MXFP4 加进同一套 reload/accuracy test harness。([GitHub][5])
6. **如果后面能拿到 MI355X，重点验证 #51473 + #47896。** 前者体现的是 MXFP4 physical-layout/KV-capacity 优化，后者体现 4-bit KV cache 原生 decode kernel 的收益；这两项对理解未来更激进的低 bit / compressed attention hardware-software co-design 很有价值。([GitHub][2])

**本周我最建议记住的三件事**是：第一，SGLang 已经开始在 SM10x 上把 **dense MXFP8 默认 GEMM 从 persistent CUTLASS 转向 FlashInfer CuTe DSL**；第二，NVFP4 的最佳执行后端越来越依赖 **W4A4/W4A16、routing semantics 和具体模型**，而不仅仅依赖“格式叫 NVFP4”；第三，低比特 KV Cache 的下一阶段竞争已经明显转向 **压缩格式原生 attention kernel**，而不是单纯把 KV 存成更少 bit。([GitHub][9])
