# 低比特大模型推理周报｜2026-09-11—2026-09-18

这一周我认为最值得关注的变化有四条。第一，**scale/metadata 已经彻底进入低比特性能主路径**：FlashInfer 在 Rubin SM107 上仅通过重做 NVFP4/MXFP4/MXFP8 的 scale-store locality 就拿到约 10% 的整体量化 kernel 几何平均收益；Triton 则发现，连“global scale 应该作为 scalar 还是 vector load”这种看似很小的 compiler decision，都可能因为 local-memory spill 带来 20%～80% 的 kernel 差异。第二，**低比特 KV 正进一步从固定 dtype 转向“每次 query 决定读多少 bit”**，Fathom 是本周最有代表性的工作。第三，1.58-bit/ternary 的竞争开始从“数值格式”进入**编码格式与真实权重分布联合设计**，BITCOS 实际做到最低 1.485 bit/weight。第四，低比特 speculative decoding 暴露出一个很危险的新问题：**draft 模型本身输出正常、量化精度看起来也不差，并不代表它还是一个好的 drafter；acceptance rate 可以无声崩到接近 0。** ([GitHub][1])

先说明版本边界：严格按 **9 月 11 日—9 月 18 日**统计，vLLM 最新正式版仍是 **v0.29.0，9 月 9 日发布**；SGLang 最新正式版仍是 **v0.5.19，9 月 5 日发布**。所以本周真正有价值的增量主要集中在 **main、已合并 PR、开放 PR/RFC/issue 与论文**，而不是新的 tagged release。([GitHub][2])

# A. 本周最重要的 9 项低比特进展

## 1. FlashInfer：Rubin SM107 的量化优化，核心竟然是“scale 怎么写回内存”

**状态：[已合入 main]｜PR #5300｜9 月 17 日**

[FlashInfer #5300](https://github.com/flashinfer-ai/flashinfer/pull/5300?utm_source=chatgpt.com)

FlashInfer 针对 **SM107/Rubin** 重调了 `nvfp4_quantize`、`mxfp4_quantize`、`mxfp8_quantize`。最重要的新路径是 **128×4 tile quantization**：原来的 row-based kernel 中，一个 warp 对应一行，1-byte scale 写入 128×4 scale layout 时会散落到多个 128B cache line；现在一个 CTA 直接负责 128 行×4 scale-column，把连续的 512B scale tile 暂存在 shared memory，再进行 full-line write。量化值本身 byte-exact 不变，优化的是 **scale-store locality**。([GitHub][1])

Rubin cold-L2 benchmark 中，128×4 路径相对 main 的几何平均收益为：NVFP4 BF16 **1.08×**、FP16 **1.09×**；MXFP4 约 **1.03×**；MXFP8 约 **1.04～1.05×**。后续完整 135-cell sweep 的总体几何平均为 **1.097×**，其中 128×4 子集达到 **1.19×**，而且没有 cell 低于 0.98×。这个 PR 的所有 dispatch 都限定 `compute capability == 10.7`，SM100/SM103 不受影响。([GitHub][1])

我认为这项工作的意义比“Rubin quant kernel 快 10%”更大。它再次证明低比特 tensor 的真实物理格式其实是：

**value bytes + scale bytes + scale swizzle + scale store/load pattern。**

在 block scaling 下，scale 已经不再是附属 metadata，而是需要独立优化 locality、TMA layout 和 cache-line utilization 的数据流。

## 2. BITCOS：ternary 模型第一次实际低于“1.58 bit/weight”

**状态：[论文]｜arXiv:2609.16338｜9 月 14 日**

[Breaking the 1.58-bit Barrier for Ternary LLMs](https://arxiv.org/abs/2609.16338?utm_source=chatgpt.com)

传统 ternary weight 为 `{-1,0,+1}`，通常以 \(\log_2 3≈1.585\) bit/weight 描述；现实部署常用 5-trit/byte packing，实际约 **1.625 bit/weight**。作者检查了 29 个真实 ternary LLM，发现 0 的比例最高达到 **51.5%**，因此三个符号显然不是等概率的。([arXiv][3])

BITCOS 不再把三个符号统一编码，而是拆成：

`presence bitmap：这个 weight 是否非零`
+
`sign vector：非零 weight 是 +1 还是 -1`

如果零比例为 \(z\)，平均存储代价是约 **2-z bit/weight**。在 29 个模型中，它有 26 个比 5-trit packing 更紧凑，最稀疏模型达到 **1.485 bit/weight**。这并没有违反信息论；1.585 bit 是三个符号等概率时的参考，而真实 ternary 权重分布具有明显偏置，真实 entropy 可以更低。([arXiv][3])

作者同时实现 AVX-512、AVX2 与 Intel Xe2 GPU unpacking。相对 production ternary matvec kernel，真实 zero-density 下最高 **1.28×** kernel gain；五个平台的端到端 decode 最多提升 **CPU 1.18×、GPU 1.27×**。([arXiv][3])

和 NVFP4/MXFP4 的区别非常明显。FP4 在做的是：

`4-bit floating value + block scale`

BITCOS 做的是：

`极低熵离散权重 + distribution-aware encoding + 解码 kernel`

所以真正进入 2 bit 以下后，**bit-width、sparsity、entropy coding 与 hardware unpack cost 必须一起设计**，仅讨论“算术精度几 bit”已经不够。

## 3. Fathom：4-bit KV 不再意味着“每次都读完整 4 bit”，而是每个 query 动态决定读几层 bit-plane

**状态：[论文]｜arXiv:2609.17652｜9 月 15 日**

[Fathom 论文](https://arxiv.org/abs/2609.17652?utm_source=chatgpt.com)

Fathom 针对的是 **百万 token、KV/index offload 到 CPU host memory** 的 sparse decode 场景。此时瓶颈不再是 GPU attention FLOPS，而是每个 decode query 为寻找 top-k keys，需要从 host 扫描多少 key/index bytes。([arXiv][4])

它把 K cache 以 **4-bit channel-major bit planes** 存储。每个 channel 的前 \(t\) 个 bit-plane 自然就是该 channel 的 \(t\)-bit approximation；每次 query 再根据 variance-weighted channel importance，通过 reverse water-filling 分配 bit budget。因此不同 query、不同 channel 实际读取的 bit 数不同。([arXiv][4])

Qwen3-8B、1M token 下，相比 Double Sparsity/Loki/SparQ r=32 的 136-bit scan，Fathom decode step 的 GPU time **1.67× 更快**；在与 SparQ 68-bit scan 相同 GPU time 下，它还能少读 **18% bytes**，并在 7 组 model/context setting 中 6 组 attention error 更低。真实 coding-agent session 中，读约 **92 bits** 就达到最准确 136-bit scan 的 step agreement。([arXiv][4])

一个非常重要的 caveat 是：**如果 index 已经完整 resident 在 GPU memory，Fathom 并不更快。**

所以它不是一种普适的新 KV quantizer，而是一种：

> **offloaded KV 场景下的自适应 memory-bandwidth scheduler。**

我认为这条思路很值得关注。未来低比特 KV 不一定是“这个 layer FP4、那个 layer FP8”，还可能变成：

**这个 query 对这个 channel 只值得读 2 bit，而另一个 channel 值得读 4 bit。**

## 4. Triton：一个 broadcast NVFP4 global scale 被错误地“向量化读取”，最高能拖慢 kernel 82.9%

**状态：[Draft PR，尚未合入]｜#11701｜9 月 11 日**

[Triton #11701](https://github.com/triton-lang/triton/pull/11701?utm_source=chatgpt.com)

Triton persistent NVFP4 matmul 即使面对**完全广播、所有 pointer 都相同的 tensor global scale**，仍然会构造一整组 row/column scale vector。某个 4-warp 配置中，这导致每线程 **504 bytes local memory allocation**，出现 spill。新方案确认 tensor scale 真正 broadcast 后，只加载一个 scalar；ragged、gather、varying scale 路径仍保留原 vector logic。([GitHub][5])

GB300 固定 tuning config 上：

| M×N×K          |    Before |     After |        改善 |
| -------------- | --------: | --------: | --------: |
| 2048×4096×4096 | 21.344 μs | 16.679 μs | **28.0%** |
| 4096×4096×4096 | 37.121 μs | 28.620 μs | **29.7%** |
| 8192×4096×256  | 36.090 μs | 19.730 μs | **82.9%** |
| 8192×4096×4096 | 66.012 μs | 54.184 μs | **21.8%** |

local memory 从 **504 B/thread → 0**，register 仍为 255/thread。默认 autotuned config 原本没有 spill，因此收益只有 **0.8%～5.7%**。([GitHub][5])

这件事对 compiler/kernel 设计特别有启发：低比特 GEMM 的 scale 不应该笼统地当成 tensor。它可能实际属于：

* tensor-global scalar；
* per-row；
* per-column；
* per-block；
* ragged/fiber scale。

把它们统一成 vector abstraction，有时会直接制造寄存器/local-memory 压力。

## 5. Triton 3.8 正在补一个 E8M0 correctness bug：scale byte=0 不是“数值 0”

**状态：[Open backport PR，尚未合入 release/3.8]｜#11737｜9 月 12 日**

[Triton #11737](https://github.com/triton-lang/triton/pull/11737?utm_source=chatgpt.com)

Triton 3.8.0 的 `tl.dot_scaled` 对 E8M0 scale 有一个很危险的 corner case：**E8M0 byte 0 被错误解释成数值 0，而正确值是 \(2^{-127}\)**；另外某些 BF16-subnormal scale 也会错误 round 成 zero。结果是 `minimum_scale` 和 `zero_scale` test 中所有元素都错误。([GitHub][6])

同一个 backport 还修复 scaled-dot `k_pack` forwarding：当左侧是 unscaled BF16、右侧是 MN-packed FP4 时，错误 flag 可以让 `AccelerateMatmul` 直接失败。当前 PR 仍是 **Open**，因此如果依赖 Triton 3.8 wheel 跑 MXFP*/E8M0 scaled dot，这一项值得检查版本和 backport 状态，而不能当成已经正式修复。([GitHub][6])

这和最近几周看到的 UE8M0/E4M3 scale bug 是同一个大趋势：**“scale=0”到底表示真实 0、最小 exponent、还是某个 sentinel，已经成为低比特 ABI 的一部分。**

## 6. NVIDIA Transformer Engine：MXFP8 已经进入大规模 MoE 训练的 grouped GEMM + EP 通信栈

**状态：[NVIDIA 官方工程实践]｜9 月 14 日**

[NVIDIA：Accelerating Dropless MoE Training in JAX with Transformer Engine](https://developer.nvidia.com/blog/accelerating-dropless-moe-training-in-jax-with-nvidia-transformer-engine/?utm_source=chatgpt.com)

NVIDIA 展示了 JAX/MaxText + Transformer Engine 上的 DeepSeek-V3 671B dropless MoE 训练。核心低比特组件包括 **group-aware MXFP8 quantization** 与 **MXFP8 grouped GEMM**，再配合 NCCL Expert Parallel dispatch/combine、token deduplication、host activation offload 和 XLA multistream collectives。Grouped GEMM 底层使用 cuBLAS/cuBLASLt，并在 Blackwell 上利用 MXFP8 block scaling。([NVIDIA Developer][7])

GB300 上，起始 stack 只有约 **103 TFLOPS/GPU**，通信占累计 kernel time 的 84%；完整优化后达到 **1,068 TFLOPS/GPU，10.4×**，在 1024 GPU 相对 128-GPU baseline 仍保持约 **97% scaling efficiency**。必须强调，**10.4× 是整套训练栈共同的结果，不是 MXFP8 单项收益**。([NVIDIA Developer][7])

NVIDIA 还明确写出下一步包括 **NVFP4、quantization fused with GEMM、A2A overlap**。虽然这是训练工作，但对推理非常有直接启示：我们最近在 serving 侧看到的：

`send-side MXFP8 quant`
→ `A2A`
→ `receiver direct consume`

正在训练端出现完全相同的设计收敛。低比特格式正在成为**计算格式 + 通信格式**。

## 7. SGLang：量化 draft 模型可以完全正常运行，却让 speculative acceptance 静默掉到接近 0

**状态：[Open Issue]｜#39087｜9 月 11 日**

[SGLang #39087](https://github.com/sgl-project/sglang/issues/39087?utm_source=chatgpt.com)

这个案例我建议以后把它加入所有 speculative-decoding 量化评测。

Qwen3.8-27B INT4 AutoRound target 搭配 DFlash2 draft。BF16 draft 正常；换成 W4A16 compressed-tensors draft 后，模型**能成功加载、能输出、没有异常和 warning**，但 mean accepted tokens 从约 **3.7 降到接近 1.0**，接近 100% draft rejection，最终 decode 反而比不用 drafter 更慢。([GitHub][8])

这说明 speculative model 的低比特评价标准不能只是：

`draft perplexity`
或
`draft GSM8K accuracy`

真正应该测：

**target-draft token agreement / acceptance length distribution / verification overhead / net TPOT。**

即使量化 draft 单独看“质量不错”，少量 logit/ranking perturbation 也可能正好打到 speculative acceptance 的敏感点。

## 8. FlashInfer 已出现真正的 NVFP4 Attention，但目前只是 SM103 experimental prepared kernel

**状态：[Open PR / Experimental]｜#5283｜9 月 17 日**

[FlashInfer NVFP4 Attention #5283](https://github.com/flashinfer-ai/flashinfer/pull/5283?utm_source=chatgpt.com)

新接口：

`prepare_nvfp4_attention(q, k, v, out, backend="cake")`

会预先把连续 BF16 Q/K/V 量化为 NVFP4，返回一个 allocation-free runner，runner 内执行 **QK → softmax → PV**，最终输出 BF16。第一版仅支持 **SM103/B300、noncausal、head_dim=128、sequence length 为 512 的倍数**。([GitHub][9])

三个 B300 shape 上，导出的 runner latency 与原 Cake source 基本 parity：约在 0.3% 以内；但这里必须特别注意 benchmark methodology——**Q/K/V quantization 与 preparation 完全不在计时范围内**。所以它证明的是：

> prepared NVFP4 attention compute kernel 已经可做到 source parity，

而不是：

> 动态 serving 中“BF16→NVFP4→attention”整体已经比 FP8/BF16 更快。([GitHub][9])

不过从研究方向看，它很重要：前几个月 NVFP4 更多集中在 weight/MoE/KV storage；现在开始出现真正 **Q/K/V NVFP4 attention arithmetic** 的公开实现。

## 9. “LLM Inference in a Flash”：低比特推理开始面向 SSD 内部计算与写耐久性，而不只是 GPU HBM

**状态：[论文]｜arXiv:2609.16161｜9 月 14 日**

[LLM Inference in a Flash!](https://arxiv.org/abs/2609.16161?utm_source=chatgpt.com)

这项工作面向 **Compute-in-Flash / near-SSD compute**。这种设备容量大，但高精度 floating-point 很弱，而且 SSD write endurance 成为 KV Cache 的新约束，因此作者采用**端到端 integer-only quantization**，避免昂贵的 floating-point compute。([arXiv][10])

KV Cache 则不只是 INT4/FP4，而采用 dictionary-based sparse coding：每个 KV vector 被表示成少量静态 dictionary vectors 的线性组合，从而降低每 token 动态写入。Llama-3.1-8B 和 Qwen-2.5-7B 上，作者报告整体 accuracy degradation 有限，同时**动态 KV cache traffic 减少 15×**。([arXiv][10])

它很值得关注，因为它改变了 KV compression 的目标函数：

GPU 上通常优化：

`HBM bytes/token`

而 Compute-in-Flash 需要优化：

`写入 bytes/token + SSD endurance + 浮点计算能力 + 数据搬移`

低比特算法最终一定会越来越 hardware-specific。

# B. 框架、kernel 与量化工具动态

## vLLM

本周没有新的正式 tagged release，但 ROCm/Blackwell 上有几个很值得关注的低比特问题。

GLM-5.3-Flash 的 open PR **#56607** 修正 indexer query FP8 quantization：原实现把 dtype 硬编码成 NVIDIA 风格 `float8_e4m3fn`，absmax 固定 448；在 ROCm gfx942 上进入 AITER FlyDSL FP8 MQA 时，需要 FN→FNUZ 转换，甚至可在 kernel emission 阶段 crash。PR 改为使用 `current_platform.fp8_dtype()` 和对应 platform FP8 max。它目前仍是 **Open PR**，不是正式 fix。([GitHub][11])

DeepSeek-V4.1-Flash 的 ROCm RFC #56506 更值得做性能分析。8×MI355X、TP4、MXFP4 MoE + DSpark MTP 中，并发 1→32 时 per-GPU output 从 **8.97→117.35 tok/s**，但 ITL 只从 25.6→47.7 ms；single-stream decode step 竟有 **14,020 个 kernel launches**，其中每层约 85% 来自一个 4×4 mHC bookkeeping block。一个已合入的 seam 优化把单个 seam 从 141 launches 降到 4，方向性实验 ITL 25.58→6.89 ms，不过作者明确指出 workload 变化，不能直接把它宣传成严格 3.7× E2E gain。([GitHub][12])

这非常能说明一个问题：**即使 MoE 已经 MXFP4，真正瓶颈仍可能完全不在低比特 GEMM。** 如果 framework 每 token 有上万次小 kernel dispatch，再优化 FP4 Tensor Core 几个百分点意义有限。

另一个 open issue #56832 则暴露了 speculative + heterogeneous quantization 的 execution-contract 问题：`--moe-backend marlin` 本来是给 NVFP4 target experts 的，却被传播到了**未量化的 BF16 MTP draft MoE**，导致启动直接报错。没有 MTP 时 Marlin 约 108–111 tok/s；使用 auto backend 能启动 MTP，但 target 改用 FlashInfer CUTLASS 后 batch-1 约 95–97 tok/s，即慢约 14%。([GitHub][13])

结论是未来 backend selection 不能只按“model-level quantization config”决定，而必须是：

**target/draft × layer/module × quantization contract × backend**。

## SGLang

本周同样没有新 tagged release，main/issue 侧主要是 scale/backend compatibility。

SM120 的 open issue **#39063** 显示，grouped FP8 DeepGEMM weight preparation 因 guard 直接在 SM120 返回 False，导致 blockwise FP8 MoE weight scale 没有从普通 FP32 scale requant 成 DeepGEMM 要求的 **UE8M0 power-of-two scale**，最终触发 DeepGEMM scale-layout assertion。手工调用已有 requant helper 后即可正常输出 finite results。([GitHub][14])

DeepSeek-V4.1-Flash MXFP4 routed experts 的 **#39226** 更进一步：`--moe-runner-backend deep_gemm` 在参数解析阶段被接受，甚至能把模型加载完，直到 CUDA Graph capture 时才因为 MXFP4 expert scale layout 与 DeepGEMM consumer contract 不匹配而 assert。([GitHub][15])

这两个 bug 放在一起非常典型：

> **backend“支持 FP4/FP8”并不意味着支持当前模型的具体 scale representation。**

SGLang 的 backend resolver 以后需要判断的不仅是 dtype，还包括 scale format/layout，而不是等 kernel launch 后才暴露。

# C. 本周新论文

除了 BITCOS、Fathom 和 Compute-in-Flash，我认为还有三篇值得记录。

### JustFit：MXFP4 大模型 + 压缩 KV + state lifetime management，在 24 GiB Mac 上跑到 200K context

JustFit 是一个 MLX runtime，组合 **KVExec compressed KV、PhaseSwap component residency、StateTrans state-preserving transition**，这些机制与 weight quantization 相互独立。Qwen3.8-27B **MXFP4** 在 24 GiB M4 Pro 上完成了 196,608 input + 16,384 output，也就是 **212,992 positions**，相比 mlx-vlm 30,720 提高 **6.93×**；32K input / 64 output 的测试达到 19.11 tok/s。([arXiv][20])

它的核心价值不是一种新的 4-bit quantizer，而是进一步证明：**weight compression 只有与 KV/state lifecycle 一起优化，才能真正转化成可服务 context capacity。**

### GLM-5.3-Flash + LMCache：cache transfer 成功并不代表模型 state 真正恢复正确

这篇验证工作使用 `GLM-5.3-Flash-NVFP4`、vLLM + LMCache、TP4。作者发现 external cache transfer 可以全部成功，但 hybrid model 的 scheduler token accounting 与恢复 state 差一个 token，导致生成不一致。使用 strict-prefix lookup 后，9 个长度 workload 的生成一致性从 **34/36→36/36**；120-request serial test 保持 output equality，CPU reload 相对 cold recompute 的 TTFT 降低 **46–64%**，total request time 降低 **1.9–7.0%**。([arXiv][21])

它提醒我们：随着低比特 KV、conv/Mamba state、sparse indexer state 共存，“cache correctness”已经不是简单 byte-perfect reload，而是**所有 state family 与 scheduler position 必须同时一致**。

### 如何真正测量“4 bit 有没伤质量”

9 月 16 日的一篇 measurement paper 提出 calibrated LLM-judge methodology。该实验中，4-bit model 在英文与中文 prose 上与 16-bit baseline 的差异落在 **±0.3 point 的测量分辨率内**；3-bit 开始出现更明显的 domain-dependent loss：英文 -0.5、中文 -0.9、多步数学 -1.1，而且同一 quantizer 在 Meta 和 Alibaba 模型上的 degradation 分别能到 -1.8 与 -0.7。([arXiv][22])

这里最有价值的不是“4 bit 一定无损”，而恰恰相反：

> **量化误差高度依赖 model family 和 task domain，不能用单个 GSM8K/PPL 数字代表整体质量。**

# D. 厂商技术博客与硬件 / 软件栈

本周最有技术价值的官方厂商文章就是 NVIDIA 的 **JAX + Transformer Engine dropless MoE**。它把 MXFP8 quantization、grouped GEMM、Expert Parallel communication 和 host offload 放在一个完整系统里，非常接近未来低比特推理的演化方向。([NVIDIA Developer][7])

尤其值得注意的是 NVIDIA 明确把下一步列为：

**NVFP4 + quantization/GEMM fusion + A2A overlap。**

换句话说，无论训练还是推理，优化正在收敛到相同的数据流：

`高精度 activation`
→ `在 producer 端量化`
→ `以低比特格式通信`
→ `consumer 直接进入 block-scaled GEMM`

而不是：

`量化 → 通信 → 反量化 → 再量化 → GEMM`。([NVIDIA Developer][7])

本统计窗口内没有找到 AMD、Intel、Meta、Google、Microsoft、OpenAI、DeepSeek、Moonshot、智谱、阿里或字节发布同等级、同时包含新低比特机制和可核验 benchmark 的官方文章。因此不为了凑厂商数量重复旧内容。

# E. 我建议下一步在 B200 / Blackwell 上优先做的实验

## 1. 最高优先级：做一套“Scale ABI Poison Test”

本周 Triton、SGLang 又连续说明 scale 是最危险的 correctness 区域。建议固定加入：

```text
E8M0 raw byte = 0 / 1 / 127 / 254
E4M3 global scale = 0.125 / 0.37 / 1 / 3.7 / 8
global scale broadcast vs per-row/per-column
FP8 E4M3FN vs E4M3FNUZ
UE8M0 power-of-two vs arbitrary FP32 scale
M/N/K = 对齐与非对齐
CUDA Graph / eager
```

同时 dump：

`quant value bytes`
`scale bytes`
`scale strides/layout`
`local-memory spill`
`consumer alpha/global-scale direction`

Triton #11701 最值得你在 B200 上复现：虽然作者验证用的是 GB300，但问题本质是 **scale vectorization → local spill**，B200 上完全值得检查不同 tile/warp 配置是否存在同类 pathology。([GitHub][5])

## 2. 在 B200 上系统比较 NVFP4 W4A16 与 W4A4，而不是预设 W4A4 一定更快

FlashInfer #5279 正在把：

`BF16 activation × NVFP4 weight`

做成 B200 CuTeDSL MegaMoE。([GitHub][16])

建议和现有：

`NVFP4 activation × NVFP4 weight`

用相同 expert shape 做：

`M={1,2,4,8,16,32,64,128,256}`

分别记录：

* activation quant cost；
* scale generation；
* MoE FC1/FC2；
* top-k reduction；
* Tensor Core utilization；
* end-to-end expert latency。

很可能 small-M decode 下，**少做一次 FP4 activation quant 的 W4A16**仍然会存在竞争区间。

## 3. 把“speculative quantization acceptance”纳入固定 benchmark

至少比较：

```text
BF16 draft
FP8 draft
W4A16 / INT4 draft
```

不要只记录 draft accuracy，要记录：

* mean accepted length；
* P50/P90 accepted length；
* verifier tokens/request；
* drafter latency；
* verifier latency；
* net TPOT；
* 与 no-spec baseline 的速度比。

SGLang #39087 已经证明，量化 drafter 可以完全不 crash，却把 accepted length 从约 3.7 打到约 1.0。([GitHub][8])

对 MTP/EAGLE/DFlash，这个指标比普通 task accuracy 更直接。

## 4. 做一个“host-offloaded K index 的 bit-depth crossover”实验

Fathom 特别适合长上下文 sparse attention。建议在 B200 上模拟：

```text
GPU-resident 4-bit K index
CPU-resident 4-bit K index
固定读 4bit
固定读 2bit
query-adaptive 1~4bit
```

记录：

`H2D bytes/decode step`
`index scan latency`
`top-k recall`
`final attention error`
`TPOT`

重点找出**什么时候 index offload 后 bandwidth 成为主瓶颈**。论文明确说 GPU-resident index 下 Fathom 不更快，所以 crossover 本身比“复现 1.67×”更有研究价值。([arXiv][4])

## 5. 用 Nsight 专门统计“scale traffic”

Rubin #5300 不能直接在 B200 复现，因为所有优化严格 gated 到 SM107；但它提示了一个在 B200 上同样值得测的指标：

**每生成一个 scale byte，到底触碰了多少 cache line / DRAM bytes。** ([GitHub][1])

可以分别分析：

`linear scale layout`
`8×4`
`128×4 / swizzled`

以及你的 NVFP4/MXFP8 producer，记录：

* L1/L2 sectors；
* global store bytes；
* theoretical scale payload；
* 实际 memory transaction amplification。

以后评价量化 kernel，我建议增加：

$$
\text{Scale Write Amplification}
=
\frac{\text{实际内存事务字节}}{\text{逻辑 scale 字节}}
$$

这个指标可能比只看 GB/s 更容易解释为什么相同 FP4 算法在不同 layout 下性能差很多。

## 6. GLM/DeepSeek 一类模型要继续坚持“先看 launch，再优化 low-bit GEMM”

vLLM 的 DSV4.1 MI355X trace 是一个很好的警示：single-stream decode 一步 **14,020 次 kernel launches**，85% per-layer launch 来自很小的 mHC bookkeeping；MoE/FFN 已经高度 fused，反而不是主要 launch 来源。([GitHub][12])

你在 B200 做 GLM-5.x/NVFP4 优化时，我建议每次先把时间拆成：

```text
attention / sparse indexer
FP4/MXFP8 MoE
norm + quant
KV read/write
scheduler / tiny tensor ops
communication
sampling
```

如果 FP4 GEMM 只占十几个百分点，再把它快 20% 也只有几个百分点 E2E；反而几十个甚至几百个“小而碎”的 producer/metadata kernel 可能更值得融合。

# 本周三个最重要的判断

**第一，scale 已经从“量化参数”正式变成低比特系统里的 performance object。** Rubin 在优化 scale cache-line locality，Triton 在优化 scale scalar/vector lowering，SGLang 在处理 FP32→UE8M0 consumer contract。以后分析 NVFP4/MXFP4/MXFP8，除了 value format，我会继续重点追踪 **scale dtype、granularity、physical layout 和 movement cost**。([GitHub][1])

**第二，KV precision 正从“静态 bit-width”走向“按查询动态分配 bandwidth”。** 前几周看到的是按 layer、按 token、按 KV subspace 选择 FP4/FP8/BF16；这周 Fathom进一步做到按**query × channel**决定读多少 bit。最终优化目标越来越像 memory hierarchy scheduling，而不是传统 quantization。([arXiv][4])

**第三，2 bit 以下的时代不会只是“发明更小的数据类型”。** BITCOS 表明真正有效的超低比特部署必须利用真实 weight distribution、zero sparsity、packing 和 unpack kernel；Compute-in-Flash 又说明硬件如果换成 SSD-near-memory，量化目标甚至会变成 write endurance 与动态 KV traffic。低比特越来越像一种完整的 **algorithm–format–layout–hardware co-design**。([arXiv][3])

如果只挑本周**三个最值得继续跟踪**的项目，我会排：**① FlashInfer #5300 的 SM107 scale-layout quantization；② Fathom 的 per-query bit-plane KV/index scan；③ SGLang #39087 揭示的 quantized speculative-draft acceptance collapse。** 第一个关系 Rubin 下一代低比特数据通路，第二个关系百万 token 下真正的 memory bottleneck，第三个则直接影响现在越来越普遍的 MTP/EAGLE/DFlash 推理体系。
