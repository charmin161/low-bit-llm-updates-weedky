# 低比特大模型推理周报｜2026-08-28—2026-09-04

这一周我认为真正值得记住的主线有三条。第一，**低比特 KV Cache 正从“GPU HBM 里的 dtype”升级为跨 HBM、CPU DRAM 甚至未来跨节点传输的系统级存储格式**；AMD 把 4-bit TurboQuant KV 与 LMCache 分层缓存结合起来，是目前这一方向最完整的一次公开工程验证。第二，**scale 正逐渐成为与 quantized value 同等重要的一等数据**：H-Scale直接优化 NVFP4 的 group scale，ModelOpt 开始保证 QAT/QAD 学到的 FP8 KV scale 在 checkpoint export 中不被破坏，vLLM 的 Inkling FP8 KV 实验也再次证明 scale 没校准会直接损伤任务精度。第三，Blackwell 上 decode 的 kernel 分工正在进一步细化，FlashInfer 同一周同时合入了通用的 block-scaled small-M CuTe DSL GEMM，以及 SM103 上高度 shape-specialized 的 NVFP4 warp-decode MoE。([ROCm Blog][1])

状态仍按 **[已合入 main] / [RFC] / [论文] / [厂商工程实践] / [开放问题]** 区分，不把实验性 PR 或论文数字写成正式框架能力。

# A. 本周最重要的 8 项低比特进展

## 1. AMD：4-bit KV 第一次真正跨出 HBM，成为 HBM→DRAM 的分层缓存格式

**状态：[AMD 官方工程实践]，8 月 28 日**

[AMD：4-bit KV Caching in LMCache](https://rocm.blogs.amd.com/software-tools-optimization/4bit-KV-LMcache/README.html)

这是本周我认为**系统意义最大**的一项工作。

AMD 在 **2×MI355X、ROCm 7.2.3、vLLM V1、MiniMax-M2.5 FP8 MoE、TP2** 上，把 TurboQuant 4-bit KV 接进 LMCache。它不是全层统一 4 bit：前 2 层和后 2 层保持 BF16，中间 58 层使用 packed 4-bit KV；LMCache connector 能识别这两种物理 layout，把它们作为不同 transfer group 在 HBM 和 CPU DRAM 之间原样搬运。4-bit KV 每 token footprint 约缩小 **3.76×**。([ROCm Blog][1])

在相同 HBM + 128 GB DRAM budget 下，TurboQuant 让 HBM resident KV 从 **201,280 tokens 增至 648,064 tokens，约 3.2×**；LMCache hit rate 从 **75.2% → 86.8%**；20 分钟 agentic trace 中完成请求从 **189 → 385，约 2.0× goodput**，p95 TTFT 从 **140 s → 53 s，约降低 2.6×**；总 KV 搬运量从 **3.30 TB → 1.94 TB，减少约 1.7×**。工作负载来自 739 条匿名 Claude Code session，约 100K context、12K warm prefix、32–64 并发。([ROCm Blog][1])

更值得关注的是：CPU DRAM 并不会 dequant 后保存，**4-bit packed representation 本身就是 tiering format**；HBM→DRAM→HBM round-trip 是 byte-exact。MiniMax-M2.5 上 4-bit 与 BF16 的三个 benchmark 均在约 1 point 内，RULER 16K/64K/128K 中 DRAM reload 与 HBM resident 的差异 ≤0.4 point。([ROCm Blog][1])

这和传统“4-bit KV 能让 HBM 多放几倍 token”的意义不同。现在低比特同时影响：

`HBM capacity → cache hit rate → PCIe/CPU DRAM bytes → re-prefill frequency → TTFT → goodput`

所以今后评价 KV quantization，我认为**不能再只报 memory compression ratio 和 attention kernel latency**，还应该报 cache hit、tier traffic 和 recompute avoidance。

## 2. Qwen Team 的 H-Scale：NVFP4 的下一个优化对象不是 FP4 code，而是每 16 个 weight 的 FP8 scale

**状态：[论文]，arXiv:2608.28113，8 月 28 日提交**

[H-Scale 论文](https://arxiv.org/abs/2608.28113)

H-Scale 非常符合最近 NVFP4 软件栈的变化方向。NVFP4 每 **16 个 E2M1 value** 共用一个 **E4M3 local scale**，再乘 tensor-level FP32 global scale；因此，一个大模型会产生海量 local scale。H-Scale 的核心观点是：过去 GPTQ/AWQ 等方法主要在优化 weight code 或 weight reconstruction，但对 NVFP4 而言，**“这 16 个数到底选哪个硬件可表示 FP8 scale”本身就是一个很大的优化空间**。([arXiv][2])

它不使用普通 weight MSE，而从 calibration activation \(X\) 得到 `diag(XᵀX)`，用这个 diagonal-Hessian proxy 衡量不同 input channel 对 layer output error 的重要性。然后对每个 1×16 group，在 baseline scale 附近枚举一小段 **E4M3 合法 scale grid**，挑 Hessian-weighted reconstruction error 最小的 scale。FP4 code、group size、实际 Tensor Core format 都不改变，因此**推理端严格零额外开销**。([arXiv][2])

Qwen3-30A3-Thinking 的论文表 1 很有代表性：

| NVFP4 PTQ |   原始 Avg. | + H-Scale |
| --------- | --------: | --------: |
| RTN       |     80.03 | **80.68** |
| 4over6    |     79.99 | **80.49** |
| ArcQuant  |     79.73 | **80.46** |
| GPTQ      |     80.01 | **81.22** |
| GPTAQ     |     80.21 | **80.71** |
| MR-GPTQ   |     79.67 | **80.41** |
| BF16      | **81.06** |         — |

注意 GPTQ+H-Scale 的 81.22 只是该论文 benchmark average 略高于 BF16 81.06，不能理解成“NVFP4 比 BF16 更准确”；更合理的解读是，**scale refinement 可以回收相当一部分本来归因于 FP4 value grid 的误差**。([arXiv][2])

在 Qwen3-4B 的 layer reconstruction 实验里，H-Scale 相比 Min-Max 平均降低 **32.5% activation loss**，约获得昂贵连续 scale oracle 40.8% 改善中的八成，而单纯优化 weight MSE 的 scale search 只降低 12.6% activation loss。([arXiv][2])

我认为这篇论文值得持续跟踪。**NVFP4 的竞争已经从“有没有 group=16”进入“同样 group=16、同样 E2M1，到底怎么决定 E4M3 scale”这一层。**

## 3. SGLang + AITER：DeepSeek-V4 FP4 sparse indexer 从 132 B/token 压到 68 B/token

**状态：[已合入 SGLang main]，PR #37353，9 月 2 日**

[SGLang PR #37353](https://github.com/sgl-project/sglang/pull/37353)

这项工作针对 AMD gfx95x 的 DeepSeek-V4 sparse indexer。AITER 使用拆开的 FP4 cache representation：

`64-byte FP4 payload + 4-byte UE8M0 scale`

因此每个 compressed token 从旧实现的 **132 bytes 降到 68 bytes**。同时 Q/K 路径中的 RoPE、Hadamard、FP4 quantization、cache write、paged-MQA logits 以及 EAGLE MTP scheduling 都接到 AITER 原生路径。([GitHub][3])

68K input / 200 output、并发 48 + HiCache 的 Agentic benchmark：

* throughput/GPU：20,251 → **21,430 tok/s，+5.8%**
* median TTFT：887 → **838 ms，-5.5%**
* GPU KV capacity：10.22M → **11.01M tokens，+7.7%**
* GPU cache hit：91.3% → **93.0%**

并发 16、不使用 HiCache 时 throughput +2.6%、TTFT -7.6%。GSM8K 1319 条为 0.948；另一套 inferenceX exact-match 为约 0.967–0.968。([GitHub][3])

这和 AMD 上面的 LMCache 工作实际上是同一方向的两个尺度：一个压缩**sparse indexer KV representation**，另一个让压缩后的 KV 能继续进入 **hierarchical storage**。

## 4. FlashInfer：为 Blackwell small-M decode 统一 NVFP4 / MXFP4 / MXFP8 / FP8 的 CuTe DSL low-latency GEMM

**状态：[已合入 main]，PR #4685，9 月 3 日**

[FlashInfer PR #4685](https://github.com/flashinfer-ai/flashinfer/pull/4685)

FlashInfer 新增 `cutedsl_low_latency` tactic，接入 `mm_fp4`、`mm_mxfp8`、`mm_fp8` 和 block-scaled TGV GEMM。目标非常明确：**SM100/SM103、M≤8 的 decode / 极小 batch GEMM**。当前 NVFP4 要求 K 是 64 的倍数；MXFP4、MXFP8 和 static FP8 要求 K 是 128 的倍数。([GitHub][4])

它值得关注的地方不是某个 headline speedup——PR 没给一个统一的端到端性能数字——而是**同一个 small-M dispatcher 已经开始横跨多个 block-scaled format**，覆盖：

* NVFP4
* MXFP4
* MXFP8
* FP8×FP8
* mixed FP8×FP4
* split-K
* bias / output scaling
* GPT-OSS-120B 与 DeepSeek-V3 shape。([GitHub][4])

这说明 backend selection 的决策树正逐渐变成：

`architecture × M/N/K × weight format × activation format × scale layout`

而不是简单的：

`FP4 → 某个 FP4 kernel`

这对你在 B200 上非常值得测，因为 M≤8 正好对应大量低并发 decode / MoE expert GEMM。

## 5. FlashInfer 又加了一个更激进的 SM103 NVFP4 warp-decode MoE：高度专用仍然能赢通用 kernel

**状态：[已合入 main]，PR #4855，9 月 3 日；仅 SM103/B300**

[FlashInfer PR #4855](https://github.com/flashinfer-ai/flashinfer/pull/4855)

和前一个“统一 low-latency GEMM”相反，这项工作走的是**极度 specialization**。

它只支持两个 calibrated fused-MoE geometry：

* H=2048，I=512，E=512，top-k=10，T=1–32
* H=2048，I=1536，E=60，top-k=4，T=1–32

而且要求**精确 compute capability 10.3**，目前不进入默认 backend selection。([GitHub][5])

B300 上完整 64 个 T/geometry case 全部快于官方 TRT-LLM comparison：

* E512：几何平均 **1.0592×**
* E60：几何平均 **1.1757×**
* 总体：**1.1160×**
* E60、T=3 的最好 case 达 **1.3102×**。([GitHub][5])

这里很能说明一个现实问题：

> 即使 CuTe DSL generic block-scaled GEMM 已经越来越好，**非常小的 token 数和固定 MoE geometry 仍然给 hand/generated specialized warp kernel 留出了明显空间。**

所以未来 runtime 很可能不是“通用 kernel 替代所有专用 kernel”，而是 autotuner 在两者之间做 tactic selection。

## 6. vLLM 修复一个非常典型的概念错误：checkpoint 写着 NVFP4，并不意味着它是 W4A4

**状态：[已合入 main]，PR #54427，8 月 30 日**

[vLLM PR #54427](https://github.com/vllm-project/vllm/pull/54427)

有些 ModelOpt checkpoint 的配置是：

`quant_algo = NVFP4`

但所有 `input_activations = null`。

也就是说，它实际上只是：

**NVFP4 weight-only → W4A16**

而不是真正：

**NVFP4 weight + NVFP4 activation → W4A4**。([GitHub][6])

此前 vLLM 看到 `NVFP4` 就可能送进 W4A4 MoE path，而该路径需要 activation input scale。如果 scale 没初始化，会把 dequant alpha 乘成 0，导致整个 expert 权重有效 scale 清零。更危险的是它**不一定 crash**，而可能静默生成重复/垃圾输出，且 allocator 差异会让问题呈现 hardware-dependent。([GitHub][6])

现在 weight-only NVFP4 会被解析为：

`W4A16_NVFP4`

然后走 **Marlin**；真正带 activation quantization 的 NVFP4 checkpoint 才保留 W4A4 path。([GitHub][6])

这一项我认为特别值得记住：

> **“NVFP4”描述的是 representation；W4A4 / W4A16 描述的是 execution contract。两者不能混为一谈。**

这和你之前在 Nemotron 上看到的 W4A16 NVFP4 → Marlin 路径，本质上是同一套语义问题进一步被框架显式化。

## 7. vLLM Inkling FP8 KV：B200 上 1M context capacity +73%，但 unity scale 让 MATH-500 掉 4.2 point

**状态：[RFC，尚未合入]，Issue #54704，9 月 1 日**

[vLLM Inkling FP8 KV RFC](https://github.com/vllm-project/vllm/issues/54704)

这是本周**最值得你在 B200 上关注的 KV Cache RFC**。

Inkling 有 full attention + sliding-window + conv state，因此 FP8 并不会简单让“总 cache 直接减半”。Attention KV bytes 在 TP4 下确实从 **7168 → 3584 bytes/token/rank**，但 conv-state admission reserve 仍固定 BF16。于是实际 pool gain 强烈依赖 serving 参数：

| max context | max batched tokens | FP8 pool gain |
| ----------- | -----------------: | ------------: |
| 8K          |                16K |         +5.9% |
| 131K        |                16K |         +8.6% |
| 131K        |                 2K |        +28.1% |
| 1M          |                16K |        +27.9% |
| 1M          |                 2K |    **+73.1%** |

真实 1M boot 测到 **+73.06%**，最大 1M concurrent request 数由 **14 → 24**；1M cold-prefill TTFT 是 BF16 的 **0.84×**；64K decode 的 attention kernel 最好约 **1.45×**。([GitHub][7])

但真正重要的是 accuracy caveat。

如果 K/V scale 全部使用 unity=1：

**MATH-500：41.9 → 37.7，-4.2 point。**

定位结果显示 **K 从未 clipping，问题全在 V**：global-attention layer 中最大 \(|V|=1272\)，而 E4M3 finite max 是 448。对每层校准 v_scale 后，MATH-500 回升到 **39.7**，大约追回一半损失，而且其他任务没有明显代价。([GitHub][7])

这个结果和 H-Scale 指向了非常相似的结论：

> **低比特格式能不能工作，很多时候不是“FP8/FP4 bit 数够不够”，而是 scale 是否跟真实 tensor distribution 对齐。**

尤其 KV Cache 不能再把 `scale=1.0` 当作一个无害默认值。

## 8. HyQuant：低比特 KV 不再按 layer 决定精度，而开始按“token 重要性”决定精度

**状态：[论文]，arXiv:2608.27875，8 月 28 日**

[HyQuant 论文](https://arxiv.org/abs/2608.27875)

HyQuant 和上周 MiniMax-M3 那种“某些 layer FP4、某些 layer FP8”不同，它把 mixed precision 下沉到**同一个 attention layer 内的 token 维度**。

作者观察到少于约 **5% 的 vertical-line tokens** 持续获得很高 attention mass，也是 aggressive 4-bit quantization 误差最敏感的位置。因此它：

`vertical-line tokens + local sliding window → FP16/BF16`

其余绝大部分：

`→ K4V4`

decode 时低比特 KV 直接在 attention kernel 里 on-the-fly dequant，不 materialize 一份完整高精度 KV。([arXiv][8])

H100 上，decode attention kernel 随 context 增长：

* 1K：1.32×
* 2K：2.40×
* 4K：3.06×
* 8K：3.36×
* 16K：3.52×
* 32K：**3.58×**

端到端 decode 则是更现实的 **1.04×–1.17×**。([arXiv][8])

Qwen3-32B LongBench average：

* FA2 full precision：48.61
* KVTuner 4bit：48.22
* HyQuant K4V4 + top-5% FP：**48.46**

它的额外 token-importance tracking 占总 runtime 约 3–5%，5% full-precision vertical tokens 则让非-window KV 相比 strict 4-bit 多约 15% memory。([arXiv][8])

所以它并不是“免费 4 bit”，而是提出了一个很有价值的 Pareto 点：

**绝大多数 token 极低 bit + 极少数语义关键 token 高精度。**

# B. 框架 / Kernel / 量化工具更新

## vLLM

本周最重要的 merged 项目就是 **#54427 weight-only NVFP4 → W4A16/Marlin**；Inkling FP8 KV 则仍是 RFC，不应视作当前 stable 功能。另一个值得监控的开放问题是 **#54945（9 月 2 日）**：FlashInfer CUTLASS NVFP4 MoE 使用 `use_fused_finalize=True` 时，相同 temperature=0 请求可能得到不同 logits；关闭 fused finalize 后 bit-stable，单次测试代价约 +3.6% decode latency。问题目前仍 open，因此需要把它当作 determinism/reproducibility 风险，而不是正式修复。([GitHub][9])

vLLM v0.28.0 是 **8 月 26 日**发布，已经在本期统计窗口之外，所以我没有重复把该 release 内容算作“本周更新”。

## SGLang

本周主线是 AMD DeepSeek-V4 FP4 indexer #37353。另外 #37331 在 9 月 2 日进一步 harden MXFP8 group quant dispatch，包括 compiler memory barrier 和 gfx95 原生路径；更偏 correctness / release-hardening，没有值得单独夸大的 E2E 性能数字。

另外需要加入风险列表：**#37559** 报告 B300 上 MXFP8×FP4/W4A8 MegaMoE、`sgl-deep-gemm 0.1.7` 在持续运行后出现 `CUDA_ERROR_ILLEGAL_ADDRESS`，当前仍是开放问题。([GitHub][10])

## FlashInfer

本周低比特 kernel 侧最活跃：

* #4685：SM100/103 通用 low-latency block-scaled GEMM；
* #4855：SM103 NVFP4 specialized warp-decode MoE。

这两个 PR 同周出现其实很有代表性：FlashInfer 同时在发展**format-unified autotuned kernel**和**model/shape-specialized kernel**，两条路线并没有互相替代。([GitHub][4])

## AITER / ROCm

AITER PR **#5081 于 9 月 2 日合入**，把 SiTUv2 activation 和 per-token FP8 quantization 融成一个 kernel：

`BF16 gate/up → SiTUv2 → FP8 + scale`

而不再 materialize BF16 activation 再单独 quant。TP8 decode trace 中，被替换的两个 kernel 从 **301.1 μs/step → 140.3 μs，局部 2.15×**；但这部分只占总 GPU 时间约 1%，所以作者明确**没有宣称 E2E throughput 提升**。([GitHub][11])

这再次说明 producer fusion 的规律：

`activation → quantization → scale generation`

最好是一条流水线，但 micro-kernel 2× 不意味着 serving 2×。

## ModelOpt

ModelOpt 当前值得注意的是**main 已经开始为 0.47 准备低比特功能，但截至本期不是正式 0.47 release**。

8 月 31 日合入 #2287，为 DeepSeek-V4-Pro-0813 增加公开的 **NVFP4 routed-experts-only PTQ recipe**：routed experts 使用 group=16 NVFP4，shared expert、attention、MTP、lm_head 等保持 source precision。一个非常重要的 caveat 是，真正影响该 checkpoint calibration 的 `--calib_seq` 仍然是 CLI 参数；默认 512 并不足以覆盖长上下文 activation range，因此 YAML recipe 本身不是完整 reproduction recipe。([GitHub][12])

9 月 2 日合入 #2298 则更有长期意义：Megatron QAT/QAD 中学到的 **FP8 KV Cache scale**，过去 export 时会被最低 clamp 到 1.0，现在可以选择保留小于 1.0 的 learned scale；默认行为仍保持 clamp 以兼容旧流程。([GitHub][13])

这项和 Inkling RFC 放在一起看非常重要：

> **scale calibration 还不够，scale 必须从训练/PTQ → checkpoint → loader → kernel 一路不丢失。**

## TensorRT-LLM / Rubin

TensorRT-LLM #18369 于 **9 月 2 日**合入 Rubin **SM107 CuTe DSL foundation**，包括 SM107 persistent BF16 GEMM/BMM 和 BF16/FP16 MoE building blocks。需要强调：**这次本身主要还是 BF16 foundation，不是“Rubin NVFP4 kernel 已经完成”**；PR 明确引用后续的 SM107 quantized dense / DeepSeek-V4 kernel #18546。([GitHub][14])

因此我把它视为 Rubin 软件 bring-up 的信号，而不是本周新增成熟低比特能力。

## TorchAO / Transformer Engine / llm-compressor / cuBLASLt

严格限定 8 月 28 日—9 月 4 日后，我没有发现这些项目中有一项**足够实质、且有明确 inference 性能/正确性数据的新能力**值得放进 A 区凑数。Transformer Engine 有 MXFP8 grouped activation/MLP 相关 kernel 工作，但仍更偏训练侧；llm-compressor 新增了 MR-GPTQ/QuIP + NVFP4A16 example，属于 recipe/integration 而不是新推理 kernel。

# C. 本周值得读的论文

除了前面的 **H-Scale** 和 **HyQuant**，我再推荐两篇。

### Strong Drafts Need Compact Memories

**arXiv:2608.30252，8 月 31 日；EMNLP 2026 Findings。**

[论文原文](https://arxiv.org/abs/2608.30252)

它不是压缩 target model 的 KV，而只压缩**speculative draft model 的 KV memory**。Target verifier 仍保留完整 KV，并继续使用标准 accept/reject，因此最终输出仍保持 speculative decoding 的 lossless guarantee。Llama 3.1 8B/70B、最长 32K prefix 下，draft-side memory 减少 **>70%**，相对 autoregressive decoding 最高分别 **2.08× / 3.33×**。([arXiv][15])

这个设计思想值得注意：

**不是所有模型组件都值得承担 quantization risk。**

可以让 draft 承担 aggressive compression，而 target 保留完整精度作为最终 correctness anchor。

### Faithfulness Is Not Free

**arXiv:2608.30996，8 月 31 日。**

[论文原文](https://arxiv.org/abs/2608.30996)

作者研究 offline RAG KV Cache 的 INT8/INT4。Qwen2.5-7B-Instruct 上，INT8 在 accuracy 和 faithfulness 上基本 near-lossless；INT4 不仅 accuracy 下降，而且在**仍然答对的问题中，超过 90% 的 faithfulness change 是负向的**，并且 retrieval 越 noisy、retrieved chunks 越多，问题越严重。([arXiv][16])

这提醒了一个很容易被普通 benchmark 漏掉的问题：

> **量化后的回答“答案对了”，不意味着模型仍然是根据给定上下文得到这个答案。**

对 agent/RAG 的低比特 KV Cache，未来最好加入 grounding / entailment / faithfulness 类评测，而不仅是 GSM8K 或 NIAH。

# D. 厂商技术博客与硬件/软件栈

AMD 8 月 28 日的 LMCache 博客是本周最重要的厂商文章，因为它真正把 **4-bit KV、CPU DRAM tier、cache hit、TTFT 和 goodput**放到了同一个系统实验里，而不是只给 kernel microbenchmark。([ROCm Blog][1])

NVIDIA 本周则在 9 月 2 日发布了 speculative decoding co-design 技术博客。虽然主题不纯粹是量化，但其中直接给出 ModelOpt 的 EAGLE-3、DFlash、DSpark workflow，并明确展示 Nemotron 3.5 Lightning 的 drafter 可以继续量化成 **FP8 或 NVFP4**。([NVIDIA Developer][17])

博客另一个和低比特很相关的系统观点是：speculation 会把 verification GEMM 的有效 M 从 \(M\) 提升到 \(M(1+D)\)。NVIDIA 的代表性 6144×6144 expert GEMM 中，D=7 时达到 compute-bound 所需 batch 约只有 D=0 的 **1/8**。因此低 bit + speculative decoding 并不是两个完全独立的优化：speculation 会改变小-M GEMM 的 operating point，也会影响你应该选择 Marlin、low-latency CuTe DSL 还是更大 tile 的 Tensor Core kernel。([NVIDIA Developer][17])

本周没有看到 NVIDIA 正式发布新的 PTX low-bit ISA revision、NVFP4 datatype 或 Rubin adaptive-compression instruction contract。**SM107 的公开增量主要还是 TensorRT-LLM / CuTe DSL bring-up 层面**，不建议从这些 PR 反推出尚未披露的 Rubin 硬件细节。([GitHub][14])

# E. 我建议你下一步在 B200 / Blackwell 上优先验证的项目

### 1. 最高优先级：复现 Inkling RFC 中的“FP8 KV scale calibration”

不要只跑：

`BF16 KV vs FP8 KV`

而要明确分三个 arm：

```text
BF16 KV
FP8 KV + unity k/v scale
FP8 KV + calibrated per-layer k/v scale
```

重点抓每层 K/V `amax`、clipping ratio、scale、MATH-500/GSM8K/长上下文 retrieval，以及 64K/128K/1M 的 KV capacity 和 attention latency。特别值得验证论文/RFC 中的现象：**K 可能完全不 clipping，而 V 才是真正 precision bottleneck。** ([GitHub][7])

### 2. FlashInfer #4685：在 B200 上做真正的 small-M backend crossover 图

建议用你实际 GLM / MiniMax / Nemotron layer shape，统一 sweep：

`M={1,2,4,8}`

对比：

`cutedsl_low_latency`
vs `FlashInfer standard CuTeDSL`
vs `CUTLASS`
vs `Marlin（W4A16 时）`

并分别测试 NVFP4、MXFP4、MXFP8、FP8。PR 现在已经把这些 format 放到了同一个 tactic system，很适合直接观察**format 是否还重要，还是 M/N/K 和 scale layout 已经成为更主要的 selector**。([GitHub][4])

### 3. 专门做一次“NVFP4 representation ≠ execution precision”实验

制作两个几乎相同的 checkpoint：

```text
A. NVFP4 weight-only
   → W4A16
   → Marlin

B. NVFP4 weight + activation quant
   → W4A4
   → FP4 Tensor Core backend
```

显式打印 vLLM 最终选择的 quant method / MoE backend，并对比 weight layout、activation scale、kernel 和性能。#54427 正好把这条语义边界正式编码进 vLLM，非常适合作为你的 NVFP4 backend 调研 baseline。([GitHub][6])

### 4. H-Scale × Four-Over-Six × plain NVFP4 做一次 calibration ablation

同一份 BF16 checkpoint：

```text
Max / RTN
H-Scale
4over6
4over6 + H-Scale
GPTQ
GPTQ + H-Scale
```

最终全部输出**完全相同的 native NVFP4 hardware format**，所以 serving kernel 和吞吐理论上不变；真正变量只在离线 scale selection 和最终 accuracy。这是一个很干净的实验，可以回答：

> “在 NVFP4 group=16 已经很细的情况下，scale search 到底还能值多少精度？”

论文数据表明这一空间仍然不小。([arXiv][2])

### 5. 把 AMD 的“4-bit KV + LMCache”思想搬到 Blackwell 上

不必机械复刻 TurboQuant。更有价值的是比较：

```text
BF16 KV + HBM
FP8 KV + HBM
低比特 KV + HBM/CPU tier
FP8/低比特 KV + LMCache
```

真正记录：

`HBM resident tokens`
`L1/L2 hit rate`
`D2H/H2D bytes`
`re-prefill tokens`
`p95 TTFT`
`goodput`

AMD 的结果说明：当工作集超出 HBM 时，**“少搬数据 + 少重新 prefill”带来的收益可能远高于 attention kernel 本身的差距**。([ROCm Blog][1])

### 6. ModelOpt FP8 KV scale export 做一次 checkpoint lifecycle 检查

如果后续做 FP8 KV 的 QAD/QAT，我建议检查：

`训练得到 scale`
→ `Megatron checkpoint`
→ `ModelOpt export`
→ `HF checkpoint`
→ `vLLM/TRT-LLM loader`
→ `kernel`

每一步的 scale 是否 bitwise/数值一致。尤其比较 export clamp 开/关。#2298 的存在本身就说明，**scale 在训练时学对了，但 export 时被“善意修正”为 1.0，也足以把低比特优化破坏掉。** ([GitHub][13])

如果之后能拿到 B300，FlashInfer #4855 的 **SM103 NVFP4 warp-decode**会是额外的高优先级实验；但它精确限定 SM103，不能用你目前的 B200 结果直接外推。([GitHub][5])

## 本周三个最重要的趋势判断

**第一，KV quantization 已经从“压显存”进入“压整个 memory hierarchy”。** AMD 的 4-bit + LMCache 是目前最明确的证据：低比特最终影响的是 HBM、DRAM、传输、cache miss 和重新 prefill 的总成本，而不只是 bytes/token。([ROCm Blog][1])

**第二，scale engineering 正在成为低比特推理的核心课题。** H-Scale 在优化 NVFP4 weight scale，ModelOpt 在保护训练出来的 FP8 KV scale，Inkling RFC 又证明 unity v_scale 会真实损失 MATH-500。现在可以把低比特 tensor 更准确地理解成：

`quantized values + scale values + scale layout + scale lifecycle`

这四者共同定义真正的数据格式。([arXiv][2])

**第三，未来最优 precision 很可能既不是“按模型统一”，也不是“按 layer 统一”。** 现在已经同时看到按 module 混合 NVFP4/FP8、按 token 保留少量 BF16、按 storage/compute 使用不同 precision，以及 draft/target 使用不同 KV precision。真正的优化问题正在变成：

**哪个数据，在什么阶段，以什么 bit 数，存在哪里，并由哪个 kernel 消费。**

这条线我认为比继续追一个孤立的“新 4-bit datatype”更值得长期关注。([arXiv][8])
