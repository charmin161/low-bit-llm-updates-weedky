# 低比特推理周报｜2026-08-14—2026-08-21

这一周我认为最值得关注的变化，并不是又出现了某个新的“4 bit 格式”，而是**低比特正在从单个 GEMM 的 datatype 优化，进一步扩展到完整推理数据流**：MoE Expert Parallel 的通信 payload 直接低比特化、不同模块使用不同量化格式、scale metadata 布局本身进入 kernel 优化范围、checkpoint 在加载时跨 NVFP4/MXFP4 转换，以及长上下文 KV Cache 开始暴露“不是量化误差而是地址空间”这一类系统问题。与此同时，FlashInfer 已经开始正式合入 Rubin SM107 的 CuTe DSL kernel 支持。([GitHub][1])

下面我把状态明确分成：**[正式发布]、[已合入 main]、[论文]、[仍属 bring-up/验证阶段]**，避免把 PR、benchmark 和正式能力混在一起。

---

## A. 本周最重要的 9 项低比特进展

### 1. [正式发布] ModelOpt 0.46：NVFP4 的重点开始从“量不量”转向“scale 怎么选”

NVIDIA Model Optimizer **0.46 于 8 月 17 日发布**。这是本周低比特 PTQ/QAD 工具层最重要的一次更新。新增内容包括 LSQ/Dual-LSQ、NVFP4 `local_hessian` scale search 的 Triton 加速、Four-Over-Six、AutoQuantize recipe、固定 activation scale、MiniMax-M3 混合 MXFP8/NVFP4 export 等。([GitHub][2])

其中我认为有三个点值得特别理解。

第一，`local_hessian` 不再用 Python 对每个 NVFP4 block 慢慢 sweep scale，而是增加 fused Triton fast path。官方给出的单个 **8192×4096 weight** 上速度约为 Python reference 的 **34×**，同时 FP16/FP32 weight 与 reference bit-exact；dense 和 fused-MoE expert 都适用。换句话说，**复杂 scale optimization 开始变得足够便宜，可以真正进入大模型 PTQ workflow**。([GitHub][2])

第二，新增 **NVFP4 Four-Over-Six（4/6）**。这里需要避免一个容易误解的点：它**不是“某个 block 用 4 bit、另一个 block 用 6 bit”**。数据仍然是 NVFP4 E2M1；算法是在每个 block 上通过 MSE 决定采用 **M=6 还是 M=4 的动态范围**，这个选择最终折叠进 FP8 block scale。`four_over_six=true` 时为了给 M=4 留 headroom，scale normalization 使用 256，而不是普通路径中的 448。当前支持 `mtq.quantize` 和 HF/Megatron export，但 **不支持 `mtq.compress`**，因为 compress 后无法保留每个 block 的 M=4/M=6 选择。([GitHub][2])

第三，AutoQuantize 现在可以把 candidate format、effective bits、cost model、具体 module search space 全部写进 recipe。ModelOpt 对 block-scaled NVFP4 的 effective-bit accounting 给到 **4.5 bit**，这意味着后续“一个模型一个量化格式”的思路正在进一步变成**按模块搜索最优 quant recipe**。同一版本还给出了 MiniMax-M3 的示例：语言模型主体 MXFP8，routed experts 再使用 MSE-calibrated NVFP4。([GitHub][2])

**我的判断：** 低比特 PTQ 的优化重心正在从 datatype 本身转向 **scale selection / calibration policy / module-wise format search**。这对于 NVFP4 尤其重要，因为 NVFP4 比 MXFP4 有更细的 block=16 和 FP8 scale，本身就给 calibration 留出了更大的优化空间。

### 2. [已合入 main] FlashInfer：B200 MoE EP 开始直接传 MXFP8，而不是传 BF16 后再量化

FlashInfer PR **#4529 于 8 月 20 日合入**，增加 SM100 的：

`MXFP8 activation × MXFP4 weight → BF16`

CuTe DSL split-MoE backend。真正重要的并不只是 W4A8 GEMM，而是它同时修改了 **Expert Parallel 通信路径**。([GitHub][1])

原来的典型数据流是：

`BF16 hidden state → NCCL EP dispatch → 每个目标 rank 再量化 MXFP8`

现在可以变成：

`源 rank 一次量化 MXFP8 → packed MXFP8 + UE8M0 scale → NCCL EP → 直接进入 W4A8 kernel`

每个 token row 的 payload 是 `[H]` FP8 数据加 `[H/32]` UE8M0 scale bytes。PR 给出的估计是，和传 BF16 再在目标 rank 量化相比，**wire cost 大约减半**。支持的 NCCL-EP low-latency hidden width 当前限制为 `{2048,2560,4096,5120,6144,7168,8192}`，top-k 最大 8；测试跑在 **8×B200**。([GitHub][1])

这件事非常重要，因为以前说 W4A8，主要关注的是：

`HBM → Tensor Core`

现在已经开始优化：

`GPU A → NVLink/NVSwitch → GPU B → Tensor Core`

也就是说，**低比特正在成为 distributed communication format**。

对于大 MoE，未来 FP4/MXFP8/NVFP4 的价值不能只看 TFLOPS 和 weight footprint，还必须把 EP bytes/token 算进去。Rubin Wide EP 时代这一点可能更重要。

### 3. [已合入 main] vLLM：DeepSeek-V4 把 FP8 shared expert 也塞进 FP4 MegaMoE persistent kernel

vLLM PR **#53040 于 8 月 20 日合入**。DeepSeek-V4 原来的路径是：

`routed FP4 experts MegaMoE`
→ `shared FP8 gate/up`
→ `shared FP8 down`
→ `add`

也就是说即使 routed expert 已经是 persistent MegaMoE kernel，shared expert 还是串行走额外 GEMM。现在 SM100 DeepGEMM MegaMoE 可以把**FP8 shared expert 与 FP4 routed experts 一起调度**，同时保留 checkpoint 中 shared expert 的 FP8 权重，最后一次 BF16 store。([GitHub][3])

B200/TP8/EP 的实测非常有价值：

* 128 input / 256 output、BS1：**130.02 → 149.50 tok/s，+14.98%**；
* TPOT：7.653 → 6.643 ms，**-13.19%**；
* ITL：-13.32%；
* 但是短输入 BS1 的 TTFT：17.32 → 18.17 ms，反而 **+4.93%**；
* 1024/128 BS1：throughput **+13.68%**，TTFT -11.77%；
* 1024/128、C64：3415.45 → 3737.98 tok/s，**+9.44%**；
* 8192/32、C16：output throughput **+6.55%**。([GitHub][3])

这项更新给出了一个很明确的工程信号：

> **混合精度不一定意味着必须分开执行。**

FP4 routed expert 和 FP8 shared expert 可以保留不同存储格式，但在一个 persistent execution schedule 里融合。

这比简单讨论“FP4 与 FP8 哪个好”更接近未来真正的推理 kernel。

### 4. [已合入 main] SGLang：一个 UE8M0 scale layout 就能省掉 DeepSeek-V4 每步 61 次 kernel launch

SGLang PR **#34277 于 8 月 17 日合入**。

之前 DSV4 activation quantizer 输出 FP32 scale；DeepGEMM 的 `fp8_einsum` 需要 TMA-aligned packed UE8M0，于是每次调用前都得执行：

`transpose_and_pack_fp32_into_ue8m0`

一个 BS1 decode step 中一共 **61 次 launch，约 114 μs**。([GitHub][4])

现在 activation quant kernel **直接产生 DeepGEMM 所需要的 TMA-aligned UE8M0 int32 layout**，中间转换全部消失。

8×B200、DeepSeek-V4-Pro、TP8、ISL16/OSL1024：

* BS1：+1.21% throughput；
* BS16：+2.38%；
* BS32：**+3.59%**；
* 几何平均 decode latency -1.42%，throughput +1.44%。([GitHub][4])

这项优化看起来百分比不大，但我认为它对理解低比特 kernel 很重要。

低比特的数据流事实上是：

`Tensor`
→ `quant value`
→ `scale`
→ `scale layout conversion`
→ `descriptor`
→ `GEMM`

只优化 quant value 而忽略 scale metadata，经常会留下大量 launch、transpose、packing 开销。

**scale 不是旁路元数据，它已经是低比特执行数据流的一部分。**

### 5. [已合入 main] TensorRT-LLM：Kimi K3 把 routing 和 MXFP8 activation quant 合成一个 CUDA kernel

TensorRT-LLM PR **#17059 于 8 月 19 日合入**，针对 Kimi K3 的 **896 experts / top-16** routing。

原先 decode 中：

`routing`
→ `routing-scale conversion`
→ `BF16 → MXFP8 quant`
→ `MoE`

是多个 launch。

现在 routing 与 MXFP8 quantization 在一个 CUDA grid 中并行执行，支持最多 64 token，面向 TRTLLMGen 的 W4A8 **MXFP4 weight + MXFP8 activation** backend。([GitHub][5])

B200、M=5 microbenchmark：

**35.8 μs → 22.4 μs，约 1.60×。**

M={1,5,64} 做了 parity。([GitHub][5])

不过这里有一个必须保留的 caveat：这些 benchmark 是 scheduler rebase **之前**测的；PR 自己明确建议后续再做 ExternalComm scheduler 下的 end-to-end 验证，而且 SM103/SM107 尚未实际验证。([GitHub][5])

这与 SGLang 那项 UE8M0 优化实际上指向同一个趋势：

**decode 小 M 场景越来越不是 Tensor Core FLOPS 不够，而是 launch / quant / routing / metadata plumbing 太多。**

### 6. [已合入 main] FlashInfer：SM100 原生 NVFP4 W4A16 CuTe DSL GEMM，和 Marlin 出现明显 shape crossover

FlashInfer PR **#4466 于 8 月 18 日合入**，增加 SM100/SM103 CuTe DSL：

`BF16 activation × NVFP4 weight → BF16`

也就是 **W4A16**，而不是 W4A4。([GitHub][6])

它与 Marlin 的对比特别值得看。

在 `N=6656, K=19968`：

* M=1：CuTe DSL 36.11 μs，Marlin NVFP4 29.17 μs，**Marlin 更快**；
* M=32：36.54 vs 45.09 μs，CuTe DSL **1.23×**；
* M=128：43.90 vs 106.01 μs，**2.41×**；
* M=512：125.71 vs 382.09 μs，**3.04×**；
* M=2048：408.66 vs 1491.82 μs，**3.65×**。([GitHub][6])

另一组 `N=19968,K=6656` 中，甚至 M=1 CuTe DSL 就已有约 1.16× 优势。([GitHub][6])

所以不能简单说：

> “NVFP4 W4A16 以后用 CuTe DSL，不用 Marlin。”

正确结论是：

> **backend selection 必须进入 shape-aware dispatch。**

尤其 decoder-only serving 的实际 M 会随着 batch/concurrency 波动，一个固定 backend 很容易在一部分区间选错。

同时这也再次强调：**NVFP4 是 weight representation，不代表 execution 必然是 W4A4。**

### 7. [已合入 main] SGLang/AMD：NVFP4 checkpoint 可以在加载时直接转换成 MXFP4

SGLang PR **#29328 于 8 月 15 日合入**，增加：

`--quantization quark_mxfp4`

可以加载 NVIDIA ModelOpt 或 AMD Quark 的 **NVFP4 checkpoint**，在 GPU 上：

`NVFP4 dequant → MXFP4 requant`

而且只在加载阶段做一次；最终模型只保留 MXFP4，并不会常驻一个完整 BF16 copy。目标硬件包括 **MI355X**。([GitHub][7])

这是很有现实意义的“checkpoint portability”路线：

**训练/发布格式 ≠ 最终硬件执行格式。**

MI355X GSM8K 数据：

* MiniMax-M2.7：0.918 → 0.920；
* GLM-5.1：0.952 → **0.928**；
* Kimi-K2.6：0.939 → 0.930；
* Qwen3.5-397B-A17B：0.954 → 0.945；
* DeepSeek-R1：0.958 → 0.950。([GitHub][7])

所以它不是“无损格式翻译”。特别是 **GLM-5.1 只恢复 97.5% benchmark score**，需要谨慎。

工程意义却很大：未来模型仓库完全可能只维护少量 canonical low-bit checkpoint，然后针对 NVIDIA/AMD 等执行平台在 load-time 转换成本机最合适的数据格式。

### 8. [已合入 main] AITER：长上下文 FP8 KV Cache 出错，原因竟然不是 FP8 精度，而是 32-bit 地址溢出

AITER PR **#4774 于 8 月 16 日合入**。这是我本周认为最值得所有做低比特 KV Cache 的人认真看的 correctness case。([GitHub][8])

`deepgemm_fp8_paged_mqa_logits` 使用 32-bit offset 做：

`block_id × stride`

生产配置 stride 是 **1,002,240 byte**，于是：

* physical block 2142：2,146,798,080，正常；
* block 2143：2,147,800,320，超过 INT32_MAX；
* 从这里开始 logits **静默变成 0**。([GitHub][8])

KV 内容本身没有损坏，但 sparse indexer 得到一堆相同的 0，top-k 最终退化为近似随机 tie-breaking，于是长上下文 retrieval 崩掉。

最终把实际执行路径的 gather 从 32-bit `buffer_load` 换成支持 64-bit pointer vector 的 `gl.load`。8×MI325X：

* 2k：45.3 → 45.3 tok/s；
* 12k：45.9 → 45.8；
* 30k：45.5 → 45.9；

几乎没有性能损失。1M max-model-len 的 DSV4-Flash 以及 600k DSV4-Pro/518k needle retrieval 均通过验证。([GitHub][8])

但 PR 也明确说明：**还有 25 个类似的 32-bit site 位于当前配置没有执行到的路径中，没有盲目修改。** ([GitHub][8])

这个案例说明：

> KV Cache 进入百 GB 甚至 TB 级逻辑地址空间后，正确性问题已经不能只盯 quant/dequant error；pointer width、page layout、stride、allocator placement 都会成为低比特 attention 的一部分。

### 9. [已合入 main，但属于 bring-up] FlashInfer 正式开始 Rubin SM107 CuTe DSL kernel plumbing

FlashInfer PR **#4526 于 8 月 19 日合入**，增加 **Rubin SM107** 的 CuTe DSL kernel 支持，以及 Blackwell/Rubin batched FP8 GEMM 基础实现。([GitHub][9])

包括：

* SM100/SM103 persistent batched FP8 GEMM；
* SM107 Rubin variant；
* Rubin fused-MoE CuTe DSL 相关 infrastructure；
* architecture-aware dispatch/autotune。([GitHub][9])

SM107 path 的软件条件目前是：

**CUDA 13.4 + CuTe DSL ≥ 4.8**。

如果 CuTe DSL 较老，FlashInfer 其他功能仍可工作，只是 SM107 kernel 不启用。([GitHub][9])

这里我暂时不会把它解读成“Rubin kernel 已成熟”或拿它推断 Rubin 性能。它更准确的状态是：

> **软件 bring-up 已经进入上游 main，真正的 Rubin architecture-specific kernel 分支开始公开出现。**

这对跟踪 Rubin adaptive compression 很有价值，因为后续 SM107 的 block-scaled GEMM、MoE contract、CuTe DSL primitive 变化会提供比 marketing material 更具体的软件线索。

## B. vLLM / SGLang / TensorRT-LLM / FlashInfer 等框架侧总结

### vLLM

本周最实质的低比特性能更新就是 **#53040 DeepSeek-V4 FP4 routed + FP8 shared expert MegaMoE fusion**。它说明 vLLM 的 DeepSeek-V4 Blackwell 路径正在从“每个组件各自调用最优 kernel”转向**整层 MoE execution schedule fusion**。([GitHub][3])

另外值得注意的是低比特 emulation/correctness 仍在补强；这类工作对研究 MXFP6/MXFP4 fake quant 特别重要，因为 fake quant 如果漏掉 activation QDQ，结果甚至可能“看起来精度很好”，实际上根本没有模拟真正硬件路径。

### SGLang

本周有三条非常清晰的线：

**第一条：scale/data layout 优化。** DeepSeek-V4 直接输出 TMA-packed UE8M0，去掉 61 个 scale-pack launches。([GitHub][4])

**第二条：跨格式加载。** NVFP4 checkpoint → AMD MXFP4 load-time requantization 已正式合入。([GitHub][7])

**第三条：checkpoint 开始真正 heterogeneous。** Kimi-K3 的官方 ModelOpt NVFP4 checkpoint 实际并不是“全模型 NVFP4”：routed experts 是 **NVFP4 + SiTU**，部分 attention projection 是 **FP8_PB_WO、128×128 block scale**。SGLang PR #35077 于 8 月 19 日合入对应支持，并在 8×GB300、TP8 下跑到 GSM8K-200 **197/200=98.5%**；这个 PR没有性能数据，定位是 correctness/checkpoint compatibility。([GitHub][10])

这个例子非常典型。以后看到模型名：

`XXX-NVFP4`

不能再默认：

`所有 Linear = NVFP4 W4A4`

而应该先看 quantization config，判断：

**哪个模块是什么格式、activation scheme 是什么、scale block 多大、到底由哪个 kernel 执行。**

### TensorRT-LLM

本周最值得看的就是 Kimi K3 **routing + MXFP8 quant fusion**。它继续强化了 TRTLLMGen 对小-M decode 的 specialization。([GitHub][5])

### FlashInfer

FlashInfer 是本周低比特 kernel 侧更新最密集的项目：

* SM100 **MXFP8×MXFP4 MoE + low-bit EP payload**；
* SM100 **NVFP4 W4A16 CuTe DSL GEMM**；
* Rubin **SM107 CuTe DSL bring-up**。([GitHub][1])

从这些 PR 可以看出来，FlashInfer 已经明显不只是“attention library”，而是在向 **serving kernel/runtime substrate** 扩展：GEMM、MoE、quantization、EP communication、autotune 都逐渐进入同一体系。

# C. 本周新论文

## 1. ExactMoE：把“低比特 MoE”用于 expert-bank residency，而不是只追求 Tensor Core FLOPS

论文 **Every Expert Counts: ExactMoE for Memory-Efficient W4A16 Inference** 于 **8 月 15 日提交 arXiv**。([arXiv][11])

它只把 routed experts 做 **symmetric group-128 W4A16**，而且直接以 kernel-native **MARLIN format** 放在 pinned host memory；GPU 上维护 expert slot cache，只有需要的 expert resident 在 GPU。Router、attention、embedding、norm 和 LM head 都保持 BF16。([arXiv][11])

OLMoE-1B-7B-Instruct、单张 NVIDIA L4：

* 16-slot：reserved GPU memory **14.168 → 1.836 GiB，-87.04%**；
* 保留 BF16 decode throughput 的 **81.85%**；
* full-resident 64-slot W4：31.923 tok/s；
* BF16：21.662 tok/s；
* zero-shot normalized accuracy：70.3534% vs 70.8996%，保留 **99.23%**；
* fused grouped W4 相比 sequential W4 reference：**1.97×**。([arXiv][11])

它和 NVFP4/MXFP4 W4A4 路线的目标并不一样。

NVFP4 W4A4 更像：

> 减 HBM bandwidth + 提 Tensor Core compute density。

ExactMoE 更像：

> **把数百个 expert 的 residency / PCIe transfer 问题变成可以管理的 cache hierarchy。**

对于“大量 experts，但每 token 只用少数 expert”的模型，这种设计很有意义。

## 2. TileMix：Attention 不再按整个 tensor 选精度，而是按 score tile 选 FP16 或 INT8

**TileMix: Tile-Centric Mixed-Precision Attention for LLM Inference Acceleration** 于 **8 月 18 日提交 arXiv**。([arXiv][12])

它的核心不是 sparse attention，而是保持**完整 dense connectivity**，把 attention score matrix 切成 hardware-aligned tile group，然后用 bitmask 决定：

`这个 tile → FP16 score compute`

还是：

`这个 tile → INT8 score compute`

两个 precision path 最后共享同一套 online softmax state。支持 GQA、variable length 和 **INT8 KV Cache**。([arXiv][12])

论文在 A100 上用 LLaMA/Qwen/Vicuna、LongEval/LV-Eval 做评测，声称相比 uniform INT8 能恢复一部分长上下文质量，同时优于 FP16 prefill throughput；摘要没有给出一个统一的 headline speedup，因此这里不人为拼一个数字。([arXiv][12])

这个工作的概念价值比较大：

过去 mixed precision 常常是：

`layer A = FP8`
`layer B = BF16`

或者：

`tensor A = INT8`
`tensor B = FP16`

TileMix 把它进一步细化成：

> **同一个 attention matrix 内，不同空间 tile 用不同 precision。**

如果这种思路未来迁移到 Blackwell/Rubin，更有意思的可能不是 FP16/INT8，而是 **FP8/FP4、dense/compressed** 的 tile-level routing。这部分目前属于我的技术推断，不是论文已经验证的结论。([arXiv][12])

# E. 我建议下一步在 B200 / Blackwell 上优先测试的 6 项

### 1. FlashInfer #4529：直接测“低比特通信”，不要只测 GEMM

建议构造两条路径：

`BF16 NCCL dispatch → remote MXFP8 quant → MXFP4 MoE`

对比：

`source MXFP8 quant → MXFP8+UE8M0 packed NCCL dispatch → MXFP4 MoE`

重点测：

* NCCL bytes/token；
* dispatch latency；
* quant latency；
* MoE kernel latency；
* top-k=1/2/4/8；
* H=4096/6144/7168；
* C=1/8/32/64/128。

我认为这是本周**最值得在 B200 上实测**的 PR，因为它直接关系到未来 Wide EP 下低比特是不是能够同时节省 compute、HBM 和 inter-GPU bandwidth。([GitHub][1])

### 2. vLLM #53040：重点追短请求 TTFT 的 +4.93% regression

不要只复现 +15% decode throughput。

建议分别跑：

* 128/256、BS1；
* 1024/128、BS1；
* 1024/128、C64；
* 8192/32、C16。

然后 Nsight 看 shared expert fusion 之后 persistent kernel 的 launch、occupancy、shared-resource scheduling。

尤其要解释：

**为什么 128-token BS1 的 TPOT 显著改善，TTFT 却变差 4.93%。** ([GitHub][3])

这可以帮助判断 MegaMoE fusion 是否存在 setup/dispatch 的 fixed cost。

### 3. FlashInfer #4466：找出 Marlin → CuTe DSL 的实际 M crossover

直接使用真实模型 layer shape，不要只用 synthetic square GEMM。

建议 sweep：

`M={1,2,4,8,16,32,64,128,256,512}`

同时抓：

* effective bandwidth；
* Tensor Core utilization；
* quant/dequant cost；
* kernel launch；
* tactic。

PR 已经说明 crossover 强烈依赖 N/K；这很适合最终做成 runtime backend selector。([GitHub][6])

### 4. SGLang #34277：用 Nsight 验证 scale metadata 是否真正消失

重点不是再验证 +1~3%，而是确认：

`transpose_and_pack_fp32_into_ue8m0`

在 decode trace 中从原来的约 **61 次/step** 消失。

然后继续找其他 NVFP4/MXFP8 kernel 是否仍存在类似：

`scale generate`
→ `scale transpose`
→ `scale repack`
→ `GEMM`

的重复数据流。([GitHub][4])

这可能比继续微调 GEMM tile 更容易拿到端到端收益。

### 5. TensorRT-LLM #17059：在当前 scheduler head 上重新做 E2E

PR 自己已经注明 benchmark 是 scheduler rebase 前的数据。

建议在 B200 上重新做：

`M={1,5,16,32,64}`

并区分：

* route；
* scale conversion；
* MXFP8 quant；
* external comm；
* MoE。

如果 35.8→22.4 μs 的 microkernel 收益最终被 communication/scheduler 吞掉，那么后续优化方向就会完全不同。([GitHub][5])

### 6. ModelOpt 0.46：做一次真正的 NVFP4 calibration ablation

选择一个你已经有稳定 FP4 baseline 的模型，同一份 BF16 weight 分别做：

`plain max`
→ `MSE`
→ `local_hessian`
→ `Four-Over-Six`

统一下游任务和 serving backend，然后同时记录：

* calibration 时间；
* per-block scale distribution；
* saturation ratio；
* PPL；
* GSM8K / LiveCodeBench 等任务；
* export 大小；
* 最终 vLLM/SGLang throughput。

尤其值得比较：

**Four-Over-Six 的 M=4/M=6 block 分布究竟集中在哪些层/专家。**

如果选择具有明显层级规律，就可能进一步启发**module-specific AutoQuantize**甚至模型训练阶段的量化友好设计。([GitHub][2])

---

## 本周三个最重要的趋势判断

**第一，低比特已经开始进入通信层。** FlashInfer 的 MXFP8 NCCL-EP packed dispatch 是非常明确的信号：以后 W4A8/MXFP8 的收益不能只算 GPU GEMM，还应该算整个 EP wire bytes。([GitHub][1])

**第二，“一个 checkpoint = 一个量化格式”的时代正在结束。** Kimi-K3 同时存在 routed-expert NVFP4、SiTU、attention block-FP8；DeepSeek-V4 则正在融合 FP4 routed experts 与 FP8 shared expert。未来真正需要追踪的是 **module × format × activation scheme × backend** 四元组。([GitHub][10])

**第三，低比特性能越来越取决于 datatype 周围的东西。** UE8M0 scale layout、route+quant launch fusion、scale-search 算法、KV page address width，这些本身都不改变“FP4/FP8”这个名字，却能决定数个百分点甚至 correctness。([GitHub][4])

如果只选**两个本周最值得实际动手的方向**，我会排：**① FlashInfer #4529 的 MXFP8 Expert-Parallel 通信压缩；② ModelOpt 0.46 的 NVFP4 Four-Over-Six / local_hessian scale calibration。** 前者关系到未来大规模 MoE 的系统瓶颈，后者关系到 NVFP4 在相同 4-bit hardware format 下还能把多少精度潜力榨出来。
