# 低比特大模型推理周报
## 2026 年 10 月 9 日—10 月 16 日

**统计截至：2026 年 10 月 16 日 08:09（北京时间）**

本周最值得关注的变化有四个。

**第一，FlashInfer 0.7.2 正式发布，B200/B300 开始具备更完整的原生 NVFP4 sparse-MLA decode 路径。** 它不再只是把 KV Cache 压成 FP4 后重新展开，而是直接读取 packed NVFP4 cache，通过 block-scaled MMA 计算 QK，再使用 FP8 MMA 完成 PV。

**第二，低比特通信出现了新的研究方向。** Echo 提出带误差反馈的 4-bit Tensor Parallel All-Reduce，在 A100 上将 1 GB collective 延迟降低到 BF16 NCCL 的约一半。这和此前 MXFP8 Expert Parallel dispatch 不同，涉及真正的跨 GPU 求和与误差累积。

**第三，NVFP4/MXFP4 的精度优化继续从 scale search 向联合 W+A 量化发展。** DualQuant 不需要 calibration activation，仅通过优化权重重建误差，就能得到改善 activation quantization 的通道缩放系数。

**第四，Rubin 的低比特软件栈进入了系统级优化阶段。** 本周 vLLM 正式展示 Rubin locality domains 对 MoE weight loading 的影响，FlashInfer 则把 cuDNN Frost MoE、MXFP8/MXFP4 Expert Parallel 和 FP8/NVFP4 fused GEMM 一起纳入正式版本。

这周的主要版本包括 **FlashInfer v0.7.2、AITER v0.1.25，以及 TensorRT-LLM v1.4.0rc0**。vLLM 和 SGLang 没有新的正式稳定版需要重复介绍。[GitHub](https://github.com/flashinfer-ai/flashinfer/releases)

# A. 本周最重要的 9 项低比特进展

## 1. FlashInfer 0.7.2：B200/B300 原生 NVFP4 Sparse MLA Decode 正式进入 Release

**状态：[正式发布]｜10 月 16 日北京时间凌晨｜FlashInfer v0.7.2**

[FlashInfer 0.7.2 Release](https://github.com/flashinfer-ai/flashinfer/releases)

这是我认为**本周最值得在 B200 上直接验证**的工作。

此前 FP4 KV Cache 的很多实现主要优化存储容量，但计算路径仍可能需要：

`FP4 KV → FP8/BF16 staging → Attention`

FlashInfer 0.7.2 则正式提供了 DeepSeek-V4 sparse MLA 的 native NVFP4 decode。

相关代码最初由 **PR #6103 于 10 月 6 日合入**，本周进入正式发布版本。这里特意区分合入日期与发布时间，避免将上周 PR 重复算作本周新合入。

### 1.1 具体的 NVFP4 KV Cache 结构

新的 sparse MLA cache 使用：

| 数据 | 存储格式 |
|---|---|
| 448 维 NoPE KV | FP4 E2M1 |
| NoPE KV block scale | 每 16 个数使用一个 E4M3 scale |
| 64 维 RoPE K | BF16 |
| 每 token 物理存储 | **384 bytes** |

这个 384 bytes 包括 packed FP4 data、RoPE BF16 数据及 scale/padding。

相比全 BF16 的 512-dimensional latent KV，压缩非常明显。

更重要的是，这条实现没有把整份 latent KV 重新展开为 BF16。

### 1.2 Attention 如何计算？

实际执行过程可以概括为：

```text
Paged NVFP4 KV Cache
        │
        ├─ FP4 NoPE values
        ├─ E4M3 block scales
        └─ BF16 RoPE values
        │
        ▼
Sparse candidate selection
        │
        ▼
QK:
tcgen05 block-scaled MMA
        │
        ▼
FP32 online softmax
        │
        ▼
PV:
FP8 MMA
        │
        ▼
BF16 attention output
```

也就是说，它并不是“Attention 全部使用 FP4”。

实际上采用了：

**QK：FP4 block-scaled MMA**

**PV：FP8 MMA**

**Softmax：FP32**

这和此前 MpFA 论文提出的 QK4PV8 非常相似，不过当前实现针对 DeepSeek-V4 的 sparse MLA 数据布局和访问机制。

### 1.3 支持范围与正确性

目前支持：

- B200 / SM100；
- B300 / SM103；
- NVFP4 paged KV Cache；
- Sparse MLA；
- CUDA Graph replay；
- 单缓存和双缓存候选索引。

作者报告 B200/B300 上共通过 **428 项测试**，覆盖 page layout、sparse indices、mask、sink、CUDA Graph replay 等情况。

调用时需要显式选择：

`kv_cache_format="nvfp4", backend="cake"`

**默认 `backend="auto"` 并没有自动切换到这条路径。**

这是一个很重要的部署细节。

此外，当前还没有充分的完整模型 E2E 数据证明该路径在所有并发和上下文长度下都优于 FP8。

因此现在应该把它视为：

> **原生 NVFP4 sparse MLA 的可用执行路径已经形成，而不是 NVFP4 一定全面快于 FP8。** [GitHub](https://github.com/flashinfer-ai/flashinfer/pull/6103)


### 1.4 我的判断

这项工作最值得关注的是 **storage precision 与 compute precision 的分离**。

未来 MLA/DSA 更可能采用：

`FP4 KV storage`

＋

`FP4 QK compute`

＋

`FP8 PV compute`

而不是强行让所有阶段使用相同数值格式。

这对你目前研究的 GLM 系列 compressed KV、Q/K 混合精度，以及 decode MXFP8/NVFP4 数据路径都有直接参考意义。

## 2. FlashInfer 0.7.2：NVFP4/FP8 GEMM 开始融合 SwiGLU、QKV Norm 和 RoPE

**状态：[正式发布]｜FlashInfer v0.7.2**

同一版本还有一项对 B200 decode 非常有价值的改进。

FlashInfer `prims_ts` 新增：

- `fp8_linear_swiglu`
- `fp4_linear_swiglu`
- `fp8_qkv_qknorm_rope`
- `fp4_qkv_qknorm_rope`

支持 B200、B300 和 Rubin SM107。

其中特别值得关注的是两个 NVFP4 PR：

**#6255：NVFP4 SwiGLU epilogue 支持 TMEM overlap**

**#6286：NVFP4 QKV fusion 支持 TMEM overlap**

[FlashInfer #6255](https://github.com/flashinfer-ai/flashinfer/pull/6255?utm_source=chatgpt.com)  
[FlashInfer #6286](https://github.com/flashinfer-ai/flashinfer/pull/6286?utm_source=chatgpt.com)

### 为什么这件事重要？

传统执行路径可能是：

```text
Low-bit GEMM
    ↓
BF16 intermediate
    ↓
SwiGLU / QK Norm
    ↓
RoPE
    ↓
Quantization
    ↓
下一个 Consumer
```

这些步骤可能包含多次：

- kernel launch；
- BF16 intermediate materialization；
- HBM read/write；
- scale generation；
- output repacking。

现在开始将上述步骤融合到 GEMM epilogue 中。

这与前几周的：

`RMSNorm → FP8 quant fusion`

`SiLU + Mul → NVFP4 quant`

属于同一个趋势，但融合范围进一步扩大到了 attention projection。

### TMEM overlap 的意义

Blackwell Tensor Core GEMM 不仅涉及 HBM/SMEM，也涉及 TMEM accumulator 的读写与消费。

如果 GEMM epilogue 必须等待完整的 accumulator drain，再单独执行下游操作，可能在 decode 小 M 场景产生明显固定成本。

新 tactic 尝试让部分 epilogue 操作与 TMEM 数据处理重叠。

不过这次 release 没有给出足够完整、可直接引用的模型级加速数据。因此我暂时不宣称融合后有固定的 2× 或 3× 收益。

**值得测试的是：这些融合能否真正减少 GLM/MiniMax 类模型每 token 的中间 kernel 和内存往返。** [GitHub](https://github.com/flashinfer-ai/flashinfer/releases)

## 3. Echo：4-bit Tensor Parallel All-Reduce，终于开始系统性处理跨层误差累积

**状态：[论文]｜10 月 9 日｜arXiv:2610.14277**

[Echo 论文原文](https://arxiv.org/abs/2610.14277)

这是我认为本周**最有潜力形成独立研究方向**的低比特工作。

过去低比特通信主要集中在两类场景：

**Expert Parallel：**

`MXFP8 activation → All-to-All → MXFP4 MoE`

这类通信主要负责搬运 token，通常不在通信操作本身执行求和。

**Tensor Parallel：**

`Partial GEMM outputs → All-Reduce → 下一层`

All-Reduce 不只是搬运数据，还必须执行数值求和。

如果直接把 TP 通信从 BF16 压缩到 INT4，可能产生一个很危险的问题：

**每层都会引入新的量化误差，而且这些误差会沿网络深度累积。**

### 3.1 Echo 的核心设计

Echo 使用：

**4-bit integer communication**

＋

**高精度求和**

＋

**双时间尺度误差反馈**。

可以将其理解为：

```text
Layer i partial outputs
        ↓
INT4 Quantization
        ↓
All-Reduce
        ↓
High-precision accumulation
        ↓
Quantization error estimation
        ↓
Error feedback state
        ↓
Layer i+1 compensation
```

与普通 INT4 All-Reduce 相比，它不是把每次 collective 当成独立事件。

而是记录量化误差，并在后续 collective 中补偿。

作者给出的理论分析表明，误差界可以避免随网络深度呈指数式放大。

### 3.2 真实实验结果

测试硬件：**NVIDIA A100**。

| 指标 | Echo 结果 |
|---|---:|
| 1 GB All-Reduce | **2.09× faster than BF16 NCCL** |
| 空闲互联下 TTFT | 最高 **1.16×** |
| 互联拥塞下 TTFT | 最高 **1.44×** |
| 空闲互联下训练 step | 最高 **1.09×** |
| 拥塞下训练 step | 最高 **1.38×** |

Qwen3-8B 在 7 个 benchmark 上，相比 16-bit 通信的平均准确率变化控制在约 **0.4 个百分点以内**。

论文还验证了 10B-token 预训练，最终 loss 与 16-bit 通信相比差距小于约 0.9%。

而且该方法**不需要原生 FP4 Tensor Core**。 [arXiv](https://arxiv.org/abs/2610.14277)


### 3.3 和 MXFP8 Expert Parallel 有什么区别？

两者优化对象不同。

MXFP8 EP：

> 降低 token dispatch/combine 的通信字节数。

Echo：

> 降低 TP All-Reduce 字节数，同时解决低精度求和误差沿层传播的问题。

我认为 Echo 对未来 TP8/TP16 模型尤其有价值。

但有一个重要限制：

**这些结果来自 A100，不能直接推断在 B200 NVLink/NVSwitch 上也有相同收益。**

当互联带宽更高时，INT4 quantization、error feedback 和额外 kernel 的固定成本可能让收益明显减小。

作者目前还没有发布完整代码，论文注明代码将在接收后公开。

## 4. DualQuant：不使用 Calibration Data，也能联合优化 W4A4

**状态：[论文]｜10 月 9 日｜arXiv:2610.13767**

[DualQuant 原文](https://arxiv.org/abs/2610.13767)

这篇是本周我最推荐认真阅读的 FP4 PTQ 论文。

它与此前 Four-Over-Six、H-Scale、OSFP4 有一个明显不同：

**DualQuant 不需要任何 calibration activation。**

### 核心思想

传统 activation-aware quantization 常使用：

`Calibration X`

来确定某些 channel 是否存在 outlier。

例如 SmoothQuant 通过 activation statistic，把一部分 activation 量化难度转移到 weight 上。

DualQuant 观察到：

> 权重某些列的 magnitude 分布，本身就包含可以帮助改善 activation quantization 的信息。

于是通过优化：

**Weight reconstruction MSE**

求解 per-row / per-column 两组缩放系数。

其中 column scale 在改善 weight reconstruction 的同时，也被用于 activation rescaling。

最终得到：

```text
BF16 Weight
     │
     ▼
Dual-scale Optimization
     │
     ├── Weight Rescaling
     │
     └── Activation Rescaling
     │
     ▼
W4A4 Quantization
```

具体求解使用 variable splitting 和 Block Coordinate Descent。

支持：

- INT4；
- MXINT4；
- MXFP4；
- NVFP4。

与依赖真实 activation 的 H-Scale 等方法相比，它的优势是部署准备阶段不需要额外收集 calibration data。

### 实验数据

作者在 Llama 和 Qwen 系列上验证，并在 RTX 4090 上实现了真实 packed W4A4 inference。

Llama-3.1-8B：

| 指标 | 相比 BF16 |
|---|---:|
| 显存占用 | 减少约 **2.51–2.61×** |
| E2E 推理吞吐 | **1.39–2.46×** |
| Quantization overhead | 总 GPU 时间的 **4.3–6.1%** |

需要注意，RTX 4090 没有 B200 的原生 FP4 Tensor Core，因此这组 benchmark 不能直接当成 native NVFP4 W4A4 的性能数字。

真正值得关注的是算法本身：

**不通过 calibration activation，是否也能接近 activation-aware PTQ 的精度？** [arXiv](https://arxiv.org/abs/2610.13767)


### 与已有方法比较

| 方法 | 是否依赖 calibration activation | 主要优化变量 |
|---|---|---|
| RTN / Absmax | 否 | 简单 block scale |
| Four-Over-Six | 可不依赖 | NVFP4 block scale |
| H-Scale | 是 | Hessian/activation-aware scale |
| OSFP4 | 是 | Smoothing + block scale |
| **DualQuant** | **否** | **Weight/activation dual rescaling** |

对你而言，这篇论文最值得验证的不是 RTX 4090 上的 2.46×，而是：

**在 B200 原生 NVFP4 上，DualQuant 是否能够以更低的 calibration 成本达到 OSFP4/H-Scale 接近的精度。**

## 5. vLLM：SM120/SM121 的 NVFP4 KV Decode 开始使用 XQA

**状态：[已合入 main]｜10 月 10 日｜vLLM #60452**

[vLLM #60452](https://github.com/vllm-project/vllm/pull/60452)

这项主要针对 RTX PRO 6000 / RTX 5090 / DGX Spark 等 SM12x 平台，而不是 B200。

不过它揭示了一类值得注意的低比特 Attention 问题。

### 原来的问题

SM120 上：

**FP8 KV Cache**

可以采用：

`Prefill → FA2`

`Decode → XQA`

而此前：

**NVFP4 KV Cache**

却可能统一进入 FA2。

这导致 speculative decoding 的多 token verification 无法使用最合适的 decode backend。

尤其 CUDA Graph 模式下，原本应该属于 decode 的 MTP verification 被当成 piecewise prefill。

作者引用的用户反馈显示：

SM120、TP2、MTP3 的某个配置中，NVFP4 KV 的 decode 速度下降到约 **15 tok/s**，而禁用 MTP 后接近 FP8 路径。

### 修复

现在对于 SM120/SM121：

`NVFP4 KV → XQA decode`

在 geometry 或配置不支持时：

`→ FA2 fallback`

同时让 speculative verification 正确进入 `UNIFORM_BATCH` CUDA Graph。

### 正确性

一份用户报告显示，Qwen3.8-27B、TP2、MTP3：

- FP8 KV GSM8K：0.962；
- NVFP4 KV GSM8K：0.962；
- 无 invalid response。

但这里需要保留重要边界：作者没有直接使用 SM12x 硬件完成全部验证，这组结果主要来自用户报告，且没有记录完整的 FlashInfer 版本与 checkout 信息。

所以它可以被视为：

**后端 dispatch correctness 修复已合入，但还不应被宣传为确定的 E2E 加速幅度。** [GitHub](https://github.com/vllm-project/vllm/pull/60452)

### 对 B200 的启示

这项 PR 本身不会改变 SM100/B200 的执行路径。

但问题具有共性：

> **KV Cache dtype 可以改变 attention backend selection，并进一步影响 speculative decoding 和 CUDA Graph 的执行策略。**

以后测试 NVFP4 KV，一定要记录最终选择的 attention backend，不能只记录 dtype。

## 6. vLLM：低比特训练与推理的 Bitwise Consistency 开始成为真正的工程目标

**状态：[官方技术博客]｜10 月 14 日**

[vLLM：Train-Inference Bitwise Consistency](https://vllm-project.github.io/2026/10/14/train-inference-consistency.html)

这是本周对低比特 QAT/QAD/RL 最有价值的一篇工程文章。

问题非常直接：

**训练端和推理端即使使用同一份 FP8/NVFP4 权重，也不一定执行完全相同的数值计算。**

原因可能包括：

- FP8 scale 计算方法不同；
- reduction order 不同；
- SiLU/乘法的舍入位置不同；
- MoE expert routing tie-breaking 不同；
- prefill/decode kernel 不同；
- CUDA Graph 与 eager 路径不同；
- Tensor/Expert Parallel layout 不同。

这些差异不一定导致普通 accuracy 明显下降。

但在 RL 中，rollout engine 和 training engine 给同一个 token 计算出的 logprob 可能不同，最终破坏训练的 on-policy 假设。

### 新方案

作者直接让训练 forward 调用 vLLM inference kernel，并逐个修正不一致的数值路径。

例如 FP8 MoE：

`SiLU(gate) × up`

先在 FP32 中完成乘法，再只进行一次 BF16 rounding，最后进入 FP8 quantization。

而不是先把 SiLU 结果 round 到 BF16，再乘 up。

这个差异看似只有一个 ULP，却可能最终造成 FP8 quantized code 改变。

### 实验结果

DeepSeek-V4-Flash 的 100-step 训练实验中：

- training/inference logprob difference：**严格为 0**；
- consistent rollout throughput：24.22 token/ms；
- baseline：26.53 token/ms；
- 相当于 baseline 的 **91.3%**。

同一实验中，baseline train-inference KL 从约 0.002 增长到 29.9，而一致性版本保持 0。

作者也在 Nemotron-3.5 的 NVFP4/Mamba hybrid 结构上验证了类似方法。

但必须强调：

**文章没有证明 bitwise-consistent RL 的完整训练耗时已经更短。**

当前严格一致性版本有一定 throughput 成本，而 baseline collapse 也与实验 recipe 有关，不能普遍外推。[vLLM Blog](https://vllm-project.github.io/2026/10/14/train-inference-consistency.html)

### 我的判断

这篇对你的研究非常重要。

你目前做 NVFP4/MXFP8 伪量化时，一般关注：

`accuracy degradation`

但如果未来进一步做低比特 QAD/RL，就必须关注：

**Fake quant forward 是否真的与最终 serving execution 对齐？**

具体不仅是量化值，也包括：

`rounding`

`scale`

`activation fusion`

`reduction`

`prefill/decode`

`CUDA Graph`

`weight reload`

这些都是数值契约的一部分。

## 7. PN-Mix：KV 量化从 Token 重要性进一步细化到 RoPE Channel Pair

**状态：[论文]｜10 月 14 日｜arXiv:2610.19605**

[PN-Mix 原文](https://arxiv.org/abs/2610.19605)

前几周已经出现 HyQuant、Fathom 等方法，分别从 token 重要性和 query-dependent bit depth 优化 KV Cache。

PN-Mix 则提出一个新视角：

**真正决定 K 量化误差影响大小的，不仅是 K channel magnitude，还包括与其配对的 Q channel。**

### 为什么？

Attention logits：

\[
S_{ij}=\sum_d Q_{i,d}K_{j,d}
\]

如果某个 K channel 很大，但对应的 Q channel 几乎为零，那么该 K channel 的量化误差可能对 logits 没有太大影响。

相反，一个 K channel 本身不算极端，但如果与大 Q channel 配对，就可能产生显著 logit perturbation。

对于 RoPE，这种重要性还应该按旋转通道对来考虑。

因此 PN-Mix 使用：

**Query-Key pair norm**

判断 channel pair 的重要性。

在 prefill 阶段确定高精度 channel pair，后续 decode 复用这一分配策略。

### 结果

作者报告：

- PN-Mix：平均 **2.26 bit**；
- 对比方法：平均 2.32–2.39 bit；
- reasoning、code generation、AIME 等任务上达到相近或更高平均准确率；
- 降到 1.5 bit 时，质量退化曲线仍相对平缓。

但摘要没有提供经过完整 GPU kernel 验证的统一 E2E throughput 倍数，因此不应由 bit-width 直接推算吞吐收益。 [arXiv](https://arxiv.org/abs/2610.19605)


### 与已有 KV Quantization 比较

PN-Mix 的优势在于它尝试回答：

> **到底应该给 K 的哪个子空间分配更多 precision？**

这种方法特别适合和 MLA 的：

`NoPE latent`

`RoPE K`

分别量化的思路对照。

不过在 MLA 中，compressed latent 的数值与传统 MHA/GQA 的显式 K 并不完全相同，因此不能直接照搬 PN-Mix 的原始 RoPE channel-pair 假设。

## 8. MFSA：硬件层开始研究如何把 MXFP4/MXFP8 的 Scale 运算直接融入 Accumulator

**状态：[论文/硬件设计]｜10 月 14 日｜MFSA**

[MFSA 论文](https://arxiv.org/abs/2610.19645)

这是本周最值得从硬件角度阅读的论文。

MFSA 的目标是设计一种能够同时支持：

- BF16；
- FP8；
- FP4；
- INT8/INT4；
- MXFP8；
- MXFP4；
- NVFP4；

的多格式 systolic array。

核心贡献不是提出新 datatype，而是优化 **block scale 在矩阵乘法内部如何被处理**。

### Online Block-Scale Rebasing

对于普通 block-scaled GEMM：

\[
C = \sum_b s_{A,b}s_{B,b}
\left(A_bB_b\right)
\]

每个 block 的 scale 都可能不同。

一种直接的硬件实现是为不同 block 保留额外的 accumulator，然后再乘 scale、累加。

MFSA 提出 **Online Block-Scale Rebasing（OBSR）**。

核心思路是：

**在 block boundary 将 scale 的影响折叠进正在更新的 FP32 partial sum，而不需要单独的第二套跨 block accumulator。**

### 硬件数据

作者使用 TSMC 28nm、1GHz 的设计流程评估。

| 指标 | 结果 |
|---|---:|
| MX 支持的增量面积 | 相比朴素实现减少 **64.2%** |
| MX 支持的增量能耗 | 减少 **67.5%** |
| NVFP4 E4M3 fractional-scale 支持 | 额外面积约 **11.8%** |
| NVFP4 额外功耗 | 约 **7.3%** |

这里的 NVFP4 面积/功耗是相对论文自身 CFP8+FP4 基础设计，而不是相对 NVIDIA B200。

**这是 ASIC 研究设计，不是 NVIDIA Rubin 已经采用 OBSR 的证据。** [arXiv](https://arxiv.org/abs/2610.19645)

### 对 Rubin 的启示

MFSA 很好地说明，未来硬件竞争可能不只是：

`FP4 MMA FLOPS`

而是：

**怎样低成本支持更多 scale format，并把 scaling factor 与 accumulation 融合。**

你此前关注 Rubin UE5M3、block scaling、2:4 compression 的硬件软件接口，这篇论文提供了一个值得参考的设计思路。

但我不会由此推测 Rubin 内部具体采用了 OBSR。

## B3. SGLang：Monokernel 开始成为一个公开 RFC，但目前不应当作默认能力

# C. 本周新论文与研究方向

本周我认为最值得完整阅读的论文是四篇。

| 论文 | 发布时间 | 核心问题 | 推荐优先级 |
|---|---|---|---|
| **DualQuant** | 10/09 | 无校准联合 W+A 量化，支持 NVFP4/MXFP4 | **高** |
| **Echo** | 10/09 | 4-bit TP All-Reduce + 跨层误差反馈 | **高** |
| **PN-Mix** | 10/14 | 按 Q/K RoPE channel pair 分配 KV precision | 中高 |
| **MFSA** | 10/14 | MXFP4/MXFP8/NVFP4 硬件 scale/accumulator 协同设计 | **高，偏硬件** |

这四篇分别代表四条不同路线：

**DualQuant：压低 calibration 成本。**

它的价值是让 W4A4 PTQ 不再高度依赖 activation calibration 数据。

**Echo：让低比特进入 TP 通信。**

它解决的是普通 EP payload quantization 无法覆盖的数值求和问题。

**PN-Mix：重新定义 KV 重要性。**

它不再只看 K，而是考虑 Q/K 对 attention logits 的联合贡献。

**MFSA：降低原生 block scaling 的硬件成本。**

它解释了为什么低比特硬件需要专门优化 scale arithmetic，而不是只增加 FP4 乘法数量。

本周也有针对稀疏 MoE weight generation 的研究，但更多属于以计算换权重存储的架构探索，没有提供同等级的原生 FP4/MXFP8 执行验证，因此不列入核心四篇。

|---|---:|

但真正值得研究的不是这三个峰值。

### Rubin 为什么需要 locality domains？

对于低并发 decode，MoE 常常受 weight loading 限制。

Rubin GPU 内部存在不同的 HBM locality domain。

如果一个 domain 的 SM 持续访问其他 domain 的 HBM，实际可用带宽可能下降。

因此 vLLM 尝试：

**按 N 维将 FC1/FC2 权重拆成两份。**

然后：

`Domain A SM → 只访问 Domain A HBM 中的权重`

`Domain B SM → 只访问 Domain B HBM 中的权重`

减少跨 domain weight read。

作者在 MiniMax-M3 MoE shape 上报告，small-token FC1+FC2 forward 平均约 **1.2×** 加速。

测试比较了默认 200 SM 的分区策略和 backfill 后使用全部 212 SM 的策略。

但这个结果不包括 MoE 通信时间。 [vLLM](https://vllm.ai/blog/2026-10-09-vera-rubin-preview)


### 系统级性能

SemiAnalysis AgentX：

**Rubin NVL72 上的 vLLM/MiniMax-M3，最高达到 GB200 NVL72 的 7.84× per-GPU throughput**，要求匹配交互性能。

在 150 tok/s/user 的约束下，吞吐约 **5.18×**。

MLPerf Qwen3-VL-235B：

相对 GB300 NVL72，部分测试最高 **3.7×**。

但这些数字必须正确归因：

> **7.84× 是整个 Rubin serving system 相对 GB200 的结果，不能归因于 NVFP4 算力提升，也不能归因于 locality domains 一项优化。**

它同时包含：

- HBM4；
- NVLink；
- MoE backend；
- attention kernel；
- scheduling；
- 整体推理栈优化。

# 本周最重要的三个趋势判断

### 第一，低比特 Attention 正在摆脱“只压缩存储、不直接计算”的阶段

FlashInfer 的 native NVFP4 sparse MLA 是明确的进展。

它不是简单：

`FP4 KV → BF16 KV → Attention`

而是直接使用 FP4 cache 参与 block-scaled QK MMA，并将 PV 留在更合适的 FP8 precision。

这也进一步验证了：**Attention 的最优精度应该按 QK、Softmax、PV 等计算阶段分别设计。**

### 第二，低比特通信可能成为下一阶段的重要性能来源

过去主要优化：

`FP4 Weight / FP8 Activation → GEMM`

后来发展到：

`MXFP8 Activation → Expert Parallel`

现在 Echo 开始解决：

**4-bit Tensor Parallel All-Reduce + Error Feedback。**

这意味着低比特不再只是 GPU arithmetic format，也开始成为 distributed numerical computation 的组成部分。

我认为这条路线非常值得持续关注，尤其对多节点 TP/EP 大模型。

### 第三，低比特真正需要统一的是 Numerical Contract，而不是简单统一 dtype

本周的几项工作都指向同一个问题：

- DualQuant：weight/activation scale 应该协同；
- FlashInfer：NVFP4 KV 应该由原生 consumer 直接读取；
- vLLM：训练/推理 FP8 数值必须对齐；
- AITER：同一 MXFP4 weight 需要多种 activation backend；
- Rubin：scale、MMA、weight locality 和通信都影响最终效率。

因此我建议后续评价低比特方案时，继续使用更完整的描述：

**Weight Format × Activation Format × KV Format × Scale Semantics × Physical Layout × Kernel Backend × Communication Precision。**

仅凭“这是 NVFP4 模型”已经无法判断它实际使用什么算子，也无法判断它的性能和精度边界。

---

## 本周最值得立即跟进的三个项目

**① FlashInfer v0.7.2 的 B200 NVFP4 sparse-MLA decode。** 这是最直接、最适合拿现有 GPU 验证的新原生低比特 Attention 路径。

**② DualQuant。** 这篇最有希望直接转化成 NVFP4/MXFP4 PTQ 方法对照，尤其适合评估 calibration-free W4A4 的精度潜力。

**③ Echo。** 这项研究范围不同于传统 GEMM 量化，但如果 4-bit TP communication 能在现代 NVLink/RoCE 环境下稳定控制误差累积，潜在系统价值很大。

此外，我建议把 **vLLM 10 月 14 日的 Train-Inference Bitwise Consistency** 文章加入长期阅读清单。对于低比特 QAT/QAD/RL 来说，它可能比继续把某个 FP4 GEMM 优化几个百分点更重要。
