# 低比特推理与框架周报｜2026-10-23 至 2026-10-30

[本期总览](../weekly/20261030.md) · [训练与后训练](../train/20261030.md) · [硬件与编译器](../gpu/20261030.md)

本期重点：模型格式跨平台迁移、量化与算子融合、低比特缓存，以及投机解码与量化模型的配合。下文“已合入”均指主分支；性能数字来自作者报告，未在本地复现。

## vLLM

<a id="vllm-nvfp4-requant"></a>
### NVFP4 模型可转换到 ROCm 的量化执行路径

**已合入 · 10-29。** vLLM 增加 MoE 权重在线重新量化：加载 NVFP4 checkpoint 后，分块解码，再转换为目标平台支持的 MXFP4 或 MXFP8 表示，并处理共享专家。它扩大了现有模型在 AMD 平台上的可用范围。关键区别是“转换后运行”，并非 AMD 原生执行 NVFP4；二次量化的精度变化与最终速度仍需按模型评估。

原文：[NVFP4 MoE 重新量化，PR #64378 对应提交](https://github.com/vllm-project/vllm/commit/2abde627d973ad28d577133bdac5472bb00ee255)

<a id="vllm-rocm-fused-mxfp8"></a>
### MXFP8 小批量解码：把激活量化直接融入矩阵乘

**已合入 · 10-29。** MI355X 路径把小 token 数下的 MXFP8 激活量化放进 GEMM 内部，减少一次启动与中间数据往返；同时避开大词表权重不适合的特定小矩阵内核。作者在 DeepSeek-V4.1-Flash 指定配置中报告解码间隔约减少 2%。值得关注其通用思路：位宽已经很低后，数据移动和调度仍可能成为主要成本。

原文：[量化融合与 lm_head 调度，PR #63179](https://github.com/vllm-project/vllm/pull/63179)

## SGLang

<a id="sglang-ascend-fp8"></a>
### 昇腾 NPU 增加 block FP8 Linear 与 MoE 路径

**已合入 · 10-29。** 新增 Qwen3.6-35B-A3B 的 block FP8 适配，允许保留原有分块 FP8 表示执行，另有加载时转为 MXFP8 的路径。它让“沿用模型原始量化格式”成为可比较的选择，减少必须重新量化的需求。关注点是 CANN 算子、缩放参数与 MoE 调度能否配套；不能仅凭都叫 FP8，就认为两条路径精度和速度相同。

原文：[SGLang 昇腾 block FP8，PR #46212](https://github.com/sgl-project/sglang/pull/46212)

<a id="sglang-rdna-w4a16"></a>
### RDNA 平台可用 W4A16 运行 Quark MXFP4 MoE

**已合入 · 10-29。** 新路径用 Triton 在计算时展开四比特权重，激活保留 BF16，使缺少相应 FP4 硬件路径的 Radeon 8060S / gfx1151 也能正确运行 Quark MXFP4 MoE。作者的 Qwen3.5 示例中，16 并发吞吐提高约 1.7 倍，但单请求生成略慢于 BF16。它是很有价值的兼容性进展，也说明省权重空间与低延迟加速不是同一件事。

原文：[Quark MXFP4 W4A16 路径，PR #41389](https://github.com/sgl-project/sglang/pull/41389)

## FlashInfer

<a id="flashinfer-qsa-formats"></a>
### 稀疏注意力扩大 KV 格式支持：FP8、BF16 与 NVFP4

**已合入 · 10-29。** 实验性 QSA 稀疏分页注意力内核在 SM80–SM90 上新增 FP8、BF16 KV cache，并优化 NVFP4 数据搬运和结果合并。值得关注的是同一类注意力逐步获得多种精度选择，便于按显存与性能权衡。这里的低比特缓存会按计算需要解码，不代表这些 GPU 获得原生 FP4 矩阵指令；速度也随形状变化。

原文：[QSA 多格式缓存，PR #7794](https://github.com/flashinfer-ai/flashinfer/pull/7794)

<a id="flashinfer-launch"></a>
### FP4/MXFP8 调用优化：去掉重复初始化

**已合入 · 10-29。** 多条 CUTLASS GEMM 和 MLA 调用路径原先会重复准备描述符，新实现复用已初始化的参数。它主要减少 CPU 发起调用的成本，对没有 CUDA Graph、矩阵很小的解码场景更有意义。此类优化不会普遍提高 GPU 的矩阵计算吞吐，却提醒我们：当低比特内核变快，外围调用开销会更显眼。

原文：[移除重复初始化，PR #6282](https://github.com/flashinfer-ai/flashinfer/pull/6282)

Rubin 的 FP4 MoE 调优范围也在本周扩展，见[硬件栏目](../gpu/20261030.md#flashinfer-rubin-moe)。

## llama.cpp / ggml

<a id="llamacpp-ocp-fp8"></a>
### ggml 引入 OCP FP8 E4M3 基础格式

**已合入 · 10-29。** ggml 新增 OCP E4M3 的饱和转换表示，推动格式体系从既有 GGUF 量化类型向标准 FP8 扩展。当前合入的是基础类型能力；KV cache、CUDA、Vulkan 后端与缩放参数衔接仍分属其他改动。跟踪时应继续看“格式进入框架”之后哪些实际算子能消费它，避免把基础类型支持当作完整 FP8 推理支持。

原文：[OCP FP8 E4M3，PR #27512](https://github.com/ggml-org/llama.cpp/pull/27512)

本周还有 Intel 量化 KV 和 Apple Metal MXFP4 优化，分别见[Intel 栏目](../gpu/20261030.md#llamacpp-kv-dpas)与 [Apple 栏目](../gpu/20261030.md#llamacpp-metal-mxfp4)。

## TensorRT

<a id="tensorrt-global-tuner"></a>
### 自动调优从单一默认策略转向“精度合格后选最快”

**官方技术博客 · 10-23。** TensorRT 11.1 的 Global Performance Tuner 搜索不同编译与调度组合，先过滤精度不合格的候选，再按端到端速度选择。官方十个工作负载的结果为默认路径的 1.14–1.63 倍。它与低比特选型相关的价值是把精度约束纳入调优流程；文中的自动插入量化节点是概念示例，不代表当前版本提供任意自动混合精度搜索。

原文：[Global Performance Tuner，Part 2](https://developer.nvidia.com/blog/scaling-nvidia-tensorrt-performance-optimization-beyond-a-single-build-route-with-the-global-performance-tuner-part-2/)

## TensorRT-LLM

<a id="trtllm-dspark"></a>
### MiniMax DSpark 草稿模型适配：量化权重与注意力语义要一起处理

**已合入 · 10-29。** TensorRT-LLM 为 MiniMax-M3.1-Flash 配套 DSpark 草稿模型增加配置、权重映射和窗口注意力处理。草稿权重中的 MXFP8 会先解码为计算精度，不应视为草稿模型已经原生使用 MXFP8 计算。该更新有助于让新模型接入投机解码；目标模型加载仍有配套依赖，特定长提示与分离部署配置也有已知限制。

原文：[MiniMax DSpark 适配，PR #20922](https://github.com/NVIDIA/TensorRT-LLM/pull/20922)

## 本期可以带走的判断

- **“支持某格式”至少有三层：能加载、能正确计算、能加速。** vLLM 的重新量化、SGLang 的 W4A16 与 ggml 的基础 FP8 类型分别处于不同环节，不能混成一张简单的支持勾选表。见 [vLLM](https://github.com/vllm-project/vllm/commit/2abde627d973ad28d577133bdac5472bb00ee255)、[SGLang](https://github.com/sgl-project/sglang/pull/41389)与 [ggml](https://github.com/ggml-org/llama.cpp/pull/27512)。
- **框架适配的竞争也在量化之外。** 量化与 GEMM 融合、减少启动成本、正确连接草稿模型，决定了低比特潜力能否变成实际请求的收益。见 [vLLM 融合](https://github.com/vllm-project/vllm/pull/63179)、[FlashInfer 调用优化](https://github.com/flashinfer-ai/flashinfer/pull/6282)与 [TensorRT-LLM](https://github.com/NVIDIA/TensorRT-LLM/pull/20922)。
