<a id="intel-kv-dpas"></a>
## Intel XMX 直接消费量化 KV 的 decode 路径｜LLAMACPP-KV-DPAS｜主分支提交｜10-29 UTC｜Xe2+ / llama.cpp f7c01c5

**结论：** llama.cpp SYCL 将 q4_0/q8_0 KV 的小 batch attention 接到 DPAS，避免每次调用先构造整份 FP16 cache；这是有生成吞吐证据的低比特执行集成。

**技术机制与证据：** cache 保存量化 block，QK 采用 s8×s4 或 s8×s8 的 XMX DPAS，PV 仍走 FP16。由于 joint_matrix 不提供 s4 类型，四比特路径使用 inline vISA。收益路径是压缩存储直接进入分块计算，减少整 cache 反量化的流量和中间缓冲；不能因此把 softmax、PV 或输出都标成 INT4。kernel 根据 head size、query 数、GQA 和地址对齐选择 staging 与 split，split 结果仍需归并。[源码和文档](https://github.com/ggml-org/llama.cpp/commit/f7c01c5226cac1de1052c17920ff38cdefea0ae6)。

提交者报告 Arc B580、Llama 3.1 8B Q4_K_M、q4_0 KV、16K context、tg128 的生成速度由 31.3 到 54.2 token/s；这是同工作负载的新旧实现比较，不能替代并发 serving 的 TTFT/TPOT。作者同时报告 FLASH_ATTN_EXT 为 4582/4584、与 master 相同两项失败，故不能写成全测试通过。没有同等完整的模型质量测量，本期不承诺长上下文精度无损。[PR 原始说明](https://github.com/ggml-org/llama.cpp/pull/31125)。

**边界与影响：** 当前为 Xe2 及更新硬件，query token 数 1–31、head size 64/96/128/256/512、每 KV head 最多 32 query heads；192 已从最终实现排除。构建需 XMX 路径，运行开关 `GGML_SYCL_FA_DPAS` 默认开启，设零回原生 SYCL kernel；不支持的 shape 不应硬套新路径。大 prefill 仍有不同后端与 FP16 转换成本。可推广的是把压缩 cache 交给实际 consumer 的设计原则；s4 DPAS/vISA、SLM 布局及阈值属于 Intel 实现，不能移植为其他厂商的 ISA 结论。

这也给“低比特 KV 只省容量”的判断提供了具体反例，但反例有条件：必须有能消费压缩 block 的计算路径，且省掉的全量转换大于分块处理开销。不能由一个长 context 的生成成绩推出短 prompt、所有 KV 格式或多请求调度均获同等收益。质量与性能的证据在此仍不对称。

<a id="ascend-block-fp8"></a>
## Ascend block-FP8：保留原 scale 与重量化是两条路径｜SGLANG-ASCEND-BLOCK-FP8｜主分支提交｜10-29 UTC｜arch35 / SGLang 019008a

**结论：** SGLang 新增 Qwen3.6-35B-A3B block-FP8 MoE 支持，代码明确区分 checkpoint FP32 block scale 的原生 G-B 路径与可选 MXFP8 重量化路径。

**技术机制与证据：** 原生路径保留 `[N,K]` 或 `[E,N,K]` 的 FP8 权重与 128×128 FP32 block scales，向 CANN 提交转置 view；激活从 BF16/FP16 动态量化为每行 128 元素分组的 E4M3，经 `npu_quant_matmul` 或 grouped matmul 消费。linear 输出回输入 dtype，bias 在 GEMM 后相加，因为此 G-B 模式不接受融合 bias。这里的 FP32 scale 不是 E8M0，也没有仅因名称含 FP8 就自动转换为 MX。[固定实现](https://github.com/sgl-project/sglang/commit/019008afe0b0a61aa46c1f32dbcd6478f1c09220)。

可选 `SGLANG_NPU_ARCH35_REQUANT_BLOCK_FP8` 则进入 MX 路径。DeepEP 低延迟输出须为 E4M3 activation 加 E8M0 scale，代码按字节重排 scale 到 consumer 需要的格式；普通 FP8 加 FP32 scale 被拒绝。原生 G-B 路径把 dispatcher 配置为 BF16，故 FP8 GEMM 不意味着跨 expert 通信也已经八比特。收益或代价应分别记在权重读、激活量化、scale 重排和通信环节，不能凭 checkpoint 大小估算全程吞吐。

**边界与影响：** MoE runner 只允许 auto/ascend，要求 gated SiLU，不支持 expert bias 及任意 GEMM1 alpha/beta/clamp 参数。低延迟 MX dispatch 缺 scale 会报错，并提示可显式 BF16 dispatch；不会把缺失元数据当成可忽略信息。提交增加 GSM8K 验收测试，但代码中的 0.90 是断言门槛，不是已测成绩；本报没有据此声称准确率达到九成。也未核得可发布的端到端性能对照或完整 CANN 最低版本矩阵。可迁移的是“格式、scale 与通信分别签订接口契约”的设计；具体算子、arch35 门槛和布局属于 Ascend。[PR 与测试上下文](https://github.com/sgl-project/sglang/pull/46212)。

这项适配改变的是已有 block-FP8 checkpoint 的可执行边界，而非宣布所有 Ascend 设备支持相同数值格式。依赖库存在对应入口、参数组合被硬件接受、框架真实选择该入口是三个独立环节；最终还要等待完整质量和吞吐记录，才能比较保留原 scale 与 MX 重量化的收益。

<a id="nvfp4-requant"></a>
## NVFP4 checkpoint 在 ROCm 上成为重量化输入｜VLLM-NVFP4-REQUANT｜主分支提交｜10-29 UTC

vLLM 将来源权重加载与目标在线量化分开：NVFP4 MoE 按 expert chunk 反量化，再交给目标 quantizer；来源阶段跳过原生后端选择，避免为了读取 checkpoint 就要求 NVFP4 执行能力。测试比较不同 chunk 大小与完整反量化结果，并覆盖 shared expert 融合。收益首先是加载可达性和峰值临时存储控制；目标可能为 MXFP4/MXFP8 等，不能称 ROCm 原生执行 NVFP4。重量化增加误差与加载成本，尚无统一模型质量/速度结论。[固定实现](https://github.com/vllm-project/vllm/commit/2abde627d973ad28d577133bdac5472bb00ee255)。

<a id="nvfp4-scale-padding"></a>
## fused activation 的 scale padding 也必须初始化｜VLLM-NVFP4-SCALE-PADDING｜主分支提交｜10-29 UTC

vLLM 修复 SiLU×gate 后融合 NVFP4 量化未写满 scale padding 的问题。GEMM 按对齐布局读取，逻辑有效区正确仍可能读到脏 scale，产生 NaN 或乱码。新增测试先用 `0x7F7F7F7F` 污染 scale 缓冲，检查行列 padding 被覆盖，覆盖 M=1/90/130 等非整齐形状。它修复元数据初始化，不改变量化 recipe，来源未提供模型质量恢复幅度或吞吐收益；不能扩张为所有 NVFP4 后端的故障。[diff 与回归](https://github.com/vllm-project/vllm/commit/b42f25b00c3d13b565ec60e81928cd21efefce32)。
