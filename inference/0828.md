# 低比特大模型推理周报

**时间窗口：2026 年 8 月 21 日—8 月 28 日**

这一周的主线非常集中：**低比特优化正在从“某个 GEMM 使用 FP4/FP8”继续向整个数据生命周期扩展**。最典型的是 MiniMax-M3 的 **分层混合 NVFP4/FP8 KV Cache**、AMD DeepSeek-V4 的 **MXFP8 直接跨 Expert Parallel 通信并原样进入 W4A8 MoE**，以及 FlashInfer 把 **RMSNorm、残差和 FP8 block quantization** 直接做成一个 producer kernel。与此同时，本周也出现了一个很有代表性的反面案例：vLLM 新合入的 Humming **MXFP4 weight + block-FP8 activation** 在 B200 正常，但 H100 几乎全部输出失效，说明低比特系统现在越来越容易在 **scale layout、producer/consumer contract 和架构差异**上出 correctness 问题。([GitHub][1])

我这期仍按状态区分：**[已合入 main]、[开放 Issue/待修复]、[论文]、[厂商 Preview]**。没有把仅有讨论、没有验证数据的东西包装成正式能力。

# A. 本周最值得关注的 9 项进展

## 1. TensorRT-LLM：MiniMax-M3 正式进入“分层混合精度 KV Cache”

**状态：[已合入 main]，PR #17985，8 月 27 日**

[TensorRT-LLM PR #17985](https://github.com/NVIDIA/TensorRT-LLM/pull/17985)

这是我认为本周**最重要的低比特 KV Cache 工作**。

MiniMax-M3 一共存在三种完全不同的 KV consumer：

* **57 层 sparse MSA target layer**；
* **3 层 dense attention target layer**；
* **1 层 Eagle speculative draft layer**。

过去为了兼容所有消费者，只能采用一种统一 KV representation。现在 TensorRT-LLM 将它拆成：

| 层类型                     | KV 格式                   | Page |
| ----------------------- | ----------------------- | ---: |
| 57 sparse target layers | **NVFP4 + block scale** | P128 |
| 3 dense target layers   | **FP8**                 | P128 |
| Eagle draft layer       | **FP8**                 |  P32 |

Eagle 暂时保留 FP8，不是因为 NVFP4 精度不够，而是**当前 draft attention kernel 没有 P32 NVFP4 consumer**。cache accounting、block table、disaggregated transfer、speculative view 都随各自物理 representation 变化。([GitHub][1])

更有意思的是 decode 路径。

TensorRT-LLM 同时实现了两种 sparse attention 方案：

**方案 A：**

`NVFP4 KV pool → NVFP4-native MSA attention`

**方案 B：**

`NVFP4 KV pool → 只取本次 decode 真正访问的 pages → staging 成 FP8 scratch → 复用成熟 FP8 MSA kernel`

在 GB300 的 AgentX 3600 秒 workload 中：

| Decode 路径                                  | served tok/s/GPU |     P90 TPOT | P90 E2E latency |
| ------------------------------------------ | ---------------: | -----------: | --------------: |
| Direct NVFP4 MSA                           |        31,543.67 |     8.713 ms |       19,513 ms |
| NVFP4 storage → selected pages FP8 staging |    **33,780.86** | **7.379 ms** |   **16,036 ms** |
| 变化                                         |       **+7.09%** |  **-15.31%** |     **-17.82%** |

([GitHub][1])

这给出了一个非常值得记住的结论：

> **最优的低比特 KV 系统不一定要求“从存储到 Tensor Core 全程保持最低 bit”。**

如果 FP8 attention kernel 明显成熟，那么：

`NVFP4 负责 resident storage / HBM capacity`

而

`FP8 负责本轮少量 active page 的 compute`

可能反而更快。

这和普通的“KV FP8 vs KV FP4”二选一思维完全不同。真正的优化对象正在变成：

**storage precision × page size × active-page selection × compute precision × staging cost。**

## 2. AMD AITER：MXFP8 终于可以真正成为 Expert Parallel 的“线上格式”

**状态：[已合入 main]，AITER #4954，8 月 25 日**

[AITER PR #4954](https://github.com/ROCm/aiter/pull/4954)

DeepSeek-V4 的 MoE 是典型：

**MXFP4 weight × MXFP8 activation，W4A8**

其中 activation 是 FP8 E4M3，带 **group-32 E8M0 microscale**。

如果 Expert Parallel 的 send side 已经把 hidden state 量化成：

`MXFP8 data + E8M0 scale`

以前 AITER `fused_moe` 并不会识别“这是已经量好的 MXFP8”，receiver 仍然重新计算一遍 scale、重新 quantize。

不会报错，结果也正确，只是**低比特通信省下来的工作在 receiver 又做了一遍**。

#4954 新增 pre-quantized branch：

`MXFP8 all-to-all output`
→ **直接保留 data**
→ 只做 routing/sort 所需的 scale rearrangement
→ `MXFP4 × MXFP8 fused MoE`

不再：

`MXFP8 → de facto re-quantization → MXFP8`。([GitHub][2])

它的 motivating consumer 是 SGLang MoRI EP：

`live token`
→ **send side MXFP8 quant**
→ all-to-all
→ receiver AITER fused_moe 直接消费。

在 **MI355X、DeepSeek-V4-Pro、TP8 + DP8 Attention + EP8/MoRI + EAGLE MTP、8192 input / 1024 output** 上：

* C4—C64 output throughput：**+6.4%～+9.8%**
* TPOT：**-6.2%～-9.3%**
* GSM8K：0.945 / 1319，0 invalid。([GitHub][2])

这一项和上周 FlashInfer 在 B200 上做的 MXFP8 EP payload 是同一条趋势：

> **低比特开始从“Tensor Core operand format”，变成“网络/互联上的 communication format”。**

这对大规模 MoE 的意义可能比 GEMM 再快几个百分点更大。

## 3. FlashInfer：Add + RMSNorm + FP8 block quant 变成一个 producer kernel

**状态：[已合入 main]，#4480，8 月 27 日**

[FlashInfer PR #4480](https://github.com/flashinfer-ai/flashinfer/pull/4480)

这个 PR 很适合解释最近低比特 kernel 优化为什么越来越强调 **producer**。

普通低比特 linear 前面经常是：

`residual add`
→ `RMSNorm`
→ 写 BF16
→ 再读 BF16
→ `1×128 FP8 quant`
→ scale layout
→ FP8 GEMM

新 kernel 一次完成：

`residual add + RMSNorm + E4M3 quant + FP32 block scale generation`

并且直接产生下游 DeepGEMM 已经能消费的：

**column-major、TMA-aligned 1×128 scale layout**。

因此没有后续 scale repacking。([GitHub][3])

H200 microbenchmark：

| M × H     |   fused | 两 kernel baseline |    加速 |
| --------- | ------: | ----------------: | ----: |
| 256×4096  | 10.2 μs |           69.0 μs | 6.78× |
| 1024×8192 | 26.7 μs |          146.5 μs | 5.49× |
| 4096×8192 | 84.2 μs |          529.0 μs | 6.28× |

几何平均 **6.23×**。

不过这里需要认真看作者自己的 caveat：baseline 第二个 quant kernel 是 Triton，性能不够理想，所以 6.23× 不能简单理解为“融合本身能让最优实现快六倍”。作者估计如果对比一个高度优化的 CUDA 两-kernel pipeline，纯 kernel compute 收益大约 **1.7×**。

真正确定的收益是：

* 2 launch → 1 launch；
* 去掉 BF16 intermediate round-trip；
* 约 **2× 更少 memory traffic**；
* scale 一开始就是最终 TMA layout。([GitHub][3])

这一项和最近 SGLang 的 UE8M0 scale layout 优化、本周 AMD 的 FP8 scale zero-copy 本质上属于同一个方向：

> **低比特性能的瓶颈正在从 GEMM 本体转向“给 GEMM 准备正确数据格式”的流水线。**

## 4. FlashInfer：NVFP4 + SVDQuant 正式进入 SM120 CuTe DSL

**状态：[已合入 main]，#4420，8 月 24 日**

这项很有意思，因为它不是单纯 NVFP4。

SVDQuant 的基本思想可以理解成：

$$
W \approx W_{\text{NVFP4}} + U V
$$

主体大矩阵使用 **NVFP4**，把量化后难以表达的一部分误差用一个**低 rank BF16 residual**补回来。

因此执行变成：

`NVFP4 main GEMM`
+
`BF16 low-rank down/up correction`

这是一种：

**4-bit 主路径 + 少量高精度修正路径**

而不是全量 W4A4。([GitHub][4])

本次支持的是 SM120/SM121 CuTe DSL，并且：

* BF16 smoothing 融入 NVFP4 activation quant；
* LoRA/down correction 走 BF16 Tensor Core；
* LoRA-up storage 与已经释放的 mainloop buffer 复用；
* fused/unfused correction 自动 autotune。

RTX PRO 6000、rank=32 的完整 `svdquant_linear`：

例如 `M=9216,N=12288,K=3072`：

* 相对 BF16：**+193.3%**
* 相对 FP8：**+59.3%**

`M=16384,N=12288,K=3072`：

* vs BF16：**+191.3%**
* vs FP8：**+54.5%**

而 residual correction 本身融合之后，在部分 shape 相比 unfused 可有 **2×～3× 左右** latency 改善。([GitHub][4])

### 它和标准 NVFP4 有什么区别？

标准 NVFP4：

`误差全靠 scale + FP4 grid 自己承担`

SVDQuant：

`NVFP4 表示大部分矩阵 + BF16 low-rank branch 专门修复难量化方向`

代价当然也很明确：

* 多一套低 rank weights；
* 多额外 Tensor Core compute；
* 增加调度和融合复杂度。

所以它不是免费提高精度，而是在：

**纯 NVFP4 的极致效率**

和

**BF16/FP8 的精度**

之间增加了新的 Pareto 点。

## 5. vLLM Humming：MXFP4 + block-FP8 合入后立刻暴露 H100 架构特定 correctness failure

**状态：[功能已于 8 月 25 日合入 main；Revert #53805 目前仍是待合入 PR]**

#51332 给 Humming MoE 增加：

**MXFP4 weight + FP8 E4M3 group-128 activation**

也就是另一类 W4A8。

它还限制 tuning 的 K block≤128，因为某些 small-M tactic 会挑 K=256，TMA descriptor 在 launch 时产生 misaligned-address error。([GitHub][5])

问题是：合入以后第一次真正跑到完整 H100 correctness job，就出现：

* GSM8K：**0.0000**
* invalid rate：**0.994**
* required floor：0.7800

但同一 build、同一配置在 **B200**：

* GSM8K：**0.8863**
* invalid rate：**0.000**。([GitHub][6])

而且 server 没 crash，1319 个请求全部正常完成，只是数字结果完全错。

因此这是一个很干净的：

**SM90/H100 low-bit correctness regression**

而不是模型下载、server startup 或 evaluation harness 问题。

目前 revert PR 仍未成为正式 merged fix，因此此路径在 H100 上不能视作稳定能力。([GitHub][6])

这个案例特别值得记下来，因为它揭示了低比特 kernel 一类非常危险的 bug：

> **数据 shape、dtype 看起来都对，kernel 也能跑完，但 producer/consumer 对 scale / packed representation 的解释并不一致。**

这种 bug 比普通 crash 更危险，因为它可能静默产生有限数值但完全错误的 logits。

## 6. vLLM + AITER：DeepSeek-V4 的 RMSNorm 和 FP8 quant 再次证明“少做一次 BF16 round-trip”有价值

**状态：[已合入 main]，vLLM #53540，8 月 27 日**

DeepSeek-V4 ROCm decode 的 SWA token insertion 原来做：

1. `q/kv RMSNorm → BF16`
2. q-lora `BF16 → FP8 group-128`
3. indexer 的 `wq_b` 又量一次相同 q

现在 AITER `fused_qk_rmsnorm_group_quant`：

`FP32 RMSNorm accumulator`
→ **直接 FP8 quantize q**
→ `(q_fp8, q_scale)`

然后 attention `wq_b` 和 indexer `wq_b` 共用这一份 pre-quantized q。KV 仍然 BF16。([GitHub][7])

micro path：

**14.277 μs → 4.919 μs，2.90×**

不过端到端并没有 2.9×：

MI350X、8k1k：

* C1 throughput：+0.73%
* C4：+0.48%
* C16：+0.84%
* C64：+0.51%
* TPOT：约 -0.5%～-1%

同时 C1 TTFT 反而 **+10.29%**，所以这里并不是全面单调变好。([GitHub][7])

这再次说明：

**micro-kernel 2.9× ≠ serving 2.9×。**

但方向是正确的：

`normalize → quantize → reuse`

应该尽量作为一条 fused producer pipeline，而不是每个 consumer 自己重复量化。

## 7. TorchAO：32×32 MXFP8 cast kernel 正式进入 B200 路径

**状态：[已合入 main]，#4777，8 月 26 日**

TorchAO 新增 standalone MXFP8 Triton quant kernel：

* FP8 E4M3 qdata；
* 每 **32×32 block 一个 E8M0 power-of-two scale**；
* RCEIL scaling；
* 直接生成 expanded / swizzled scale representation。

以前 TorchAO 主要有 1×32 或 32×1 的 microscaling，这次加入真正二维 32×32 block。([GitHub][8])

B200：

| Tensor |  latency |         有效 BW |
| ------ | -------: | ------------: |
| 4096²  |  12.5 μs |     4.04 TB/s |
| 8192²  |  38.4 μs |     5.24 TB/s |
| 16384² | 136.7 μs | **5.90 TB/s** |

另一 variant 达到约 **6.09 TB/s**，作者估计约为 B200 8 TB/s HBM peak 的 **76%**，因此大 shape 已经明显 memory-bound。([GitHub][8])

它目前还是 standalone kernel，并没有自动接进所有 MXTensor flow。

但这个工作值得关注，是因为 32×32 MXFP8 对：

* FPROP；
* DGRAD；
* transpose-symmetric weight representation；
* Blackwell scale-layout

都有直接意义。

它更偏**训练基础设施**，但其 quantization/layout kernel 与 inference 数据格式完全共通，所以值得继续跟。

## 8. SGLang 已经开始真正碰 SM107/Rubin 的 MXFP8 representation compatibility

**状态：[已合入 main]，#35405，8 月 23 日**

这次不是性能新 kernel，而是 Rubin bring-up 时很典型的格式兼容问题。

GPT-OSS 在 **SM107** 上进入 FlashInfer MXFP4 MoE 时，如果前面没有 pre-quantized routing handoff，SGLang 原本用自己的 Triton per-token-group quantizer 做 MXFP8 activation。

问题是：

> 它产生的 representation 并不能可靠满足 FlashInfer SM107 MXFP4 MoE kernel 所假定的 layout。

现在 SM107 改为直接使用 FlashInfer 自己的 MXFP8 quantizer；Kimi-K3 已有的 fused routing/quant path 保持不变。([GitHub][9])

这里没有 headline 性能数据，价值在于一个软件信号：

**SM107 的真正 serving kernel 已经开始暴露 architecture-specific low-bit format contract。**

也就是说，Rubin 并不是简单：

`把 sm100 编译成 sm107 就结束`

上层框架已经开始需要专门处理：

* MXFP8 activation producer；
* scale representation；
* padding；
* FlashInfer consumer contract。

## 9. NVIDIA 首次把 Rubin/Blackwell 的低比特推理放进 AgentX 系统级能效叙事

**状态：[官方厂商 Preview，8 月 24 日；不是独立第三方验证]**

NVIDIA 本周公布 AgentX 系统结果：

* Vera Rubin NVL72 preview，在 DeepSeek-V4-Pro、160 tok/s/user 条件下，声称相对 GB300 NVL72 **最高 30× throughput/MW**；
* GB300 NVL72 相对 H200 NVL8：

  * DeepSeek-V4-Pro：最高约 **15× throughput/MW**
  * Kimi K3 2.8T：最高约 **80× throughput/MW**；
* GB300 的 cost/Mtoken 最多降低约 10×。([NVIDIA Developer][10])

但这个数字**绝对不能理解为 NVFP4 带来 30× 或 80×**。

官方明确把收益归因于完整系统：

* Wide Expert Parallel；
* SGLang / TensorRT-LLM / vLLM；
* DeepGEMM；
* **MXFP4/MXFP8**；
* Dynamo prefill/decode disaggregation；
* KV-aware routing；
* NVLink；
* speculative decoding；
* Rubin 上的 **NVFP4**。([NVIDIA Developer][10])

因此我把它视作：

> **“厂商正在把 FP4 从单 GPU Tensor Core optimization 提升为 rack-scale serving design primitive”**

的证据，而不是 FP4 microbenchmark。

Rubin 数字目前属于 NVIDIA preview，官方也说明尚待 SemiAnalysis review，应该保留这个可信度边界。

# SGLang

除了 SM107 修复，本周 AMD 侧还有一个很典型的 metadata 优化。

DeepSeek-V4 MI355X 的一些 producer 已经能直接生成 transpose-scale representation，但代码仍然调用：

`materialize_bpreshuffle_fp8_scale`

实际发生一次 per-layer copy。

#33166 将其改成 `torch.as_strided` 的**零拷贝 reinterpretation**，应用到：

* MoE down projection；
* MLA `o_proj` BMM；
* fused RMS producer。

producer-level 测试确认 FP8 qdata 和 scale **bit-identical**。([GitHub][13])

单次 TP8 serving 数据只有：

* C16：+0.8%
* C32：+0.4%
* C64：+0.6%

作者自己明确说，这个幅度处在 run-to-run noise 里，不能宣称确定的 E2E speedup。真正确定的价值只是**删除了每层无意义的 scale copy**。([GitHub][13])

本周还有一个值得继续盯的 **open issue #36447（8 月 26 日）**：GLM-5.2 MXFP4 + DSA/NSA + Mega-MoE 正在准备 upstream。该 checkpoint 本身就是 heterogeneous precision：

* dense attention/shared experts：block FP8 E4M3；
* routed experts：FP4 E2M1 + UE8M0；
* embedding/norm/router/lm_head：BF16/F32；
* DSA/NSA indexer top-k=2048。

目前这是**Feature Issue，不是已发布能力**。([GitHub][14])

此外本周仍有一个值得注意的开放问题：**NVFP4 KV Cache + speculative decoding 在 SM120 上存在兼容问题**。这类路径在正式使用前仍需要特别验证。

# C. 本周新论文

我只保留两篇我认为真正对低比特工程有价值的。本周也有 GPTQ/AWQ/2-bit 行为分析类论文，但没有加入，避免凑数。

## 1. Quantization-Aware Healing：压缩模型以后，不要拿“压缩后的 BF16”当最终 teacher

**8 月 21 日，arXiv:2608.20953**

论文研究的 pipeline 非常实际：

**GPT-OSS 120B**
→ structural compression 到 **60B**
→ distillation recovery BF16
→ **MXFP4**

作者发现普通 QAT：

`MXFP4 student ← compressed BF16 model`

训练慢，而且 peak 之后容易 collapse。

他们提出 QAH：

`MXFP4 compressed student ← 原始未压缩 120B teacher`

也就是说，**跨过中间的 compressed BF16 checkpoint，直接向原模型蒸馏**。([arXiv][16])

结果 Hypernova-60B：

* 参数只有 teacher 一半；
* weight memory 约减少 **4×**；
* 9 个 benchmark 中 **7 个达到或超过 compressed BF16 source**；
* 相比 matched QAT，达到类似 peak 大约 **7× 更快**；
* 继续训练也更加稳定。([arXiv][16])

### 我认为它最重要的启示

过去我们常把：

`BF16 compressed checkpoint`

视为“ground truth”，然后量化只负责逼近它。

但如果 structural compression 本身已经引入一次信息损失，那么：

**低比特 student 没必要忠实复制一个已经有误差的中间模型。**

可以直接利用原始 full model 的 soft distribution 修复：

`compression error + quantization error`

两种误差。

这对后续做低比特 post-training / RL 很有参考价值。

## 2. Great Inversion：为什么 Hadamard rotation 对 MXFP4 有用，却未必对 NVFP4 同样有用？

**8 月 25 日，arXiv:2608.25188**

这篇不是新 quantizer，而是一篇非常有价值的**理论/综述工作**，整理约 200 篇文献、43 类 transform method。

它提出一个很有用的概念：

### 传统 transform coding

如果可以：

**重要方向多分 bits，不重要方向少分 bits**

那么希望通过 PCA/KLT 等 transform：

> **把能量尽量集中。**

### GPU 上的 group quantization

现实的 MXFP4/NVFP4 通常不是自由分配 bit。

一个 block：

* 所有 value 都是相同 4 bit；
* 共用一个 scale。

这时如果某一个 outlier 特别大，就会把整个 group scale 拉大。

所以最优目标反过来了：

> **尽量把能量摊平，避免少数坐标极端突出。**

这就是作者说的 **Great Inversion**。([arXiv][17])

更关键的是作者指出，rotation 的价值与 format 本身强相关：

### MXFP4

scale 是 power-of-two E8M0，精度比较粗。

因此 block 内 flattening / Hadamard rotation 仍然很有价值。

### NVFP4

scale 本身是带 mantissa 的 FP8 scale，而且 block 只有 16。

scale 对真实 max 的拟合能力强得多，因此：

> flattening 带来的收益理论上就应该下降。

这很好地解释了为什么：

**MXFP4 recipe 中 rotation/RHT 经常是核心组成，而 NVFP4 有时能够用更简单的 calibration 就保持很高精度。**

这个结论对比较 NVFP4、MXFP4、Four-Over-Six、Hadamard 的组合非常有用。

# D. 厂商博客与硬件软件栈

本周真正值得单列的厂商公开信息主要来自 NVIDIA 8 月 24 日的 Rubin / Blackwell AgentX 文章。

它提供了一个重要视角：

以前宣传低比特主要是：

**FP4 Tensor Core = BF16 的多少倍 FLOPS**

现在 NVIDIA 的系统叙事明显变成：

**NVFP4 / MXFP4 / MXFP8**
+
**Wide Expert Parallel**
+
**NVLink**
+
**disaggregated P/D**
+
**KV routing**
+
**speculative decoding**

共同决定：

**tokens / second / MW**。([NVIDIA Developer][10])

我认为这比“Rubin FP4 峰值多少 PFLOPS”更值得持续跟踪。

因为对于 DeepSeek-V4、Kimi K3 这种模型，真正受限的经常已经不是单个 GEMM：

* MoE A2A；
* KV movement；
* expert residency；
* long-context attention；
* scale metadata；
* quant producer；
* scheduler；

都进入系统瓶颈。

本周我没有找到 AMD 或 Intel 同级别、直接针对低比特 LLM 推理的新官方技术博客；AMD 的实质进展反而主要集中在 AITER、vLLM、SGLang 的 upstream PR 里，这些代码证据比营销博客更有价值。

# E. 我认为最值得在 B200 / Blackwell 上实际验证的 6 个方向

## 1. 最高优先级：自己复现“NVFP4 storage → selective FP8 compute”

TensorRT-LLM #17985 非常值得拆出来单独实验。

不要只比较：

`KV FP8`
vs
`KV NVFP4`

建议比较三种：

```text
A. FP8 resident KV → FP8 attention

B. NVFP4 resident KV → native NVFP4 attention

C. NVFP4 resident KV
   → gather selected pages
   → temporary FP8 scratch
   → FP8 attention
```

重点测：

* context length；
* active-page ratio；
* staging bytes/token；
* dequant latency；
* attention latency；
* KV capacity；
* TPOT。

我特别想知道：

> **C 相比 B 的 crossover 点到底由 active-page ratio 决定，还是 NVFP4 attention kernel maturity 决定。**

这对以后设计 vLLM 的 NVFP4 KV cache 路径会非常有启发。

---

## 2. 在 B200 上复测 FlashInfer #4480，而不是直接采用 H200 的 6.23×

尤其 sweep：

`M={1,2,4,8,16,32,128,512,2048}`

因为 H200 benchmark 主要是 M≥256。

真正 serving decode 更关心：

**小 M 下，一个 launch 被省掉到底值多少。**

建议 Nsight 对比：

```text
Add/RMSNorm
FP8 quant
scale write
BF16 intermediate traffic
launch gap
```

我预期它在 decode 场景的价值可能更多来自**固定 launch overhead**，而不是 HBM bandwidth。

---

## 3. 专门复现 Humming 的 H100/B200 divergence

这是本周非常好的低比特 debugging case。

同一个：

`MXFP4 W + group128 FP8 A`

分别在：

* H100；
* B200

抓：

* quantized activation bytes；
* scale bytes；
* scale stride/layout；
* Humming kernel input；
* GEMM output；
* 第一层出现 NaN/garbage 的位置。

因为 B200 0.8863 正常而 H100 0.0000，这非常可能帮助厘清：

**同名 dtype != 同一种物理 representation contract。**

---

## 4. vLLM DeepSeek-V4：FlashInfer MoE-EP vs native DeepGEMM

现在 #49636 已经给了一个相对干净的 comparison point：

```text
deep_gemm_mega_moe

vs

flashinfer_moe_ep_mega_deep_gemm

vs

flashinfer_moe_ep_mega_cutedsl
```

在 8×B200 上建议同时 sweep：

* MXFP4 checkpoint；
* NVFP4 checkpoint；
* TP/EP；
* sequence parallel；
* token/rank；
* C1/C8/C32/C64。

目前 DeepGEMM variant 基本 parity，**CuTeDSL 才是真正值得继续看的性能变量**。([GitHub][12])

---

## 5. 把 MXFP8 Expert Parallel 当成独立研究对象

结合上周 FlashInfer 和本周 AITER，可以形成一个非常明确的实验：

```text
BF16 send
→ A2A
→ receiver quant MXFP8

vs

send-side quant MXFP8
→ MXFP8 + E8M0 A2A
→ receiver direct consume
```

分别测：

* NVLink bytes；
* NCCL/MoRI latency；
* sender quant；
* receiver quant；
* MoE；
* overlap。

这可能比单纯再测一个 W4A8 GEMM 有更高研究价值。

---

## 6. TorchAO 32×32 MXFP8：重点研究 scale layout，不只是 bandwidth

B200 上已经做到约 **6 TB/s** cast bandwidth。

更值得看的其实是：

> 32×32 scale representation 能否在 training、checkpoint、serving 之间保持一致，而无需 expand/swizzle/repack。

如果最终：

# `training output layout`

`serving GEMM expected layout`

那么这类工作就不仅仅是训练 kernel，而是在建立真正的：

**training-to-serving native low-bit representation**。

# 本周我最想强调的三个趋势

**第一，KV Cache 正从“全模型一个 dtype”变成“按 layer / consumer 决定 precision”。**

MiniMax-M3 的：

`57层 NVFP4 + 3层 FP8 + Eagle FP8`

可能比“所有 KV 都 FP4”更接近未来真实 deployment。([GitHub][1])

**第二，MXFP8 正从 activation datatype 变成 communication datatype。**

AITER 已经能直接消费 all-to-all 后的 MXFP8；FlashInfer 上周也开始发送低比特 EP payload。以后 W4A8 的评价指标必须增加：

**inter-GPU bytes/token。** ([GitHub][2])

**第三，低比特真正困难的地方越来越不是 FP4 本身，而是 scale 和 layout。**

本周最典型的几件事：

`RMSNorm→FP8 quant fusion`

`scale zero-copy`

`SM107 MXFP8 producer compatibility`

`H100/B200 Humming correctness divergence`

其实都不是发明了一个新 datatype。

它们解决的是：

> **这个 datatype 在真实 serving pipeline 中到底如何被生产、传输、存储、重排和消费。**

我认为这是目前低比特推理工程最值得持续追踪的主线。
