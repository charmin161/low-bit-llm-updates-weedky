## 1. DeepGEMM 正式登陆 Ascend 950：FP4×FP4 已做到 98.3% 硬件理论上限

**状态：[正式发布]｜DeepGEMM-Ascend 初始版本｜9 月 30 日**

这是本周我认为**生态层面影响最大**的一项。

DeepSeek 正式开源 **DeepGEMM-Ascend**，面向 Ascend 950 + CANN 9.20，并且刻意保持与 CUDA DeepGEMM 相同的 API/workflow。首版已经覆盖：

**BF16 / FP8 / FP4 GEMM、MQA logits、MegaMoE。** [GitHub](https://github.com/deepseek-ai/DeepGEMM-Ascend)

更值得看的是公开的 Ascend 950DT 数据：

| 算子 | 实测 | 硬件上限 | 利用率 |
|---|---:|---:|---:|
| FP4×FP4，M4096/N7168/K16384 | 1701 TFLOPS | 1730 | **98.3%** |
| FP8×FP4 | 861 TFLOPS | 865 | **99.5%** |
| FP8×FP8 | 861 TFLOPS | 865 | **99.5%** |
| BF16×BF16 | 431 TFLOPS | 432 | **99.8%** |

DeepSeek Lightning Indexer 的 MQA logits 同样已经有 FP4 路径：prefill 4096×8192 时 FP8 为 302.6 μs、FP4 为 **277.4 μs**；decode 256×8192 时 FP8 150.9 μs、FP4 **124.2 μs**。MegaMoE 则已经做到 EP8 下 dispatch + 两次 grouped GEMM + SwiGLU + combine 的整体融合。[GitHub](https://github.com/deepseek-ai/DeepGEMM-Ascend)

这里还有一个特别值得你关注的细节：**Ascend 的 scale physical representation 和 NVIDIA 不相同。** DeepGEMM-Ascend 将 K 维相邻的两个 UE8M0 scale 打包到一个 `int16`，再按 MN-major 存储，并提供专门的 `transform_sf_into_required_layout`。[GitHub](https://github.com/deepseek-ai/DeepGEMM-Ascend)

这进一步验证了我前几期反复强调的一点：

> **MXFP4 / FP4 只是数学格式；真正的 execution format 还包含 scale packing 和 physical layout。**

因此 DeepGEMM-Ascend 并不是简单“把 CUDA kernel 翻译成 CANN”，而是在尽量维持**上层 API 统一、底层 physical representation hardware-specific**。

这对跨 NVIDIA / AMD / Ascend 的 checkpoint portability 很有价值。

## 2. vLLM + AITER：DeepSeek-V4.1 的 sparse indexer 已经可以直接在 paged MXFP4 K Cache 上算

**状态：[已合入 main]｜vLLM #58671｜9 月 29 日**

[vLLM #58671](https://github.com/vllm-project/vllm/pull/58671?utm_source=chatgpt.com)

这是本周最值得关注的 **MXFP4 Attention/Indexer** 工程工作之一。

DeepSeek-V4.1 在 gfx950/MI355X 上新增两条路径：

**Dense MXFP4：**

`paged MXFP4 K Cache → 直接算完整 logits`

**Sparse MXFP4：**

`paged MXFP4 K Cache`
→ `生成 block maxima/candidate pool`
→ `consumer layer 只对 candidate 算 logits`

最重要的是：**AITER MQA kernel 直接读已经 preshuffle 好的 paged MXFP4 K Cache，不再把 K gather 出来。** Q 同样使用 MXFP4 quantizer；prefill chunk 合到一次 launch，128-token KV page 是推荐布局。[GitHub](https://github.com/vllm-project/vllm/pull/58671)

长上下文 benchmark 很明显。C=32、128 个请求、每个 **350K input + 350 output、5+1 speculation**：

| Path | Total tok/s | Mean TTFT | Mean TPOT |
|---|---:|---:|---:|
| baseline | 19,225 | 378.2 s | 490.8 ms |
| MXFP4 dense | 22,796 | 319.4 s | 412.1 ms |
| **MXFP4 sparse** | **24,863** | **292.3 s** | **380.5 ms** |
| 相对 baseline | **+29.3%** | **-22.7%** | **-22.5%** |

TPOT P99 甚至下降 **26.8%**。而 8K/1K 的普通场景，MXFP4 dense 相比 FP8 只提升约 **3–7%**。[GitHub](https://github.com/vllm-project/vllm/pull/58671)

这个 crossover 很重要：

> **低 bit index cache 的收益随 context length 增长而放大。**

短上下文主要只得到少一点 bandwidth benefit；350K 级上下文下，MXFP4 + sparse candidate pruning 两个因素开始叠加。

准确率方面，GSM8K flexible extract：

- baseline 0.9651 ± 0.0051
- sparse MXFP4 0.9613 ± 0.0053
- dense MXFP4 0.9598 ± 0.0054

至少在这组数据里处于相近波动范围。[GitHub](https://github.com/vllm-project/vllm/pull/58671)

## 4. MpFA：B200 上“QK 用 NVFP4、PV 用 FP8”比全 FP4 Attention 更合理

**状态：[论文]｜arXiv:2609.33135｜9 月 27 日**

这是我认为本周**对你最值得读的一篇 kernel/算法论文**。

论文发现 fully-FP4 Attention 虽然 Tensor Core FLOPS 很高，但并没有自动变成端到端收益，因为：

- Softmax 之后还要重新 FP4 quant；
- scale/conversion 有成本；
- shared/tensor-memory movement；
- softmax pipeline contention。

于是作者不是做 QK4V4，而是：

### **QK4PV8**

`Q × K：NVFP4`

`P × V：FP8`

这样 QK 享受 FP4 Tensor Core throughput，而 PV 不承担 softmax 后 FP4 conversion/scale 的额外代价。[arXiv](https://arxiv.org/abs/2609.33135)

准确率恢复则使用 **rank-one smoothing compensation**，通过额外一次 Tensor Core MMA 做补偿，而不是继续增加 softmax 主路径负担。

B200、16K–128K context、Llama-3.1-8B / Qwen3-14B 上：

**end-to-end output throughput 相比 BF16 FlashAttention-4 达到 2.81×。**

rank-one compensation 能恢复约 **62.5% 的量化准确率损失**，kernel overhead 约 **2%**。[arXiv](https://arxiv.org/abs/2609.33135)

这篇论文最重要的结论不是 2.81×，而是：

> **FP4 不应该被理解为“把整个 Attention 全改 FP4”。**

QK 和 PV 的数值分布、算术密度、softmax 前后位置完全不同。

我认为以后 Attention 很可能会逐渐变成：

**Q precision × K precision × score precision × P precision × V precision**

分别设计，而不是一个“Attention dtype”。

## 5. QATFactory：NVFP4/MXFP4 开始有真正 deployment-aligned 的开源 QAD/QARL

**状态：[论文 + 开源框架]｜9 月 30 日**

QATFactory 的目标不是再做一个 fake-quant QAT，而是把**生产 inference engine 的真实数值语义作为训练规范**。

支持：

- NVFP4
- MXFP4
- llama.cpp Q4_K
- dense / MoE
- Full parameter / LoRA
- QAD
- quantization-aware RL

而 GEMM 本身仍可以在 BF16 做，所以甚至可以在**没有 FP4 Tensor Core 的 H100 上训练 NVFP4 模型**。导出后直接进入 vLLM / SGLang / llama.cpp，不再做第二次有损转换。[arXiv](https://arxiv.org/abs/2609.39223)

Qwen3.5-9B：

| Format | 最佳 PTQ | QAD |
|---|---:|---:|
| NVFP4 | 65.4 | **68.9** |
| MXFP4 | 56.4 | **66.0** |

也就是说 MXFP4 的 training-aware recovery 尤其明显。[arXiv](https://arxiv.org/abs/2609.39223)

更有意思的是论文发现：

- **NVFP4 QAD：训练时只量化 weight 通常更好**
- **MXFP4 QAD：weight + activation 一起量化更好**

也就是说，所谓“deployment faithful”并不意味着训练阶段必须机械复现所有量化噪声。

原因很可能与两个格式的 scale 粒度和 scale precision 不同有关：NVFP4 block=16 + E4M3 scale 本身噪声小，加入 activation FP4 noise 可能更多是在破坏 optimization；MXFP4 的 block=32 + E8M0 更粗，模型则更需要提前适应 activation quant noise。

论文还报告 NVFP4 QARL 相比 **BF16 RL → PTQ** 的路线，end-to-end RL training 提速 **1.23×**，reasoning accuracy 平均提高 2.7 points。[arXiv](https://arxiv.org/abs/2609.39223)

我认为这条线非常重要：低 bit 正从“训练后压缩”走向**deployment numerics-aware post-training**。

## 6. MiniMax-M3：NVFP4 KV Cache 本周同时进入 TensorRT-LLM 和 vLLM

这是一个很强的生态收敛信号。

### TensorRT-LLM #19422｜9 月 26 日 merged

MiniMax-M3 现在采用：

- sparse target layers：**NVFP4 KV**
- dense target layers：FP8 KV
- shared Eagle3 draft layer：FP8 KV

NVFP4 sparse decode 由 MSA/TRTLLM Triton kernel 消费，并限制在 SM100/SM103。4×B200、TP4/EP4 的 full-model 验证：

- ordinary NVFP4 KV：MMLU **84.479%**，GSM8K **88.704%**
- NVFP4 KV + Eagle3：MMLU **84.747%**，GSM8K **90.485%**
- Eagle acceptance rate **0.832**
- mean accepted length **3.497**

[TensorRT-LLM #19422](https://github.com/NVIDIA/TensorRT-LLM/pull/19422?utm_source=chatgpt.com)

### vLLM #59300｜10 月 2 日凌晨 merged

vLLM 随后也把 M3 sparse MSA 接到：

`--kv-cache-dtype nvfp4`

而且路径做得更彻底：

`QK norm`
→ `RoPE`
→ **K/V NVFP4 quant**
→ `写 paged cache`

在**同一个 fused insert kernel**中完成。

每个 128-dim K/V head 的物理 slot 直接包含：

`packed E2M1 data + E4M3 block scale`

prefill 和 decode 都原地读 NVFP4 page；NVFP4 decode 不允许退回不支持该 layout 的 Triton backend，而是固定选择 CUTLASS，unsupported geometry 直接报错，而不是静默 fallback。

[vLLM #59300](https://github.com/vllm-project/vllm/pull/59300?utm_source=chatgpt.com)

另外，Q 会直接写 FP8 query buffer，CUTLASS decode 直接消费，不再额外保存一份 BF16 query。

这说明 MiniMax-M3 正形成一个很典型的 precision hierarchy：

**sparse target KV → NVFP4**

**dense attention KV → FP8**

**draft KV → FP8**

**query → FP8**

而不是全模型“统一 FP4 KV”。

## 7. FlashInfer：SM120/SM121 正式加入 native NVFP4 W4A4 CuTe DSL，并与 W4A16 共用同一份权重

**状态：[已合入 main]｜#5100｜10 月 1 日**

这项对 DGX Spark / RTX Blackwell 特别有意思。

新 kernel 直接消费：

`canonical packed NVFP4 weight`
+
`physical 128×4 E4M3 scale`

**不 repack，也不创建第二份 weight copy。**

因此同一份 NVFP4 weight 可以同时供：

`W4A4 kernel`

和

`W4A16 kernel`

使用，为 runtime **dynamic W4A4/W4A16 selection** 铺平了道路。[GitHub](https://github.com/flashinfer-ai/flashinfer/pull/5100)

DGX Spark SM121，27B down projection `N=5120,K=17408`：

- M=4096：比 default CUTLASS **1.69×**
- M=8192：**2.13×**
- 两边都 autotune 后：1.17× / 1.41×

但整个 shape grid 很能说明问题：

| 范围 | CuTe DSL vs autotuned CUTLASS |
|---|---:|
| M ≤ 16 | **1.071×** |
| M = 64 | **1.052×** |
| M ≥ 128 | **0.942×** |
| 全部 159 shape | **1.026×** |

也就是说**它不是全面胜出**。[GitHub](https://github.com/flashinfer-ai/flashinfer/pull/5100)

更重要的趋势是：

> 同一份 NVFP4 checkpoint，不同 M 可以动态决定到底使用 W4A4 还是 W4A16。

这比“模型是 NVFP4，所以一定走 FP4 activation”更合理。

## 10. ModelOpt：weight/activation 和 KV quantization 开始进入同一个 AutoQuant workflow；同时修了一个危险的 NVFP4 fake-quant bug

**状态：[均已合入 main，本周没有新的 tagged release]**

ModelOpt #2273 把已有 GEMM AutoQuant 与 **KV-cache AutoQuant**组合起来：

- fixed FP8 GEMM PTQ + mixed-KV AutoQuant；
- gradient-based NVFP4/FP8 GEMM AutoQuant + 独立 KV AutoQuant；
- KV 有自己的 candidates / constraint / calibration/checkpoint；
- 做 KV candidate calibration 时，已经选定的 weight/activation QDQ 保持生效但冻结。

[ModelOpt #2273](https://github.com/NVIDIA/Model-Optimizer/pull/2273?utm_source=chatgpt.com)

这个方向我认为很正确。未来 AutoQuant 的优化变量不会只有：

`哪个 layer 用 FP8 / NVFP4`

而应该包含：

`weight precision × activation precision × KV precision`。

同周 #2549 修复了一个很值得加入 regression test 的 NVFP4 问题：

dynamic Triton fake-quant 对 **FP8 block scale < 1e-5** 的情况错误地用 `1.0` 替换，本意只是防 divide-by-zero，却导致 `max|x| ≲ 6e-5` 的整个 block 被量化成零。Static kernel、CUDA fallback 和 export 路径并没有这个 floor，所以**训练/fake-quant numerics 与真实 checkpoint numerics 不一致**。

[ModelOpt #2549](https://github.com/NVIDIA/Model-Optimizer/pull/2549?utm_source=chatgpt.com)

此外，ModelOpt 在 10 月 1 日正式注册 **IQ1_M 1.75 bit/weight** 的 GGML CUDA encoder/recipe。它不是 Tensor Core native format，而是超低比特 GGML/llama.cpp 类 deployment format，但意味着 ModelOpt 现在也开始覆盖 1–2 bit 的 IQ family。

[ModelOpt IQ1_M #2595](https://github.com/NVIDIA/Model-Optimizer/pull/2595?utm_source=chatgpt.com)

# C. 本周新论文

除上面的 **MpFA** 与 **QATFactory**，我再保留一篇真正有新思路的论文。

## QuantForge / HiRes：MXFP4 PTQ 不再把 transform、code assignment、residual correction 分开优化

**arXiv:2609.34680｜9 月 28 日**

QuantForge 用程序演化去搜索 MXFP4 PTQ algorithm，但真正值得看的结果是它找到的 **HiRes**。

HiRes 会顺序处理：

`coordinate shaping`
→ `合法 MXFP4 code reassignment`
→ `attention residual recovery`
→ `MLP residual recovery`

关键是每一步看到的是**前面步骤执行完以后留下的真实 residual**，而不是每种 technique 独立优化。[arXiv](https://arxiv.org/abs/2609.34680)

论文在 7 个 task 上报告：

- 7-model Robust Fit **0.09300，为比较方法最低**
- 32B 的 quantized Fit-7 最低

而 QuantForge 自身在固定 240 evaluator calls 下，8 次搜索里 **6 次**找到能迁移到 held-out target 的方案；textual-memory / reflection 都只有 3/8，score-only 1/8。[arXiv](https://arxiv.org/abs/2609.34680)

这篇对工程的启示是：

> **MXFP4 的误差不是某一个 quantizer 局部产生的，而是 transform → block scaling → rounding → residual propagation 的连锁反应。**

如果未来要把 rotation、H-Scale、GPTQ、4over6 一类方法组合起来，最好也按这种 sequential residual 的视角评价，而不是把每个模块独立调到局部最优。

# E. 我建议下一步在 B200 / Blackwell 上优先验证的 6 个方向

## 1. 最高优先级：复现 MpFA 的 QK4PV8，而不是继续假设“全 FP4 Attention 最优”

建议至少做四条：

```text
BF16 QK + BF16 PV
FP8 QK + FP8 PV
NVFP4 QK + NVFP4 PV
NVFP4 QK + FP8 PV
```

context sweep：

`16K / 32K / 64K / 128K`

分别抓：

- Q/K quant；
- QK MMA；
- online softmax；
- P quant；
- PV MMA；
- tensor/shared-memory traffic；
- total attention latency；
- E2E TPOT。

论文给出的 2.81× 很大，我会特别想验证：

> **QK4PV8 相比 QK4PV4 的真实差距到底有多少来自省掉 softmax 后 FP4 quant，又有多少来自 PV Tensor Core 本身。** [arXiv](https://arxiv.org/abs/2609.33135)

如果这个结论能在 GLM/DeepSeek MLA/DSA 类结构上复现，其意义会明显超过普通 NVFP4 GEMM 调优。

---

## 2. MiniMax-M3：直接比较 vLLM 与 TRT-LLM 的 NVFP4 sparse KV physical path

两边现在本周都已经合入了同一类功能。

重点不要只比 E2E tok/s，而是审计：

```text
KV producer
scale generation
physical page layout
Q dtype
prefill consumer
decode consumer
fallback policy
```

特别值得验证 vLLM 的：

`Norm + RoPE + NVFP4 KV insert`

是不是确实完全不 materialize BF16/FP8 K/V intermediate。

同时检查：

- E2M1 payload；
- E4M3 scale；
- per-head slot；
- 128-token page；
- global K/V scale。

这可能是目前最干净的**原生 NVFP4 KV producer→consumer pipeline**之一。

---

## 3. 在 B200 上再做一次 W4A4 / W4A8 / W4A16 concurrency crossover，而不是只做 GEMM M sweep

AMD 本周的数据特别有参考价值：

- C1：A4W4 比 A8W4 **慢 1%**
- C8：基本持平
- C64：A4W4 **快 10.5%**

说明决定 crossover 的不仅是 GEMM M，还有真实 serving concurrency、routing 和 quant producer。

B200 上建议统一 checkpoint/source：

```text
NVFP4 W4A4
NVFP4/MXFP4 W4A8
NVFP4 W4A16
```

测：

`C1 / C4 / C8 / C16 / C32 / C64 / C128`

然后把 FP4 activation quant 单独从 MoE GEMM 里剥出来。

这样你最终得到的不是一张“哪种 bit 理论 FLOPS 高”的表，而是一张真正可以指导 backend dispatch 的：

**concurrency × expert-M × precision crossover map。**

---

## 4. 给所有 NVFP4 fake-quant / 伪量化内核增加“小尺度 block poison test”

ModelOpt #2549 暴露的问题特别适合加入你的量化 kernel correctness suite。

建议构造 block：

```text
amax = 0
1e-8
1e-7
1e-6
1e-5
3e-5
6e-5
1e-4
```

比较：

`Python oracle`

`Triton fake quant`

`CUDA quant`

`checkpoint export`

`真实 FP4 dequant`

确保 scale floor、zero handling、RNE 完全一致。

如果 fake quant 和真正 inference 数值在小 activation 上不一致，那么后续拿它研究 KV/Attention 精度的结论可能从根上就是错的。

---

## 5. DeepGEMM locality-aware MegaMoE：B200 上建议同时测功率、频率，不只测 latency

#462 的 **100 W 节省 + 5–10% clock 提升**是一个很有意思的新维度。[GitHub](https://github.com/deepseek-ai/DeepGEMM/pull/462)

建议固定：

- model/expert layout；
- token routing；
- batch；
- power cap；

对比：

`normal MegaMoE`

vs

`weight-localized MegaMoE`

记录：

`kernel latency`
`SM clock`
`GPU power`
`HBM power/bandwidth`
`Tensor Core active`
`tok/s/W`

如果 locality 真能减少跨-domain 数据流并降低功耗，那么未来低 bit MoE 的优化目标就不再只是：

**tok/s**

而应该增加：

**tok/s/W。**

对于 Rubin/NVL72 这可能会越来越重要。

## 6. QATFactory：值得做一组 NVFP4 “W-only QAD vs W+A QAD”复现

这个结果有点反直觉，所以非常值得验证。

同一个 BF16 checkpoint：

```text
PTQ NVFP4
QAD: weight-only fake NVFP4
QAD: weight + activation fake NVFP4
```

最终三者**全部导出相同 W4A4 NVFP4 deployment format**。

然后比较：

- calibration/training stability；
- loss；
- LiveCodeBench；
- reasoning benchmark；
- logit drift；
- 真正 vLLM/SGLang serving accuracy。

如果论文结论成立，那么它意味着：

> **最佳 training numerics 不等于严格复制 inference numerics。**

这对后续做 NVFP4 post-training/RL 会是非常重要的 recipe 设计原则。[arXiv](https://arxiv.org/abs/2609.39223)

# 本周我认为最重要的四个判断

**第一，FP4 已经正式变成跨硬件生态的 execution format，而不是 NVIDIA 特有故事。** Ascend 950 的 DeepGEMM 已经公开 FP4×FP4、FP8×FP4、FP4 MQA 和 MegaMoE，而且 FP4 GEMM 达到 98%+ hardware limit。真正无法直接跨平台复制的，是 **scale packing / memory layout / hardware pipeline**。[GitHub](https://github.com/deepseek-ai/DeepGEMM-Ascend)

**第二，“越低 bit 越快”这个规则在 Attention 和 MoE 两边同时失效。** MpFA 发现 PV 保 FP8 比完全 FP4 更合理；AMD 则发现 A4W4 在 C1 甚至略输 A8W4，但 C64 明显赢。真正优化对象应该是：

**算子阶段 × M/concurrency × quant cost × memory traffic × consumer kernel。**

**第三，低比特 KV 正越来越接近真正的 native representation，而不再是“把 cache 压缩一下再解回来”。** 本周的 DeepSeek-V4.1 MXFP4 indexer 和 MiniMax-M3 NVFP4 sparse attention 都已经做到直接从 low-bit paged cache 读取、直接计算，没有完整高精度 K materialization。[GitHub](https://github.com/vllm-project/vllm/pull/58671)

**第四，低比特研究正在从 PTQ 配方走向“训练—checkpoint—runtime 一体化 numerical contract”。** QATFactory 在训练阶段模仿最终 engine semantics；ModelOpt 开始同时优化 GEMM 和 KV precision；FlashInfer 把 4over6 从环境变量提升为显式 QuantConfig；DeepGEMM 又进一步把 packed UE8M0 scale 变成正式 API contract。

如果本周只选**三个最值得马上动手验证**的方向，我会排：

1. **MpFA QK4PV8**——因为它直接挑战“Attention 全 FP4 最优”这个直觉；
2. **MiniMax-M3 NVFP4 sparse KV producer→consumer path**——因为 vLLM/TRT-LLM 已经同时进入可验证状态；
3. **W4A4/W4A8/W4A16 的真实 serving crossover**——因为现在 NVIDIA 和 AMD 两边都已经有足够完整的 backend，可以不再只做理论判断。
