# 低比特大模型推理周报
## 2026 年 10 月 16 日—10 月 23 日

**统计截至：2026 年 10 月 23 日上午（北京时间）**

本周最重要的变化，我归纳为四条。

**第一，低比特 Attention 的混合精度开始出现更清晰的 Accuracy–Performance Trade-off。** FlashInfer 在 MiniMax-H3 上合入了 NVFP4-QK + FP8-PV kernel。实验显示，PV 保持 FP8 能明显改善数值误差，但并不是最快方案：全 FP4 路径仍然具有性能优势。

**第二，原生 FP8 KV Cache 的价值进一步得到验证。** TensorRT-LLM 针对 GLM-5.3-Flash，删除了 FP8 KV → BF16 → FlashMLA 的中间转换。在 4×B200 上，配合 cache-update fusion，C8 aggregate throughput 达到原来的 **2.13×**。

**第三，低比特格式与稀疏计算的关系出现了一项值得认真研究的新结论。** 10 月 20 日的新论文直接比较降低数值精度与引入 2:4 sparsity，发现当硬件还存在更低精度执行路径时，直接降 bit 往往比增加 2:4 sparsity 更值得；但达到硬件最低精度后，稀疏性仍可能提供额外收益。

**第四，本周出现两个非常典型的 correctness 风险：Expert Parallel 的跨 rank scale 不一致，以及 KV 分层缓存恢复时遗漏 sparse-indexer state。** 两个问题都可能导致模型正常运行却输出错误结果。

版本方面，**vLLM 0.32.0、SGLang 0.5.22、AITER 0.1.26** 已正式发布；TensorRT-LLM 发布了 **1.4.0rc1 预览版**。ModelOpt 发布了 **0.48.0rc1 预览版**，LLM-Compressor 则发布了 0.14.0.1 依赖修复版本。[GitHub](https://github.com/vllm-project/vllm/releases)

# A. 本周最重要的 9 项进展

## 1. FlashInfer：MiniMax-H3 正式合入 NVFP4-QK + FP8-PV Attention

**状态：[已合入 main，实验性 opt-in]**

**日期：10 月 21 日**

**PR：[FlashInfer #6936](https://github.com/flashinfer-ai/flashinfer/pull/6936?utm_source=chatgpt.com)**

这是本周我认为最值得从 Attention 数值设计角度研究的一项工作。

### 1.1 三条不同的 Attention 路径

FlashInfer 在 SM120 上为 MiniMax-H3 的 packed-variable-length Attention 提供了三种可比较的实现：

| 路径 | QK 计算 | PV 计算 | 定位 |
|---|---|---|---|
| FP8 baseline | FP8 | FP8 | 已有基准实现 |
| NVFP4 default | NVFP4 | FP4 | 优先优化性能 |
| **NVFP4 hybrid** | **NVFP4** | **FP8** | **改善量化误差** |

新的 hybrid 路径通过：

```python
minimax_h3_sm120_varlen_attention_nvfp4(
    ...,
    pv_mode="fp8",
)
```

显式启用。

它没有替换原来的 `pv_mode="fp4"`，因此属于新增的可选精度策略，而不是默认行为改变。

整个算子包含统计、量化以及 Attention 计算等阶段，共通过三个 launch 执行。[GitHub](https://github.com/flashinfer-ai/flashinfer/pull/6936)

### 1.2 性能数据

作者在 RTX 5090 和 RTX PRO 6000 Blackwell Server Edition 上测试了实际生产 workload 的代表性 shape。

比较的是 **完整 Attention 算子时间，包含输入量化**，而不是仅计时 MMA。

| 硬件 | Hybrid vs FP8 baseline | Hybrid vs 默认全 FP4 |
|---|---:|---|
| RTX 5090 | **1.381×** | 更慢 |
| RTX PRO 6000 | **1.188×** | 更慢 |

例如 RTX 5090 上约 33K token 的测试：

| 实现 | Latency |
|---|---:|
| FP8 baseline | 75.25 ms |
| NVFP4-QK + FP8-PV | 55.20 ms |
| NVFP4 default | **41.64 ms** |

所以 Hybrid 的价值不是最高吞吐，而是数值质量。

相对 FP32 reference：

- Hybrid relative L2 error：**0.136–0.143**
- 默认 FP4 relative L2 error：**0.186–0.193**

也就是说，PV 保持 FP8 显著改善了输出误差，同时仍然快于原来的 FP8 Attention。[GitHub](https://github.com/flashinfer-ai/flashinfer/pull/6936)

### 1.3 与 MpFA 有什么关系？

前几周我们讨论过 MpFA 的 QK4PV8。

这次 FlashInfer 的工作说明同样的设计原则开始在真实模型专用 kernel 中落地：

**QK 与 PV 不应该被迫使用相同 precision。**

不过，也需要注意一个区别。

MpFA 重点讨论 FP4/FP8 Attention 的整体计算组织；这次实现针对 MiniMax-H3、SM120 和 packed-varlen workload，是一个高度专用的执行路径。

目前不能直接将这些性能数字推广到 B200 的 GLM/DeepSeek MLA。

### 技术判断

这项工作值得记住的不是“FP8-PV 比 FP4-PV 快”。

实际上本次测试恰恰相反。

它证明的是：

> **在 QK 已经使用 FP4 的前提下，PV 保留 FP8 可以成为一个有价值的 Accuracy–Performance Pareto 点。**

对于长上下文 Attention，今后需要独立考虑 QK quantization error、softmax amplification 和 PV quantization error。

## 2. TensorRT-LLM：GLM-5.3-Flash 原生 FP8 Sparse MLA，C8 吞吐达到 2.13×

**状态：[已合入 main]**

**日期：10 月 21 日**

**PR：[TensorRT-LLM #20454](https://github.com/NVIDIA/TensorRT-LLM/pull/20454?utm_source=chatgpt.com)**

这是本周**最值得直接在 B200 上复现的推理性能优化**。

### 2.1 原来的低效路径

GLM-5.3-Flash 使用 sparse MLA。

当 KV Cache 使用 FP8 时，原来的 `glm_kpool` 路径仍然执行：

```text
FP8 KV Cache
      ↓
Gather selected KV
      ↓
Dequantize to BF16
      ↓
BF16 FlashMLA
      ↓
Attention output
```

问题在于：

**KV 已经是 FP8，但 Attention consumer 仍然要求 BF16。**

所以减少 KV storage bytes，并不意味着减少了完整 Attention 数据流的转换开销。

### 2.2 新路径

现在改成：

```text
FP8 KV Cache
      ↓
Sparse candidate selection
      ↓
TRTLLM-GEN native FP8 Sparse MLA
      ↓
Attention output
```

对于每 rank 16、32、64 个 query heads 的配置，FP8 sparse KV 可以直接进入原生 kernel。

适用组合包括：

- TP4；
- TP2；
- Attention DP；
- Context 与 Generation；
- CUDA Graph。

BF16 KV 则仍然保留原来的执行路径。

另外，这个 PR 还优化了两处相关开销。

**第一，融合 KV 与 Indexer Cache 更新。**

原来需要分开执行 page/index 计算、KV 写入和 indexer state 写入。

现在通过 `append_paged_state_rows`，一次 Triton launch 同时更新 latent KV 和 packed indexer state。

Speculative decode 的多个 draft positions 也可以在一次 kernel 中处理。

**第二，删除 Context Row 构建时不必要的 Host Synchronization。**

位置和 request-id tensor 改为异步 H2D staging。[GitHub](https://github.com/NVIDIA/TensorRT-LLM/pull/20454)

### 2.3 B200 实测

配置：

- 4×B200；
- GLM-5.3-Flash NVFP4 checkpoint；
- FP8 KV Cache；
- TP4 / EP4；
- MTP3；
- ISL=13,312；
- OSL=33；
- 每组中位数取自 3 次运行。

| 指标 | Baseline | 全部优化后 | 变化 |
|---|---:|---:|---:|
| C1 TTFT | 558 ms | **268 ms** | **-52%** |
| C1 ITL | 3.20 ms | **2.87 ms** | -10.3% |
| C1 tok/s/user | 313 | **348** | +11.2% |
| C8 TTFT | 2406 ms | **1051 ms** | **-56.3%** |
| C8 aggregate tok/s | 60.6 | **129.1** | **2.13×** |

值得注意，性能收益的最大部分来自**原生 FP8 Sparse MLA**，后面的 fused cache update 和 asynchronous context-row 进一步改善性能。

代价是原生 kernel workspace 略增，GPU KV pool 从 74.25 GiB 降到 74.22 GiB，变化很小。[GitHub](https://github.com/NVIDIA/TensorRT-LLM/pull/20454)

### 2.4 精度是否下降？

作者测试：

- 原路径 GSM8K：92.38；
- 新路径 GSM8K：93.44；
- MTP acceptance length：3.399 → 3.403。

GSM8K 差异被作者归入 run-to-run noise，不能据此宣称新 Attention kernel 提升了模型准确率。[GitHub](https://github.com/NVIDIA/TensorRT-LLM/pull/20454)

### 我的判断

这项工作可以视作最近几个月低比特系统优化的一个典型案例：

> **真正大的收益，不一定来自把 FP8 再压成 FP4，而可能来自删除 FP8→BF16→Attention 的格式往返。**

尤其对于 sparse attention，应该重点关注：

`KV storage format × candidate-gather format × native consumer format`

三者是否一致。

## 3. 新论文：降低 bit 数与增加 2:4 Sparsity，究竟哪个更值得？

**状态：[论文]**

**日期：10 月 20 日**

**arXiv：2610.28947**

[论文原文：Is 2:4 Sparsity Still Worth It?](https://arxiv.org/abs/2610.28947?utm_source=chatgpt.com)

这篇与 NVFP4、MXFP4，以及你持续关注的 Rubin 2:4/adaptive compression 有直接联系。

### 3.1 论文要回答的问题

假设有一个 FP8 GEMM。

现在有两个优化选择：

**方案 A：进一步降低精度。**

```text
Dense FP8
    ↓
Dense FP4
```

**方案 B：引入半结构化稀疏。**

```text
Dense FP8
    ↓
2:4 Sparse FP8
```

哪一个更好？

作者没有只比较理论 FLOPS，而是同时考虑：

- 量化误差；
- 结构化剪枝误差；
- Sparsity metadata；
- 实际 GEMM kernel；
- Runtime quantization/pruning；
- 不同 GPU 世代；
- 完整模型恢复训练。

### 3.2 核心结论

论文报告：

**当硬件仍提供更低精度执行模式时，直接降低精度通常优于增加 2:4 sparsity。**

其原因是：

对于每 4 个数保留 2 个的稀疏方案，被删除的两个数会产生不可忽略的剪枝误差。

即使数值格式变得更精细，也不会让被剪掉的权重重新出现。

相比之下，量化误差能够随数值精度增加而减小。

但当已经达到硬件支持的最低精度时，情况又不同。

此时引入 2:4 sparsity，论文报告：

- Linear GEMM 加速 **1.3–1.7×**；
- H100 上 FP8 + retrained 2:4 sparse model；
- vLLM prefill throughput **+27%**；
- GSM8K accuracy 与 dense FP8 基本相当。

不过作者也发现：PPL 往往比 reasoning capability 更容易通过 retraining 恢复。

Blackwell 的 sparse FP4 实验中，论文研究的 pairwise 4:8 pattern 带来更大的质量损失，在作者使用的训练预算内没有完全恢复。[arXiv](https://arxiv.org/abs/2610.28947)

### 3.3 对 Rubin 有什么启示？

前几周 CUTLASS 4.8 公开了 Rubin 的 FP4 sparse MMA 接口。

但这篇论文给了一个非常重要的提醒：

**硬件支持稀疏执行，不代表实际模型一定适合稀疏化。**

至少需要区分：

1. Dense FP8 → Dense FP4；
2. Dense FP8 → Sparse FP8；
3. Dense FP4 → Sparse FP4。

前两条是不同优化方向，第三条则是在最低精度基础上叠加稀疏。

此外，Rubin 的硬件 sparse contract 与论文测试的 Blackwell kernel 不能直接等同。

因此论文的结论对 Rubin 具有研究参考价值，但**不能直接推导 Rubin FP4 2:4 必然快多少或精度损失多少**。

### 我建议关注的研究问题

对 NVFP4 E2M1 来说，2:4 sparsity 与 block scale 并非完全独立。

例如剪枝可能改变：

- block `amax`；
- 最优 FP8 scale；
- FP4 code assignment；
- activation error；
- expert 输出分布。

因此比简单的：

`Prune → RTN`

更值得研究的可能是：

**Pruning mask 与 NVFP4 scale/code 联合优化。**

这一点属于进一步研究建议，不是论文已证明的结果。

## 4. 新论文：UE5M3 Scale 在 FP4 下出现有吸引力的硬件—精度 Pareto 点

**状态：[论文 / 硬件设计研究]**

**日期：10 月 19 日**

**arXiv：2610.26083**

[MX-Like Tensor Core for LLM Inference](https://arxiv.org/abs/2610.26083?utm_source=chatgpt.com)

这篇是本周我认为最值得从硬件数值格式角度阅读的工作。

### 4.1 研究背景

当前最常见的两套原生 FP4 scaling 方案是：

**MXFP4：**

```text
FP4 E2M1
+
Block32 UE8M0 scale
```

**NVFP4：**

```text
FP4 E2M1
+
Block16 E4M3 scale
+
FP32 Tensor Global Scale
```

两者主要区别不仅是 block size，还包括 scale 是否具有 mantissa、是否包含 tensor-level global scale。

论文进一步研究：

> 如果 scale 也是一种可以独立设计的 8-bit 数值格式，哪些 exponent/mantissa 分配更值得采用？

作者系统探索不同的 8-bit scale representation，以及 weight/activation 使用不同精度时的准确率和硬件成本。

### 4.2 重点结果

论文发现，在比较激进的 FP4 quantization regime 下，scale representation 仍然具有重要影响。

其中 **UE5M3** 是一个较有吸引力的选择。

相对论文构造的 NVFP4-like baseline：

- PPL degradation 最多降低 **25.3%**；
- 设计面积额外增加 **0.06%**；
- 功耗额外增加 **0.49%**。

这是在作者基于开源 SNAX NPU 平台的 HW/SW co-design 中得到的结果。[arXiv](https://arxiv.org/abs/2610.26083)

### 4.3 需要注意的边界

这里的 NVFP4-like baseline **没有使用 per-tensor scaling**。

因此，不能直接理解成：

> UE5M3 相比 NVIDIA 现有完整 NVFP4 配方提升 25.3%。

这会错误地忽略 NVFP4 tensor-global scale 的作用。

同样，论文的面积和功耗也不是 B200/Rubin 的真实芯片数据。

### 技术判断

这项工作与 CUTLASS 4.8 新增的 Rubin UE5M3 scale-factor 接口在研究方向上高度相关。

它进一步表明：

**低比特硬件设计不能只比较 value format，还必须把 scale format 作为独立设计变量。**

但目前只能确认存在这样的软件接口与论文研究结果，不能断言 NVIDIA Rubin 采用了该论文的硬件实现。

## 5. TensorRT-LLM：GLM-5.3 NVFP4 MoE 修复跨 Expert-Parallel Rank 的 Scale Contract

**状态：[已合入 main]**

**日期：10 月 20 日**

**PR：[TensorRT-LLM #20547](https://github.com/NVIDIA/TensorRT-LLM/pull/20547?utm_source=chatgpt.com)**

这是本周最值得所有做 NVFP4 MoE 的人注意的 correctness fix。

### 5.1 问题背景

在某些 NVFP4 fused-MoE 实现中，所有 experts 的 `input_scale` 会共同参与形成一个 layer-wide activation scale。

例如：

\[
s_{\text{layer}}=\max_e s_e
\]

实际 loader 会根据 quantization contract 收集所有 experts 的 scale。

但开启 Expert Parallel 后，GLM-5.3 的 loader 之前只收集**当前 rank 本地 experts**的 scale。

于是每张 GPU 得到的 `s_layer` 可能不同。

### 5.2 为什么这会导致 silent error？

假设：

**GPU A：**

`activation quant scale = s_A`

**GPU B：**

`activation quant scale = s_B`

GPU A 负责将 token 量化并 dispatch 到 GPU B。

但 GPU B 执行 GEMM 时，却按照自己的 scale contract 做 rescaling。

如果：

\[
s_A\neq s_B
\]

就可能引入一个额外的比例因子。

结果是：

**MoE output 数值错误，但 kernel 可能完全正常结束。**

### 5.3 修复方式

对于 expert weights：

**仍然只加载本地负责的 experts。**

但对于 `input_scale`：

**需要收集所有 experts 的对应 scale，以满足全局 layer scale 的语义。**

作者在 4×B200、Attention DP + EP4 上复现了数据不完整问题：

```text
Expected input scales: 288 experts

Previously loaded:
72 / 288 experts
```

修复后所有需要的 scale 都会被收集。[GitHub](https://github.com/NVIDIA/TensorRT-LLM/pull/20547)

### 5.4 一个重要 caveat

当前公开的 `nvidia/GLM-5.3-Flash-NVFP4` checkpoint，在对应的 42 个量化 MoE layers 中，288 个 experts 的 `input_scale` 实际相同。

因此这次 bug **并没有导致当前官方 checkpoint 可确认的 accuracy regression**。

它主要修复了未来 per-expert scale 不完全相同时会出现的错误，同时也解决了某些 MegaMoE-CuTeDSL 加载路径的兼容问题。[GitHub](https://github.com/NVIDIA/TensorRT-LLM/pull/20547)

### 我的判断

这项工作给出了一个很重要的结论：

> **Scale 的归约范围本身就是量化格式定义的一部分。**

同样叫 NVFP4 activation scale，实际可能具有：

- per-block；
- per-tensor；
- per-expert；
- per-layer；
- cross-rank shared；

不同语义。

对于 EP/DP 模型，错误地把 global scale 当作 rank-local scale，可能产生比普通 FP4 rounding error 更严重的问题。

## 6. SGLang：分层 KV Cache 恢复时遗漏 Indexer State，导致 EAGLE Acceptance 崩溃

**状态：[Open Issue，尚未确认已修复]**

**日期：10 月 21 日**

**Issue：[SGLang #45563](https://github.com/sgl-project/sglang/issues/45563?utm_source=chatgpt.com)**

这是本周我认为**最值得记入长期低比特 KV Cache 测试集**的故障案例。

### 6.1 问题场景

模型：

**GLM-5.3-NVFP4**

运行配置：

- 8×B200；
- SGLang 0.5.18；
- FP8 KV Cache；
- DSA；
- Attention DP；
- EAGLE speculative decoding；
- HiCache；
- NIXL L3；
- NVMe host/offload storage。

这里需要同时持久化两类状态：

```text
MLA KV Cache

DSA Indexer State
```

只有 MLA KV 还不够，因为 sparse attention 的 top-k 选择仍依赖 indexer。

### 6.2 出错过程

当前某种 INDEXER page 的大小为：

**667,392 bytes。**

但在使用 `O_DIRECT` 的 POSIX storage path 中，buffer/page 需要满足相应的对齐约束。

该对象没有正确 padding，结果：

`Indexer write → EINVAL`

但软件依然在文件系统中创建了对应对象。

最终出现：

```text
MLA KV object:
正常写入

Indexer object:
文件存在，但大小为 0 bytes
```

下一次其他 DP rank 复用共享前缀时：

- 根据文件存在性判断为 cache hit；
- 读取 0-byte indexer；
- zero-filled buffer 被当成恢复结果；
- scheduler 认为整个 prefix 已经恢复。

最终：

**MLA KV 正常，但 Indexer K 和 scale 全零。**

模型不会必然 crash，却会改变 sparse top-k 结果，并使 EAGLE acceptance collapse。

作者在实际环境中观察到约 16.8 万个 indexer 对象全部是 0 bytes。[GitHub](https://github.com/sgl-project/sglang/issues/45563)

### 6.3 为什么这对低比特 KV 特别重要？

以前我们一般验证：

`KV quant`

→ `KV store`

→ `KV reload`

→ `KV dequant`

但现在大型模型的完整缓存状态可能包括：

```text
Compressed KV
Indexer K
Indexer Scale
Top-k Metadata
RoPE State
MTP/Draft State
Recurrent State
```

如果只验证主 KV bytes 是否 byte-exact，而忽略 indexer sidecar，那么 cache 看起来可能是完整的，但生成结果仍然错误。

### 技术结论

对于支持 KV offload / prefix reuse 的低比特 Attention：

**Cache hit 必须意味着完整模型状态已恢复，而不能只意味着主要 KV 文件存在。**

建议后续把：

`object size`

`alignment`

`checksum`

`state-family completeness`

加入回归验证。

目前这是开放 Issue，并非 SGLang 已经发布了正式修复。

[vLLM v0.32.0](https://github.com/vllm-project/vllm/releases/tag/v0.32.0?utm_source=chatgpt.com)

这是本周最重要的正式框架发布之一。

vLLM 在 Release Highlights 中明确将：

**Low-precision KV Cache Everywhere**

作为重点。

新增或正式纳入版本的能力包括：

| 平台 | 低比特 KV 能力 |
|---|---|
| SM8x | NVFP4 KV Cache |
| SM90 | NVFP4 KV Cache |
| SM12x | NVFP4 KV Cache + XQA decode |
| SM100 | MiniMax-M3 sparse NVFP4 KV |
| ROCm | `ultraquant_4bit` KV |

另外，GLM-5.x 在 SM100 上默认采用 FP8 KV，减少约一半 KV memory per rank。

对应 PR 的 benchmark 中，output throughput 提高 **2.3%–5.5%**，但 TTFT 增加 **7%–11%**。[GitHub](https://github.com/vllm-project/vllm/releases)

### 7.1 支持 NVFP4 KV，不等于支持 native NVFP4 Attention

这里需要特别强调。

不同 GPU 架构下，NVFP4 KV Cache 的计算路径可能完全不同。

例如 H100/SM90 不具备 Blackwell 原生 FP4 Tensor Core 能力。

所以即使：

`KV Cache dtype = NVFP4`

实际 consumer 也可能采用软件解量化或其他转换路径。

因此应该区分：

**Low-bit storage support**

与：

**Low-bit native arithmetic support**

这是两个完全不同的能力。

### 7.2 对 GLM 系列的意义

GLM-5.x 默认 FP8 KV 的改变进一步说明：

**在真实系统中，FP8 有时比 NVFP4 更容易达到较好的总体 Pareto 点。**

NVFP4 可以进一步降低存储字节数，但它可能引入：

- 更复杂的 scale generation；
- 缺少对应 native consumer；
- 更昂贵的中间转换；
- 更高的 prefill quantization overhead。

因此最终应通过实际 backend 和完整数据流判断，而不是单纯按 bit 数排序。

# C. 本周论文：三篇值得深入阅读

除了 A 部分已经详细分析的 **2:4 Sparsity vs Quantization** 和 **MX-Like Tensor Core**，本周还有一篇训练侧工作值得关注。

## PACT：消费级 GPU 上的原生 NVFP4 Data-Flow LoRA Fine-Tuning

**日期：10 月 18 日**

**arXiv：2610.25048**

[PACT 论文原文](https://arxiv.org/abs/2610.25048?utm_source=chatgpt.com)

这篇不属于直接的 serving framework 优化，但对低比特训练—部署数值一致性很有参考价值。

### 核心思路

LoRA 虽然降低了 trainable parameter 数量，但冻结的 Linear 投影仍可能消耗大量计算资源，Backward activation storage 也很昂贵。

PACT 选择：

**冻结的 Linear：原生 NVFP4 GEMM。**

**LoRA trainable branch：保留更高精度。**

同时，它尽量复用已经量化的中间表示。

具体包括：

- 重用 quantized RMSNorm output；
- Gate/Up activation 以 NVFP4 保存供 backward 使用；
- Nonlinear forward 保留必要的 BF16 input；
- 预先缓存 Forward/Backward 所需的不同 FP4 weight layout；
- 对 frozen weights 使用适应 NVFP4 scale 与 quantized activation 的 GPTQ calibration。

作者在 16GB RTX 5080 上测试了多种模型与任务，报告了更低的显存占用、更快的 LoRA fine-tuning，以及具有竞争力的准确率。摘要没有提供一个能够普遍适用的加速百分比，所以这里不人为给出 headline speedup。[arXiv](https://arxiv.org/abs/2610.25048)

### 为什么值得关注？

这篇和普通 QAT 的区别在于：

> **它不仅模拟 FP4 数值误差，也尝试让训练数据流实际使用与低比特执行相匹配的物理表示。**

这与此前 vLLM 提出的 train-inference numerical consistency 是同一方向。

从长期看，低比特训练可能会越来越重视：

**训练时的量化表示能否直接成为最终部署时的表示。**

# 本周最重要的三个判断

## 第一，低比特 Attention 已经进入按计算阶段分配精度的阶段

FlashInfer #6936 的结果很有代表性。

**QK4PV8 比原 FP8 Attention 更快，而且比 QK4PV4 更准确；但 QK4PV4 仍然最快。**

所以未来的 Attention 量化不能只说：

> “整个 Attention 使用 NVFP4。”

更合适的描述是：

**Q precision × K precision × QK compute × Softmax precision × PV compute × V precision。**

每个环节都可能有不同的最优格式。

## 第二，低比特与稀疏性不是简单叠加关系

新论文表明，至少在其测试的硬件与训练预算下：

**从较高精度直接降 bit，可能优于在原精度上引入 2:4 sparsity。**

但在已经达到最低硬件精度后，sparsity 仍可能提供额外 GEMM 收益。

对 Rubin 来说，接下来最值得研究的是：

**FP4 code、scale selection、sparsity pattern 与真实 sparse MMA execution 的联合优化。**

不能只看理论稀疏倍数。

## 第三，低比特执行契约已经扩展到跨 GPU 和跨存储层级

本周两个故障尤其典型：

**TensorRT-LLM：跨 EP Rank 的 NVFP4 input_scale 不完整。**

**SGLang：KV 恢复时遗漏 DSA Indexer sidecar。**

它们说明真正的低比特数值正确性不只取决于：

`Quantize → GEMM → Dequantize`

而是取决于完整链条：

**Checkpoint → Quantization → Rank Sharding → Communication → KV/Indexer Storage → Reload → Native Consumer → Speculative Verification。**

其中任何一个环节的 scale/layout/state 不一致，都可能造成 silent error。

---

## 本周最值得优先跟进的三个项目
