## NVFP4 编译必须保留真实 scale 布局｜TE-NVFP4-COMPILE-LAYOUT｜已合入主分支｜10-20 UTC｜TE / torch.compile / Blackwell

**结论：** 修复不仅涉及高维输入无法编译；Bias backward 的 fake metadata 与原生 packed tensor 不一致，会让编译 GEMM 按错误布局解释 scale，影响梯度。

**技术机制与证据：** 输入逻辑形状可以是三维、四维，原生量化却按展平后的二维矩阵生成 columnwise FP4 buffer。旧 metadata 没有始终遵循这一转换；另一路 fused bias-gradient quantization 会产生 compact scale，但 fake output 可能宣称它是 GEMM-swizzled scale。错误沿着“梯度 producer → fused quantize → TensorSpec 重建 → GEMM consumer”传播，不能仅用输入输出逻辑 shape 排除风险。

新实现由 NVFP4Quantizer 共享对齐条件，让 TensorSpec 携带真实布局标记，并让 Dynamo 看到 RHT fusion 环境变量变化，从而建立相应 guard。测试增加不同阶数、singleton 维、动态 batch、RHT 开关、compact/swizzled scale 和冷启动 CUDA Graph。Bias 测试不仅比较 dequantized 值，也比较 columnwise payload 和布局标记；确定性 NVFP4 分支以零容差比较 eager/compiled 的前向与梯度。关闭 stochastic rounding 是该测试的设置，不能推广为任意随机训练均逐位一致。[固定实现与测试](https://github.com/NVIDIA/TransformerEngine/commit/f0b1096128c0f41e18c6d0b4d6b4a3d749c0f008)。

**边界与影响：** 合入不代表所有硬件验证完成。核验日 PR 描述中，SM89 本地检查跳过了 NVFP4 硬件用例，并提示最终 SM100 测试待验证；当前说明不能作为截止前 CI 成功的证明。本报未做 B200 实测，也没有长期 loss 或吞吐结论。对 `ops.Linear + Bias + torch.compile` 用户，回归检查必须覆盖物理 scale layout 和 backward；只看 forward loss 或 BF16 eager，无法可靠区分量化误差与编译元数据错误。[PR 描述与状态](https://github.com/NVIDIA/TransformerEngine/pull/3628)。

## cuBLASMp 接入 NVFP4 overlap｜TE-NVFP4-CUBLASMP｜已合入主分支｜10-21 UTC｜cuBLASMp ≥0.11.0

**结论：** NVFP4 进入 TE 的 cuBLASMp 通信–GEMM overlap 路径；关键是设备端 alpha/beta 与全局 scale 衔接，而不只是通信 payload 变为四比特。

**技术机制与证据：** NVFP4 operand 包含 packed FP4、每 16 元素 UE4M3 block scale，以及经 amax 导出的 tensor-level scale。TE 在 GPU 计算全局乘数 alpha；先读回 CPU 再调用 GEMM 会引入主机同步。cuBLASMp 0.11.0 的 device pointer mode 允许新代码在 context 设备 buffer 保存 alpha 与 beta 0/1，沿当前 stream 写入，以 TN 布局和对应 columnwise payload/amax 交给消费端。

Backward 还必须控制随机量化次数：Dgrad 使用 rowwise grad_output，Wgrad 需要 columnwise 表示。新路径在 Dgrad 前一次生成两种 usage，随后为 Wgrad gather 已生成的 columnwise 数据；再次量化会重新抽取 stochastic-rounding 随机数，改变与非 overlap 路径的关系。接口要求 all-gather operand 在各 rank 上 amax 一致，因为每个 rank 用本地全局 scale 解释汇聚数据。只传 payload 而忽略这一契约，不能保证远端数据有相同数值含义。[固定实现、接口与测试](https://github.com/NVIDIA/TransformerEngine/commit/6b5cd7e2e43cee6da5dff9b9f86bc2ec05d7b1ad)。

**边界与影响：** 编译期和实际加载库均须 ≥0.11.0；row-scaled NVFP4、UE5M3 block scale、量化输出被拒绝。`n / tp_size` 非 128 倍数时，部分 RS/AR 路径回落默认算法并警告；Userbuffers 不因这项修改获得 NVFP4 支持。新增测试以量化后反量化的 operand 为参考，避免将固有量化误差误判为通信错误，却不证明 optimizer/master weight 或长期收敛。本期不引用未经匹配配置验证的 step speedup。它打开了可测试的软件边界，收益仍取决于 TP、shape、互联和 scale 同步成本。

NVFP4 scale-type wrapper 接收了 `rht_matrix`，却继续传 `nullptr`，触发非空断言；补丁恢复转发。它是已有路径回归修复，不是新 RHT 算法，也不是旧周报“静默全零”的再次报道。该修改不证明历史共享内存问题同时解决；B200/SM100 用户不能套用 SM120/121 的故障边界。[固定提交](https://github.com/NVIDIA/TransformerEngine/commit/4a3a8a8e8578e96319467d0cc96b9f5db552a7d3)。

## 长程 NVFP4 recipe 不能只凭短跑排名｜NVFP4-LONG-HORIZON｜论文实验｜10-17 UTC｜Blackwell

《What Matters for NVFP4 Training?》比较共同训练栈下的 recipe。作者在 Nemotron-H 8B 与 30B-A3B 上训练至 1T tokens，结合一维权重量化、backward 重量化、128 维 RHT、梯度 MS-EDEN 与选择性 4over6。重要负结果是 8B 全层 NVFP4 超过约 300B tokens 后发散，主要长跑保留末尾 15% 层为 BF16。短跑可筛灾难性错误，不能据此证明长期收敛；没有可直接换算为 B200 端到端收益的统一吞吐证据。[论文 v1，表1与§4–6](https://arxiv.org/html/2610.24343v1)。
