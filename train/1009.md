## 低比特训练技术简报｜10 月 2—9 日

本周没有值得单列的新 FP4/FP8 训练论文，也没有新的 4over6 训练结果。高信号进展全部来自实现：UE5M3 block scale 首次进入 Transformer Engine、NVFP4 scale learning 获得完整官方流程，以及三个会影响实际 scale/Wgrad 语义的正确性修复。

### 1. Transformer Engine 落地 UE5M3-scaled NVFP4 prototype

10 月 4 日，TE 将此前的 UE5M3 研究方案实现为可运行原型：

```python
from transformer_engine.common.recipe import Format, NVFP4BlockScaling

recipe = NVFP4BlockScaling(fp8_format=Format.UE5M3)
```

**已证明的实现事实：**

- FP4 payload 仍为 E2M1；每 block scale 改为 unsigned E5M3，scale 上界从 E4M3 的 `448` 扩展为 `114688`。
- cuDNN fused GEMM 路径覆盖前向和反向，Wgrad 显式进入 cuDNN Wgrad API。
- `GroupedLinear` 已接通，但 UE5M3 grouped GEMM 必要时会拆成逐 expert dense GEMM。
- 新增精确量化/GEMM reference tests：
  - `tests/pytorch/nvfp4/test_nvfp4_quantize_exact.py`
  - `tests/pytorch/nvfp4/test_nvfp4_gemm_exact.py`
  - `tests/pytorch/nvfp4/test_nvfp4_group_quantize_graph_safe.py`

合入过程中发现两个很有价值的数据流错误：持久化 weight scale 曾被原地 swizzle，optimizer step 重写成未 swizzle layout 后标记却未清除；在真实 DeepSeek-V3 weight 上造成 `2.6` relative error、loss `12.98`，对照 E4M3 为 `7.86`。另一次修复解决了 helper 实际把未 swizzle scale 传入 GEMM、导致 routing 塌缩到 expert 0 的问题。

**限制：**仍标为 prototype；没有新收敛或吞吐数据。JAX 路径仍有硬编码 E4M3 `448` 的待办，当前测试也把 UE5M3 与 4over6 组合标为不支持。[官方提交](https://github.com/NVIDIA/TransformerEngine/commit/d0b4b32c8e9046246a7ea20025eb06eaba3d7a6b)

### 2. NVFP4 scale learning 获得官方算法、结果和 Megatron 接入

Model Optimizer 10 月 7 日发布完整说明，并由 Megatron-LM 同日接入训练参数组。

其核心是直接学习每 16 个权重共享的 NVFP4 block scale。Dual-LSQ 将量化前后的 scale 解耦：

\[
\tilde x=s_{\text{post}}\,
Q_{\mathrm{E2M1}}\!\left(x/s_{\text{pre}}\right)
\]

训练时通过 STE 更新 `_amax_pre`、`_amax_post`；导出时丢弃 pre-scale，将 post-scale 烘焙进普通 NVFP4 checkpoint，因此部署格式和 kernel 不变。

Megatron 使用方式：

```bash
--lsq-scale-lr 1e-4
```

设置 `--lr 0` 且保持非零 `--lsq-scale-lr`，即可只训练 scales。实现还把 owning expert weight 的 `.allreduce` 属性传播给 LSQ amax 参数，避免它们在 EP 下错误进入全局 DP group。

Nemotron 3.5 Lightning 的官方单次结果中，scale-only learning 相比 MSE PTQ 在六项测试中五项改善、一项持平；KL loss 约从 `0.090` 降至 `0.045`。官方建议 scale LR 从 `1e-4` 起步，部分模型约 50 step 即可收敛。

**限制：**这是 fake-quant QAD，不是低比特 Dgrad/Wgrad；虽然只有约 `1/16` 的参数及 optimizer state 可训练，仍需完整反向计算。Dual scale 并非始终优于 tied scale，公开结果也主要来自单个模型配置。[算法、配置与结果](https://nvidia.github.io/Model-Optimizer/announcements/scale-learning.html)、[Megatron 接入](https://github.com/NVIDIA/Megatron-LM/commit/965e9068c77be47ed5a88424652f7b07be14d363)

### 3. TE 修复“配置写了 scale policy、实际 quantizer 没采用”

`Float8CurrentScaling` 和 `Float8BlockScaling` 原先在类定义时创建 `fp8_quant_*`，因此实例化时显式传入的：

```python
Float8CurrentScaling(use_power_2_scales=True)
Float8BlockScaling(use_f32_scales=True)
```

可能只改变 recipe 字段，却没有改变 Fprop input、Fprop weight 和 backward gradient 三套 `QParams`。

10 月 8 日的修复把它们移入 `__post_init__`，并为旧 pickle 增加 `__setstate__` 重建逻辑。官方最小复现确认旧行为会分别得到错误的 `False` 和 `True`。[github.com](https://github.com/NVIDIA/TransformerEngine/issues/3593?utm_source=chatgpt.com)

**为什么重要：**power-of-two 与 FP32 scale 会改变 scale rounding、有效动态范围，并同时影响 Fprop、Dgrad 和 Wgrad operands。日志中的 recipe 字段此前可能与实际执行语义不一致。

**限制：**只有使用显式非默认参数或依赖不同实例配置的运行受影响；提交没有量化现有训练的 loss 影响。[官方修复](https://github.com/NVIDIA/TransformerEngine/commit/14be43fb924af0431d99e3fcc9043574b3afbefd)

### 4. MFSDP v2 将 delayed Wgrad 同步推迟到真正的反向末尾

TE delayed Wgrad 可以在普通 autograd completion callback 之后才生成。旧 MFSDP v2 callback 此时已经等待 reduction stream，导致后续 Wgrad reduce-scatter 没有被该 wait 覆盖，optimizer 可能过早读取或修改梯度。

新流程是：

```text
autograd backward
→ delayed Wgrad
→ Wgrad reduce-scatter
→ context.finish_grad_sync()
→ optimizer
```

实现要求 MFSDP v2 使用：

```python
fully_shard_context(caller_managed_grad_sync=True)
```

并由 `FullyShardedDataParallelV2.finish_grad_sync()` 显式等待。默认自动模式若遇到 autograd 后产生的 delayed Wgrad，现在会拒绝运行，而不是假设已同步。相关设计问题也明确指出，仅靠参数梯度 readiness 无法证明 TE delayed Wgrad 已完成。[github.com](https://github.com/NVIDIA/Megatron-LM/issues/7764?utm_source=chatgpt.com)

**限制：**测试覆盖 CUDA Graph replay、多 microbatch 和 delayed/immediate parity，但没有大模型长跑或 overlap 性能数据。[官方修复](https://github.com/NVIDIA/Megatron-LM/commit/441a987409b8fdd2b90b463f7999bac970109a43)

### 5. GTP 修复跨 CUDA stream 提前复用 Wgrad scratch

GTP 的 Wgrad reduce-scatter 调用 `Work.wait()` 后，会把 scratch 放回共享池；但 `wait()` 只为调用它的 stream 建立顺序，另一个 stream 仍可能取出同一 buffer 并覆盖尚未读取完成的数据。

修复后：

- RS 或 copy 完成时记录 CUDA event；
- 普通 scratch pool 与 symmetric-memory LIFO pool 都保存该 event；
- 下一个 writer checkout 时调用 `current_stream.wait_event()`；
- 不引入 CPU block 或全设备同步，未使用该 buffer 的计算仍可重叠。

这保护的是 Wgrad 的存储生命周期，独立于 operand 是 BF16、FP8 还是 FP4；低比特训练只是更容易同时启用 GTP、通信重叠和 delayed Wgrad。

**限制：**回归测试是定向 cross-stream poison test，没有端到端吞吐或跨 rank 数值统计。[官方修复](https://github.com/NVIDIA/Megatron-LM/commit/9de9bde025fea4b5d72fa78a0b94d4d0f3c85c48)

### 6. Megatron 发布统一低精度训练配置指南

10 月 3 日的新指南把 `delayed`、`tensorwise`、`mxfp8`、`blockwise`、`nvfp4` 和 custom recipe 的硬件要求、param-gather、CUDA Graph、CPU offload及稳定性开关整理到同一处。官方 roadmap 也将其列为低精度训练配置交付项。[GitHub](https://github.com/NVIDIA/Megatron-LM/issues/4997?utm_source=chatgpt.com)

尤其值得核对：

- MXFP8 param gather 应配合 `--reuse-grad-buf-for-mxfp8-param-ag`；
- `--fp8-wgrad False` 是保留高精度 Wgrad 的最后防线；
- NVFP4 起步配置建议 first/last layers 保持 BF16；
- optimizer CPU offload 目前只支持 delayed FP8；
- NVFP4 的 CUDA Graph 和 inference 支持仍标为 partial。

**限制：**这是配置参考，不是性能或收敛证据；“支持”不代表目标 shape 一定命中低比特 kernel，仍需 profiler 验证。[官方指南提交](https://github.com/NVIDIA/Megatron-LM/commit/b1a6f076993662664f824d1cb8e81e51cf572b8b)

## Worth testing

- 用同一组 `X/W/dY` 比较 E4M3-scale 与 UE5M3-scale NVFP4，分别记录 Fprop、Dgrad、Wgrad MSE；每次 optimizer step 后检查 weight scale layout、swizzle 标记和反量化 hash。
- 对 UE5M3 跑完整 CUDA Graph warmup/replay，并覆盖非 256 对齐 shape、GroupedLinear 和 FP4 param gather；确认没有 dense fallback 或 host-to-device offset allocation。
- 以 MSE 和 Local-Hessian 分别初始化 LSQ，交叉比较 tied/dual scale；使用 `--lr 0 --lsq-scale-lr 1e-4`，同时检查每个 expert amax 的 gradient-reduction group。
- 在运行时直接断言三套 `fp8_quant_*` 的 `power_2_scale`，并对旧 recipe pickle 做 restore 测试，避免只检查 recipe 顶层字段。
- 将 MFSDP delayed Wgrad 与 GTP scratch pool 组合做多 stream 压力测试：延迟 RS reader、poison 复用 buffer，并在 `finish_grad_sync()` 前后 hash 所有 rank 的 `main_grad`。
